# CLAUDE.md คือคู่มือประจำโครงงาน

> note: พูดว่า "commit คือเซฟไว้ในเครื่อง push คือส่งขึ้นตู้เซฟบนคลาวด์ สองอย่างนี้คนละอย่างกัน" · ยกตัวอย่างจริง "โน้ตบุ๊กหายหนึ่งเครื่อง = เสียเวลาซื้อใหม่ ไม่ใช่เสียงานทั้งเดือน"

# ก่อน push ต้องทำสิ่งนี้ก่อนเสมอ
- สร้างไฟล์ชื่อ **.gitignore**
- แปลว่า "รายการไฟล์ที่ห้ามส่งขึ้นไป"
- ต้องมี `node_modules` และไฟล์คีย์ผู้ดูแล
- ทำก่อน push ครั้งแรก ไม่ใช่หลัง
> note: ย้ำลำดับ "ทำ .gitignore ก่อน push เสมอ" ซ้ำสองรอบ · บอกว่า "ลำดับนี้สลับกันไม่ได้ เพราะของที่ขึ้นไปแล้วเอากลับลงมาไม่จบในคลิกเดียว"

!! ไฟล์คีย์ผู้ดูแล ห้ามขึ้น GitHub

> note: พูดช้า ๆ "คีย์ระดับผู้ดูแล (service account) คือกุญแจที่เปิดข้อมูลได้ทั้งฐาน ถ้ามันหลุดขึ้น GitHub สาธารณะ บอทเก็บไปได้ภายในไม่กี่นาที"

## ช่วงที่ 2 — NoSQL คิดแบบโฟลเดอร์และไฟล์ ⏱ 50 นาที ⭐
> note: บอกตรง ๆ ว่า "นี่คือหัวใจของทั้งเดือน ผมขอสมาธิเต็มที่ 50 นาทีนี้" · ขอให้ทุกคนพักมือจากคีย์บอร์ด ช่วงนี้ฟังและคิดตามอย่างเดียว

# คำถามเปิดช่วง
- ใครจัดไฟล์ในคอมพิวเตอร์ตัวเองเป็นบ้าง
- เคยสร้างโฟลเดอร์ แล้วมีโฟลเดอร์ย่อยข้างในไหม
- เคยตั้งชื่อไฟล์ให้รู้ว่าอะไรเป็นอะไรไหม
> note: ให้ผู้เรียนพิมพ์ 🙋 ในแชท รอจนได้อย่างน้อย 10 คน แล้วค่อยไปสไลด์ถัดไป · จังหวะนี้สำคัญ อย่าข้าม เพราะทั้งช่วงสร้างบนคำตอบนี้

!! คุณใช้ NoSQL เป็นอยู่แล้ว

> note: พูดว่า "ทุกคนที่ยกมือเมื่อกี้ ใช้วิธีคิดแบบ NoSQL มาหลายปีแล้วโดยไม่รู้ตัว วันนี้เราจะแปะชื่อทางการลงไปบนสิ่งที่คุณทำเป็นอยู่แล้วเท่านั้น"

# แบบเดิมที่เราออกแบบไว้เดือนที่ 1 — คิดเป็นตาราง

```flow chain
ตาราง | แถว | *คอลัมน์
```

> note: ชี้กล่องซ้ายสุดก่อนแล้วพูดว่า "นี่คือวิธีที่เราออกแบบข้อมูลกันไว้ตั้งแต่เดือนที่ 1 เปิดตารางหนึ่งใบ ข้างในมีแถว ในแถวมีคอลัมน์" · ไล่นิ้วไปทางขวาทีละกล่อง จบค้างที่กล่องเข้มขวาสุด · ย้ำเสียงหนักแน่นว่า "แบบนี้ไม่ได้ผิดและไม่ต้องทิ้งนะครับ สไลด์ถัดไปคือของชุดเดียวกันนี้ ในภาษาของ Firestore"

# แบบ Firestore — ของเดียวกัน คนละคำเรียก

```flow chain
โฟลเดอร์ | ไฟล์ | *ข้อมูลในไฟล์
```

> note: ชี้กล่องซ้ายสุดแล้วพูดว่า "โฟลเดอร์คือของที่สไลด์ที่แล้วเราเรียกว่าตาราง" · ไล่นิ้วไปขวาทีละกล่อง เทียบกับสไลด์ก่อนหน้าเป็นคู่ ๆ "แถวคือไฟล์ คอลัมน์คือข้อมูลในไฟล์" · จบค้างที่กล่องเข้มแล้วพูดว่า "ไม่มีของใหม่ที่คุณต้องเรียนเพิ่มเลยครับ มีแต่ชื่อเรียกใหม่สามคำ"

# แปลศัพท์ชุดที่ 1
| สิ่งที่คุณคุ้นอยู่แล้ว | เรียกว่า | ตัวอย่างใน FixIt |
|---|---|---|
| 📁 โฟลเดอร์ | Collection | `tickets` |
| 📄 ไฟล์ในโฟลเดอร์ | Document | ใบแจ้งซ่อม 1 ใบ |
| ✏️ ข้อมูลข้างในไฟล์ | Field | หัวข้อ สถานะ วันที่ |
> note: อ่านออกเสียงทีละแถวจากซ้ายไปขวา "โฟลเดอร์ เรียกว่า collection ตัวอย่างคือโฟลเดอร์ tickets" · ย้ำว่าถ้าจำสามคำนี้ได้ ที่เหลือของวันนี้จะตามได้ลื่นขึ้นมาก

# แปลศัพท์ชุดที่ 2
| สิ่งที่คุณคุ้นอยู่แล้ว | เรียกว่า | ตัวอย่างใน FixIt |
|---|---|---|
| 🏷️ ชื่อไฟล์ | Document ID | `t001` |
| 📁 โฟลเดอร์ย่อยข้างใน | Subcollection | `comments` |
| 🗺️ path เต็มของไฟล์ | Document Path | `tickets/t001/comments/c001` |
> note: ชี้ path เต็มแล้วพูดว่า "อ่านจากซ้ายไปขวาเหมือนที่อยู่บ้าน โฟลเดอร์ tickets ไฟล์ t001 ข้างในมีโฟลเดอร์ comments ไฟล์ c001" · ให้ห้องอ่านตามพร้อมกัน 1 รอบ

# หน้าตาจริงของ FixIt บน Firestore

```code
   📄 u002  { name: "สมหญิง", email: "...", role: "technician" }

📁 categories/
   📄 c001  { name: "ไฟฟ้า" }
   📄 c002  { name: "ประปา" }

📁 tickets/

              categoryId: "c001",  categoryName: "ไฟฟ้า",
              createdAt }
      📁 comments/
         📄 cm001 { authorId, authorName, message, createdAt }
```
> note: อย่าเพิ่งอธิบายบรรทัดที่จดชื่อซ้ำ ปล่อยให้ค้างไว้ก่อน · พูดว่า "ค่อย ๆ กวาดตาดูนะครับ นี่คือทั้งฐานข้อมูลของ FixIt อยู่ในภาพเดียว" · หยุด 10 วินาที

# สามข้อที่ต่างจากตาราง
- ข้อ 1 — ไฟล์ในโฟลเดอร์เดียวกันไม่ต้องเหมือนกัน
- ข้อ 2 — **ไม่มี JOIN**
- ข้อ 3 — ไม่มี Migration
> note: บอกว่า "สามข้อนี้คือทั้งหมดที่ต่างจากตารางแบบ Excel ที่คุณคุ้น ข้อ 2 คือข้อที่ทำให้คนสับสนมากที่สุด ผมจะใช้เวลากับข้อนั้นมากที่สุด"

# ข้อ 1 — ไฟล์ไม่ต้องมีหัวข้อเหมือนกัน
- ตาราง: ทุกแถวต้องมีคอลัมน์ครบเท่ากัน
- โฟลเดอร์: ไฟล์นี้มี 8 หัวข้อ ไฟล์นั้นมี 5 หัวข้อ ได้
- ยืดหยุ่นกว่า แต่ **เราต้องมีวินัยเอง**
- ไม่มีใครคอยห้าม
> note: พูดว่า "เหมือนโฟลเดอร์รูปในเครื่องคุณ บางรูปมีชื่อสถานที่ บางรูปไม่มี ระบบไม่บ่นสักคำ ความยืดหยุ่นนี้มีราคาของมัน"

!! `status` กับ `Status` ไม่ใช่ตัวเดียวกัน

> note: พูดว่า "ถ้าไฟล์หนึ่งสะกดตัวเล็ก อีกไฟล์สะกดตัวใหญ่ ระบบจะพังแบบเงียบ ๆ ไม่มี error ให้เห็น หน้าจอจะว่างเฉย ๆ" · บอกว่านี่คือเหตุผลที่ต้องเขียนโครงสร้างลง CLAUDE.md ให้ AI สะกดตามชุดเดียวกันทุกครั้ง · **บอกตรงนี้ด้วยว่า "นี่คือเหตุผลเดียวที่วันนี้เราจะมี prompt ยาวกว่าปกติอยู่ 2 อัน ตอนเขียนโครงสร้างและตอนใส่ข้อมูลตัวอย่าง เพราะต้องระบุชื่อช่องข้อมูลให้ครบทุกตัว งานอื่นกลับไปสั่งสั้นเหมือนเดิม"**

# ข้อ 2 — ไม่มี JOIN
- ในไฟล์ใบแจ้งซ่อม เก็บไว้เท่านี้ `reporterId: "u001"`
- อยากรู้ชื่อผู้แจ้ง ต้องเปิดโฟลเดอร์ `users` หาไฟล์ `u001` อีกที
- ทำทุกครั้งที่แสดงรายการ = ช้าและยุ่ง
- 20 ใบแจ้งซ่อม = เปิดหาอีก 20 รอบ
> note: **นี่คือสไลด์ที่ห้ามรีบที่สุดในคาบ** · เล่าเป็นภาพ "เหมือนคุณเปิดใบเสร็จแล้วเห็นแต่รหัสลูกค้า ต้องวิ่งไปเปิดแฟ้มทะเบียนลูกค้าอีกตู้หนึ่งทุกครั้งที่อยากรู้ว่าใคร" · ถามห้องว่าเคยเจอแบบนี้ในงานจริงไหม

# ทางแก้ — จดชื่อซ้ำไว้ในไฟล์เลย
- ศัพท์ทางการเรียกว่า **Denormalize (จดซ้ำ)**
- เก็บทั้ง `reporterId` และ `reporterName`
- เปิดไฟล์ใบเดียว ได้ครบทุกอย่างที่ต้องแสดง
- ไม่ต้องวิ่งไปเปิดโฟลเดอร์อื่น
> note: ย้ำคำเทียบ **Denormalize = จดข้อมูลที่ใช้บ่อยซ้ำไว้ในไฟล์เลย จะได้ไม่ต้องไปเปิดหาที่อื่น** · พูดว่า "ถ้าตอนบ่ายชื่อผู้ขอลาไม่ขึ้นบนหน้าจอ 90% คือคุณเก็บแต่ ID ไว้ กลับมาที่สไลด์นี้"

# ไม่มี JOIN จึงต้องจดชื่อซ้ำ

```flow compare
❌ เก็บไว้เฉพาะรหัส :: เปิดใบแจ้งซ่อม | *เห็นรหัส u001 | เปิดโฟลเดอร์ users
✅ จดชื่อซ้ำไว้ในไฟล์ :: เปิดใบแจ้งซ่อม | เห็นชื่อสมชาย | จบในไฟล์เดียว
```

> note: ชี้แถบบนไล่จากซ้ายไปขวา หยุดค้างที่กล่องเข้มแล้วพูดว่า "ถึงตรงนี้หน้าจอขึ้นแต่ u001 อ่านแล้วไม่รู้ว่าใคร" · ชี้กล่องขวาสุดของแถบบนแล้วพูดว่า "ต้องวิ่งไปเปิดอีกโฟลเดอร์ ใบแจ้งซ่อม 20 ใบก็ 20 รอบ" · จากนั้นเลื่อนลงชี้แถบล่างทีละกล่องจากซ้ายไปขวา ปิดท้ายที่กล่องขวาสุดว่า "จบในไฟล์เดียว นี่คือสิ่งที่เรียกว่าจดซ้ำ"

# ทวน — ถึงตรงนี้เราได้อะไรมาแล้ว
- โฟลเดอร์ = Collection · ไฟล์ = Document
- ข้อมูลในไฟล์ = Field · โฟลเดอร์ย่อย = Subcollection
- ไม่มี JOIN → จดชื่อซ้ำ
- จดซ้ำมีราคา → ต้องไล่แก้เมื่อของเดิมเปลี่ยน
> note: ให้ทุกคนพิมพ์ในแชทว่า "ไม่มี JOIN แปลว่าอะไร" ตอบสั้น ๆ คนละบรรทัด · กวาดตาดูคำตอบ 10 อันแรก ถ้ามีคนตอบว่า "เชื่อมสองตารางไม่ได้" ให้ชมแล้วเสริมว่า "และทางแก้คือจดซ้ำ"

# แปลง ERD เป็นโฟลเดอร์ — กติกา 4 ข้อ
- ตาราง → 📁 โฟลเดอร์
- แถว → 📄 ไฟล์
- คอลัมน์ → ✏️ ข้อมูลในไฟล์
- **Foreign Key → เก็บ ID + จดชื่อซ้ำ** · ตารางลูก → 📁 โฟลเดอร์ย่อย
> note: บอกว่า "สี่บรรทัดนี้คือทั้งหมดของการแปลง ถ่ายรูปสไลด์นี้เก็บไว้ ตอนบ่ายคุณจะใช้มันกับ LeaveEasy และสัปดาห์หน้าใช้กับโครงงานตัวเอง"

# ERD ของ FixIt ที่เราออกแบบไว้เดือนที่ 1

```code
users ──1:N──► tickets ◄──N:1── categories
 id            id, หัวข้อ,        id, ชื่อหมวด
 ชื่อ           รายละเอียด,
 อีเมล,        สถานะ,
 บทบาท         ผู้แจ้ง(FK),
               ช่างที่รับผิดชอบ(FK),
               หมวดหมู่(FK)
                    │
                  1:N
                    ▼
               comments
                id, ตั๋ว(FK), ผู้เขียน(FK), ข้อความ
```
> note: พูดว่า "นี่คือของที่คุณออกแบบไว้ตั้งแต่เดือนที่ 1 มันไม่ได้ผิด และไม่ต้องทิ้ง เราจะแปลงมันเท่านั้น" · ชี้คำว่า FK แล้วบอกว่า **Foreign Key = ช่องที่ชี้ไปหาแถวในอีกตารางหนึ่ง**


> note: ใช้ภาพนี้ค้างไว้ระหว่างสาธิตการแปลง ถ้าจอไม่พอให้เปิดสองหน้าต่างข้างกัน

# ข้อจำกัดของการค้นหาที่ต้องรู้ไว้
- Firestore ค้นหาหลายเงื่อนไขพร้อมกันได้จำกัด
- การเรียงลำดับหรือกรองบางแบบต้องมี **Index**
- Index = สารบัญที่ช่วยให้ค้นหาเร็วขึ้น
- ระบบจะบอกเองว่าต้องสร้างเมื่อไร
> note: บอกล่วงหน้าเลยว่า "ตอนบ่ายบางคนจะเจอ error สีแดงเรื่อง index อย่าตกใจ ไม่ใช่ความผิดของคุณ"

# เจอ error เรื่อง index ให้ทำแบบนี้
- อ่าน error จะเห็นลิงก์สีฟ้าอยู่ในข้อความ
- **กดลิงก์นั้น** → เปิด Firebase Console
- กดปุ่มสร้าง Index → รอประมาณ 1–2 นาที
- กลับมารีเฟรชหน้าเว็บ
> note: พูดว่า "นี่เป็นเรื่องปกติของ Firestore ไม่ใช่ความผิดพลาด คนที่ทำระบบจริงก็เจอทุกคน" · ให้จดขั้นตอน 4 ข้อนี้ไว้ เพราะจะได้ใช้จริงตอนบ่าย

# "Backend" ในโลก Firebase อยู่ตรงไหน
- **Frontend** = หน้าจอที่ผู้ใช้เห็นและกด
- **Backend** = ส่วนที่ทำงานเบื้องหลัง ผู้ใช้แก้ไม่ได้
- หน้าเว็บของเราคุยกับ Firestore ได้โดยตรง
- เราไม่ต้องเขียนเซิร์ฟเวอร์เอง
> note: พูดว่า "คุณตัดงานไปได้ทั้งชั้นหนึ่ง ในหลักสูตรทั่วไป เรื่องนี้กินเวลาสองสัปดาห์" · แล้วเตือนว่า "สิ่งที่ทำหน้าที่ปกป้องข้อมูลแทนเซิร์ฟเวอร์คือ Security Rules ซึ่งเราจะลงลึกสัปดาห์หน้า"

# เส้นทางข้อมูลตอนกดบันทึก


> note: ชี้กล่องซ้ายสุดก่อน แล้วเลื่อนนิ้วไปทางขวาทีละกล่องพร้อมพูดว่า "ผู้ใช้กดปุ่มบันทึก หน้าเว็บเขียนไฟล์ใหม่ Firestore เก็บไฟล์นั้นไว้บนคลาวด์ แล้วหน้าเว็บอ่านกลับมาแสดง" · หยุดค้างที่กล่องเข้มแล้วพูดว่า "กล่องนี้เป็นกล่องเดียวที่อยู่บนคลาวด์ ที่เหลืออยู่ในเครื่องของคุณ ข้อมูลจึงไม่หายตอนปิดเบราว์เซอร์" · ปิดท้ายที่กล่องขวาสุดว่า "ตอนบ่ายถ้าข้อมูลหาย ให้ถามตัวเองว่าขาดตรงกล่องไหน"

- **แก้ข้อมูลในไฟล์** — เปลี่ยนสถานะเป็นกำลังซ่อม
- **ลบไฟล์** — ยกเลิกใบแจ้งซ่อม
> note: ย้ำคำเทียบ **CRUD = เพิ่ม / ดู / แก้ / ลบ ข้อมูล** · พูดว่า "สี่คำนี้คือทั้งหมดที่ระบบฐานข้อมูลทำได้ ไม่มีอย่างที่ห้า"

## ช่วงที่ 4 — ความปลอดภัยและ PDPA ⏱ 10 นาที

# ค่าตั้งค่า Firebase ที่อยู่ในหน้าเว็บ ไม่ใช่ความลับ
- ใครเปิดหน้าเว็บก็เห็นค่าชุดนี้ได้
- **เป็นแบบนี้โดยการออกแบบ ไม่ใช่ความผิดพลาด**
- สิ่งที่กันข้อมูลจริงคือ **Security Rules**
- Security Rules = ยามเฝ้าประตูโฟลเดอร์
> note: พูดว่า "หลายคนจะตกใจตอนเห็นค่าพวกนี้ในหน้าเว็บ ผมบอกไว้ก่อนว่าไม่ต้องตกใจ มันไม่ใช่กุญแจ กุญแจจริงคือกฎที่เราจะเขียนสัปดาห์หน้า"

# แต่วันนี้ ยามยังไม่มา
- โหมดทดสอบ = ประตูยังเปิดกว้าง
- ใครที่รู้ที่อยู่ ก็อ่านและเขียนข้อมูลได้
- เราจะปิดประตูสัปดาห์หน้าทั้งสัปดาห์
- วันนี้จึงมีกฎเหล็กหนึ่งข้อ
> note: อย่าทำให้ผู้เรียนกลัวจนไม่กล้าทำงาน พูดว่า "สถานะแบบนี้ปกติสำหรับวันแรกของทุกโครงงาน สิ่งที่ไม่ปกติคือปล่อยไว้แบบนี้แล้วเอาข้อมูลจริงใส่"

!! สัปดาห์นี้ใช้ข้อมูลจำลองเท่านั้น

> note: พูดเสียงหนักแน่น "ห้ามใส่ข้อมูลจริงของคนอื่นเด็ดขาด ไม่ใช่ชื่อจริงเพื่อนร่วมงาน ไม่ใช่เบอร์โทรจริง ไม่ใช่อีเมลจริงของลูกค้า ใช้สมชาย สมหญิง สมศรี" · บอกว่าผู้สอนจะเปิด Console ดูตอนตรวจงาน ถ้าเจอข้อมูลจริงจะให้ลบทันที
