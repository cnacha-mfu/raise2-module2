# สัปดาห์ที่แล้ว ระบบอ่านได้อย่างเดียว

- หน้ารายการอ่านจากฐานจริงแล้ว — แต่ปุ่มบันทึกยังหลอกอยู่
- กรอกใบใหม่ รีเฟรชแล้วหายเหมือนเดิม
- ระบบยังไม่รู้ว่าใครเป็นคนใช้
- และยังเปิดได้ในเครื่องเราเครื่องเดียว

> note: ถามห้องว่า "สัปดาห์ที่แล้วใครลองกดปุ่มบันทึกแล้วข้อมูลหายบ้างครับ" รอคำตอบในแชท แล้วพูดว่า "ถูกต้องแล้วครับ สัปดาห์ที่แล้วเราตั้งใจทำเฉพาะการอ่าน วันนี้สี่ข้อบนจอนี้จะหายไปทั้งหมดภายในเที่ยง"

!! ระบบรู้จักผู้ใช้ และออกสู่โลก

> note: หยุด 3 วินาที แล้วพูดว่า "ประโยคนี้คือความคิดเดียวของวันนี้ครับ เย็นนี้ระบบของคุณจะบันทึก แก้ ลบ ได้จริง รู้ว่าใครล็อกอินอยู่ และมี URL ที่คนอื่นเปิดได้"

# ปัญหาที่ทุกคนเจอเมื่อสัปดาห์ที่แล้ว

- เริ่มบทสนทนาใหม่ = อธิบายโปรเจกต์ใหม่ทั้งหมด
- ลืมบอกข้อตกลง → AI สะกดชื่อช่องข้อมูลเพี้ยน
- วันนี้งานใหญ่ขึ้น — พลาดแล้วแพงกว่าเดิม

> note: พูดว่า "สามข้อนี้ไม่ใช่ความผิดของคุณ และไม่ใช่ความผิดของ AI มันแก้ได้ด้วยไฟล์เดียว" · โยงกับ /clear ที่เรียนสัปดาห์ที่แล้ว "หลายคนไม่กล้า clear เพราะกลัว AI ลืม วันนี้ความกลัวนั้นจะหมดไป"

# CLAUDE.md — คู่มือประจำโครงงานที่ AI อ่านทุกครั้ง

- ไฟล์ข้อความธรรมดา วางที่โฟลเดอร์บนสุด
- **Claude Code อ่านไฟล์นี้ก่อนเริ่มงานทุกครั้ง**
- เขียนครั้งเดียว ใช้ได้ทุกบทสนทนา
- โครงงานเปลี่ยน ก็แก้เพิ่มได้ตลอด

> note: เปรียบว่า "เหมือนคู่มือที่วางไว้ให้พนักงานใหม่อ่านก่อนเริ่มงานวันแรก คุณไม่ต้องยืนอธิบายซ้ำทุกเช้า" · ย้ำคำแปล CLAUDE.md = คู่มือประจำโครงงานที่ AI อ่านทุกครั้งก่อนทำงาน

# /init — ให้ AI ร่าง แล้วเราอ่านตรวจ

```code

```

- คำสั่งนี้ทำแทนเราได้จังหวะที่ 1 และ 2 เท่านั้น
- ⭐ จังหวะที่ 3 — **อ่านแล้วบอกว่าอะไรขาด** ยังเป็นงานของเรา
- ร่างที่ได้จะบางมาก เป็นเรื่องปกติ — โครงสร้างข้อมูลต้องเติมเอง
- ⚠️ ไม่ได้ผล พิมพ์ `/help` แล้วสั่งด้วยประโยคธรรมดาแทน

> note: พูดว่า "ไม่ต้องนั่งพิมพ์ไฟล์นี้เองนะครับ พิมพ์ /init คำสั่งเดียว มันจะไล่อ่านโปรเจกต์แล้วร่างมาให้ดูก่อน ถามก่อนบันทึกด้วย" · **ย้ำหนักที่สุดที่บรรทัดสอง** "พิมพ์ /init แล้วผ่านไปเลยไม่ได้ครับ การอ่านแล้วรู้ว่าอะไรขาด คือทักษะที่เราฝึกกันทั้งเดือน และคำสั่งทำแทนคุณไม่ได้"

## ช่วงที่ 2 — ⭐ CRUD ให้ครบ 4 ตัว ⏱ 09:20–10:15

> note: พูดว่า "55 นาทีนี้คือหัวใจของวันนี้ครับ จบช่วงนี้ ปุ่มทุกปุ่มบนหน้าจอจะทำงานจริง" · บอกว่าจะสาธิตสลับกับสไลด์ตลอดช่วง ผู้เรียนไม่ต้องพิมพ์ตาม ทุกคำสั่งอยู่ในใบงานบ่ายนี้แล้ว

# CRUD = เพิ่ม ดู แก้ ลบ

| ตัว | แปลว่า | สถานะ |
|:---:|---|---|
| C | เพิ่มข้อมูลใหม่ลงฐาน | **วันนี้** |
| R | อ่านข้อมูลมาแสดง | เสร็จแล้วสัปดาห์ที่แล้ว ✅ |
| U | แก้ข้อมูลในไฟล์เดิม | **วันนี้** |
| D | ลบไฟล์ออกจากฐาน | **วันนี้** |

> note: ทวนคำเทียบ CRUD = เพิ่ม ดู แก้ ลบ ข้อมูล · พูดว่า "ตัว R เราทำเสร็จไปแล้วสัปดาห์ที่แล้ว วันนี้เติมอีกสามตัวที่เหลือ ทีละตัว ไม่ใช่พร้อมกัน"

!! ทำทีละตัว ตรวจ Console ทุกตัว ก่อนไปตัวถัดไป

> note: พูดช้า ๆ "นี่คือกติกาเหล็กของช่วงนี้ครับ ถ้าสั่งทั้งสามตัวรวดเดียวแล้วพัง คุณจะไม่รู้ว่าพังที่ตัวไหน ทำทีละตัว เปิด Firebase Console ส่องด้วยตา เห็นข้อมูลเปลี่ยนจริง ค่อยไปตัวถัดไป"

# วงจรของทุกตัว — เหมือนกันทั้ง 3 รอบ

```flow cycle
สั่งทำ 1 ตัว | ทดสอบบนหน้าจอ | *Console ยืนยันด้วยตา | commit
```

> note: ชี้กล่องซ้ายสุด "สั่งทำทีละตัว ใช้วงจร 4 จังหวะเหมือนเดิม" · กล่องสอง "กดปุ่มบนหน้าจอจริง" · **หยุดค้างที่กล่องเข้ม** "หน้าจอโกหกได้ แต่ Console ไม่โกหก ข้อมูลเข้าจริงต้องเห็นไฟล์ใน Console เปลี่ยน" · กล่องขวาสุด "สำเร็จแล้ว commit เก็บหมุดไว้ แล้ววนกลับไปเริ่มตัวถัดไป"

# C — ฟอร์มเพิ่ม บันทึกลงฐานจริง

- ปุ่มบันทึกจากสัปดาห์ที่แล้วยังหลอกอยู่ — วันนี้ต่อสายจริง
- ต้องบันทึก**ครบทุกช่อง รวมชื่อที่จดซ้ำ** ด้วย
- สถานะเริ่มต้นตั้งให้อัตโนมัติ ผู้ใช้ไม่ต้องเลือก
- วันเวลาที่สร้าง (`createdAt`) ติดมาเอง

> note: ชี้ข้อสองแล้วพูดว่า "จำเรื่องจดชื่อซ้ำจากสัปดาห์ที่แล้วได้ไหมครับ ตอนเพิ่มใบใหม่ ถ้าบันทึกแต่รหัส ไม่บันทึกชื่อ หน้ารายการจะขึ้นรหัสประหลาดทันที นี่คือจุดที่แผนของ AI มักขาด และเป็นหน้าที่เราตรวจ"

# ตรวจข้อมูลก่อนบันทึก — กันขยะเข้าฐาน

- กรอกไม่ครบ → ต้องขึ้นข้อความเตือน ไม่บันทึก
- วันที่สิ้นสุดมาก่อนวันที่เริ่ม → ต้องไม่ผ่าน
- ข้อความว่างเปล่า → ต้องไม่ผ่าน
- เตือนเป็นภาษาไทยที่ผู้ใช้เข้าใจ

> note: พูดว่า "ฐานข้อมูลจะดีเท่ากับข้อมูลที่เราปล่อยเข้าไป ศัพท์ทางการเรียกว่า validation แปลว่าตรวจข้อมูลก่อนบันทึก" · ยกตัวอย่างจริง "ใบแจ้งซ่อมที่ไม่มีหัวข้อ ช่างอ่านแล้วซ่อมอะไรไม่ได้เลย"

# 🎬 สาธิต — C: แจ้งซ่อมใบใหม่ ลงฐานจริง ⏱ 10 นาที

- ขอแผน → **แผนขาดเรื่องชื่อจดซ้ำ** → เราแก้แผน
- กรอกฟอร์ม → กดบันทึก → เปิด Console เห็นไฟล์ใหม่
- ทดสอบกรอกไม่ครบ → ต้องมีข้อความเตือน → commit

# Firebase Authentication — ระบบล็อกอินสำเร็จรูป

- **Authentication** = ระบบยืนยันตัวตน (สมัคร/เข้า/ออก)
- ใช้แบบอีเมล + รหัสผ่าน
- ไม่ต้องเขียนระบบรหัสผ่านเอง — เรื่องนี้พลาดแล้วเจ็บจริง
- เปิดใช้ใน Firebase Console ก่อน แล้วค่อยสั่ง AI ต่อ

> note: ย้ำคำแปล Authentication = ระบบยืนยันตัวตน หรือเรียกสั้น ๆ ว่าล็อกอิน · พูดว่า "การเก็บรหัสผ่านคนอื่นคืองานที่มืออาชีพยังพลาด เราไม่เขียนเองเด็ดขาด ใช้ของสำเร็จที่มีคนดูแลให้"

# uid — เลขประจำตัวผู้ใช้

- สมัครสำเร็จ ระบบออก **uid** (เลขประจำตัวผู้ใช้) ให้อัตโนมัติ
- ใช้ uid เป็น**ชื่อไฟล์**ในโฟลเดอร์ `users`
- ใบแจ้งใหม่บันทึกช่องผู้แจ้ง = uid ของคนที่ล็อกอินอยู่จริง
- ช่อง `role` (บทบาท) เก็บไว้ในไฟล์นั้น — มาจาก Persona

> note: พูดว่า "uid เหมือนเลขบัตรประชาชนของผู้ใช้ในระบบเรา ระบบออกให้เอง ไม่ซ้ำกันแน่นอน" · ชี้ข้อสาม "ตรงนี้แหละคือคำว่า ระบบรู้จักผู้ใช้ ใบไหนของใคร ตอบได้ทันที" · ข้อสี่บอกว่าค่า role ใช้รหัสอังกฤษตาม spec เพราะสัปดาห์หน้าจะใช้เขียนกฎ

# เส้นทางของการล็อกอิน

```flow chain
สมัคร / เข้าระบบ | ได้ uid ประจำตัว | *บันทึก uid ลงข้อมูล | รู้ว่าใบไหนของใคร
```

> note: ชี้กล่องซ้ายสุด "ผู้ใช้สมัครหรือเข้าระบบด้วยอีเมล" · กล่องสอง "Firebase ออก uid ให้" · **หยุดค้างที่กล่องเข้ม** "จุดสำคัญอยู่ตรงนี้ ทุกไฟล์ที่สร้างใหม่ต้องแนบ uid ของเจ้าของไปด้วย ถ้าลืมขั้นนี้ ล็อกอินได้ก็จริงแต่ข้อมูลยังไม่รู้เจ้าของ" · กล่องขวาสุด "พอมี uid ในไฟล์ สัปดาห์หน้าเราจะสั่งได้ว่าใครเห็นใบไหน"

# ก่อนออกออนไลน์ ต้องล็อกประตูอย่างน้อย 1 ชั้น

- โหมดทดสอบ = ตู้ที่ไม่ล็อกกุญแจ ใครรู้ที่อยู่ก็เปิดได้
- อีกครึ่งชั่วโมง ที่อยู่ตู้จะเป็นสาธารณะ
- **Security Rules** = กฎที่บอกว่าใครเปิดอะไรได้ (ยามเฝ้าข้อมูล)
- วันนี้ใส่กฎขั้นต่ำ 1 ข้อ: **ต้องล็อกอินก่อน ถึงอ่าน/เขียนได้**

> note: ย้ำคำแปล Security Rules = กฎที่บอกว่าใครเปิดข้อมูลอะไรได้ เปรียบเป็นยามเฝ้าประตูตู้ · พูดว่า "กฎละเอียดรายห้องเป็นเรื่องใหญ่ของสัปดาห์หน้า วันนี้เราใส่กุญแจประตูหน้าบ้านหนึ่งดอกก่อน ต้องล็อกอินก่อนถึงเข้าบ้านได้"

## ช่วงที่ 5 — 👥 Git หลายคนบน repo เดียว ⭐ ⏱ 11:10–11:35

> note: พูดว่า "ช่วงนี้ 25 นาที และเป็นของใหม่จริงของวันนี้ครับ บ่ายนี้เป็นครั้งแรกที่โค้ดของคุณจะไปอยู่บน GitHub และเป็นครั้งแรกที่โค้ดสองที่อาจไม่ตรงกัน ผมสอนตรงนี้เพราะอีกสองชั่วโมงคุณได้ใช้ทันที"

# บ่ายนี้โค้ดของคุณขึ้น GitHub เป็นครั้งแรก

- บ่ายนี้โค้ดของคุณจะขึ้น **GitHub** — ที่เก็บงานบนอินเทอร์เน็ต
- 👤 **ทุกคน commit ในชื่อตัวเอง** — สัปดาห์นี้เริ่มนับจริง
- ไม่มี commit เลยทั้ง Module = ไม่ผ่าน
- โค้ดอยู่สองที่แล้ว — ต้องมีกติกากันไม่ให้ทับกัน

> note: ย้ำข้อสองหนัก ๆ "ผมเปิดประวัติ repo ดูได้ว่าใครพิมพ์บ้าง และผมดูทุกสัปดาห์ ไม่ใช่รอตอนจบ" · ข้อสี่คือเหตุผลของช่วงนี้ — ตั้งแต่วันนี้โค้ดอยู่ทั้งในเครื่องและบน GitHub

# ก่อน push ครั้งแรก — .gitignore ต้องมาก่อน

- **.gitignore** = รายการไฟล์ที่ห้ามส่งขึ้น GitHub
- ต้องกัน `node_modules` และ**ไฟล์คีย์ทุกชนิด**
- ให้ AI สร้าง → เราตรวจด้วย `git status` ว่ากันได้จริง
- ลำดับสลับไม่ได้ — ของที่ขึ้นไปแล้ว มีคนคัดลอกได้ทันที

> note: ย้ำคำแปล .gitignore = รายการไฟล์ที่ห้ามส่งขึ้นไป · พูดว่า "ทำ .gitignore ก่อน push เสมอ สลับลำดับไม่ได้ เพราะไฟล์ที่เคยขึ้นไปแล้ว ต่อให้ลบทีหลัง ก็มีคนคัดลอกไปได้ตั้งแต่วินาทีแรก" · เตือนล่วงหน้า "ถ้าเผลอ push คีย์ขึ้นไป ให้เพิกถอนคีย์ก่อน แล้วค่อยลบไฟล์ ลบอย่างเดียวไม่พอ"

# push / pull — ส่งขึ้น กับ ดึงลง

```code
git pull     ดึงงานล่าสุดจาก GitHub ลงเครื่องเรา
git push     ส่งงานจากเครื่องเราขึ้น GitHub
```

- **pull = ดึงลง** ก่อนเริ่มงานทุกครั้ง
- **push = ส่งขึ้น** หลัง commit ทุกครั้งที่งานเสร็จ
- งานล่าสุดอยู่บน GitHub — เครื่องใครก็ตามอาจล้าหลัง

> note: เปรียบว่า "GitHub เหมือนแฟ้มกลางของโปรเจกต์ ก่อนเริ่มงานต้องหยิบแฟ้มเวอร์ชันล่าสุดมาก่อน ทำเสร็จต้องเอาไปคืนแฟ้มกลาง ถ้าใครทำงานบนเวอร์ชันเก่า เดี๋ยวจะไปทับของเพื่อน"

# กติกา 3 ข้อส่วนกลาง — ท่องให้ขึ้นใจ

- 1️⃣ **ดึงก่อนเริ่มเสมอ** — `git pull` ทุกครั้งก่อนแตะงาน
- 2️⃣ **push ทุกครั้งที่งานเสร็จก้อนหนึ่ง** — อย่าดองไว้
- 3️⃣ **แก้ที่เดียว** — อย่าแก้ทั้งบน GitHub และในเครื่องพร้อมกัน

> note: อ่านออกเสียงทีละข้อ แล้วพูดว่า "สามข้อนี้กันปัญหาได้เกือบร้อยเปอร์เซ็นต์ครับ ปัญหางานชนกันเกิดจากการละเมิดข้อใดข้อหนึ่งในนี้เสมอ" · บอกว่าบ่ายนี้จะให้ซ้อมทำให้ชนกันเองแล้วกู้ · และทักษะนี้คือของที่ Module 3 ใช้ตอนทำงานหลายคน

# ถ้าไม่มีกติกา จะเกิดอะไร

```flow compare
❌ แก้สองที่พร้อมกัน :: แก้บน GitHub | แก้ในเครื่อง | *pull แล้วชน
✅ ใช้กติกา 3 ข้อ :: ดึงก่อนเริ่ม | แก้ที่เดียว | push ผ่าน
```

> note: ชี้แถบบนทีละกล่อง "แก้บน GitHub ทีหนึ่ง แก้ในเครื่องอีกทีหนึ่ง พอ pull ลงมาก็ชนกัน" · หยุดที่กล่องเข้ม "ตรงนี้คือจุดที่คนตกใจที่สุด เห็นคำว่า conflict แล้วคิดว่างานหาย" · ไล่แถบล่าง "แถบล่างคือบ่ายนี้ของคุณ ถ้าตามกติกาสามข้อ จะไม่เจอแถบบนเลย"

# งานชนกัน (conflict) — หน้าตาเป็นแบบนี้

- push ถูกปฏิเสธ → ให้ pull ก่อน
- pull แล้วมีไฟล์ที่ขึ้นเครื่องหมาย `<<<<<<<`
- แปลว่า git ถามเราว่า **จะเก็บของใคร**
- **ไม่มีงานของใครหาย** — ทั้งสองเวอร์ชันอยู่ในไฟล์นั้น

> note: ย้ำข้อสุดท้ายหนักที่สุด "คำว่า conflict ฟังน่ากลัว แต่ความจริงคือ git เก็บของทั้งสองคนไว้ให้ครบ แล้วถามเราว่าจะเอาแบบไหน มันคือคำถาม ไม่ใช่ความเสียหาย" · แปลศัพท์ conflict = งานชนกัน สองคนแก้ที่เดียวกัน git เลือกเองไม่ได้

# 🎬💥 สาธิต — push ขึ้น GitHub แล้วทำให้งานชนกัน ⏱ 11 นาที

- สมมติว่ามีการแก้ไฟล์ไว้บน GitHub
- เราแก้ไฟล์เดียวกันในเครื่อง → push → **ถูกปฏิเสธ**
- pull → เจอเครื่องหมายชนกัน → ให้ Claude ช่วยรวม → push ผ่าน

> note: สลับไปสาธิตตามสคริปต์บล็อก E — **นี่คือจุดที่ตั้งใจให้พังจุดที่ 2 ห้ามตัด** · ตอน push ถูกปฏิเสธให้พูดว่า "เห็นไหมครับ ผมเองก็เจอ ทีนี้มาดูกันว่ากู้ยังไงใน 3 นาที" · จบแล้วทวนกติกา 3 ข้ออีกรอบ

## ช่วงที่ 6 — 🌐 Deploy ขึ้นออนไลน์ ⏱ 11:35–11:55

> note: พูดว่า "20 นาทีสุดท้ายของเช้าครับ และเป็นนาทีที่ผมชอบที่สุดของทั้งเดือน ระบบที่อยู่ในเครื่องเราคนเดียวยังไม่นับว่าเป็นระบบ อีกสิบนาที FixIt จะมีที่อยู่จริงบนอินเทอร์เน็ต"

# Deploy = นำเว็บขึ้นออนไลน์ให้คนอื่นเปิดได้

- **Deploy** = ส่งเว็บจากเครื่องเราขึ้นไปอยู่บนอินเทอร์เน็ต
- ใช้ **Firebase Hosting** (บริการที่ทำให้เว็บเรามี URL)
- `localhost` = ในเครื่องเราคนเดียว · URL จริง = ใครก็เปิดได้
- ยังไม่สมบูรณ์ก็ deploy ได้ — ไม่ต้องรอเสร็จร้อยเปอร์เซ็นต์

> note: ย้ำคำแปล Deploy = นำเว็บขึ้นออนไลน์ · Hosting = บริการที่ให้เว็บเรามีที่อยู่จริง · พูดว่า "จำคำว่า localhost จากสัปดาห์ที่แล้วได้ไหมครับ วันนี้เราจะเปลี่ยนจาก localhost เป็นที่อยู่ที่ส่งให้ใครก็ได้"

# เส้นทางของการ deploy

```flow chain
โค้ดในเครื่องเรา | คำสั่ง deploy | *Hosting บนคลาวด์ | ใครก็เปิด URL ได้
```

> note: ชี้ทีละกล่องจากซ้าย "โค้ดที่เสร็จแล้วในเครื่อง สั่ง deploy หนึ่งครั้ง มันจะถูกคัดลอกขึ้นไปวางบน Hosting" · หยุดที่กล่องเข้ม "ตั้งแต่วินาทีที่ของถึงกล่องนี้ เว็บเราไม่ได้อยู่ในเครื่องเราแล้ว ปิดคอมไปเลยก็ยังเปิดได้" · ปิดที่กล่องขวาสุด "และนั่นแปลว่าคนแปลกหน้าก็เปิดได้ด้วย เพราะฉะนั้นกฎเมื่อกี้ถึงต้องมาก่อน"

# deploy เว็บอย่างเดียวไม่พอ — กฎต้องขึ้นด้วย

- เว็บกับกฎ deploy แยกกันคนละส่วน
- กฎที่เขียนไว้ในเครื่อง **ยังไม่คุ้มครองของจริง** จนกว่าจะ deploy
- 🚫 **ห้ามออกออนไลน์โดยไม่มีกฎขั้นต่ำ** — ไม่มีข้อยกเว้น
- สั่ง AI ให้ deploy ทั้งเว็บและกฎในรอบเดียว

> note: พูดว่า "จุดพลาดคลาสสิกคือเขียนกฎไว้ในเครื่องแล้วนึกว่าปลอดภัยแล้ว กฎทำงานเฉพาะฉบับที่อยู่บนเซิร์ฟเวอร์ครับ ใบงานบ่ายนี้จึงเขียนให้ deploy กฎพร้อมเว็บเสมอ"

# ในเครื่องได้ ออนไลน์พัง — 2 สาเหตุหลัก

- สาเหตุ 1: **กฎยังไม่ deploy** — ขึ้น permission denied
- สาเหตุ 2: **index** (สารบัญช่วยค้น) ยังไม่สร้าง
- ทางแก้ index: อ่าน error → **กดลิงก์ในข้อความ** → กดสร้าง → รอ
- อ่าน error ให้จบบรรทัดก่อนตกใจ

> note: พูดว่า "สองอาการนี้คืออันดับหนึ่งกับสองของบ่ายนี้ ผมบอกล่วงหน้าเลย ถ้าเว็บออนไลน์พังแต่ในเครื่องปกติ ให้เช็กสองข้อนี้ก่อนเสมอ" · ทวน index จากสัปดาห์ที่แล้ว "Firestore จะบอกเองว่าต้องสร้างสารบัญ พร้อมแนบลิงก์มาให้กด ไม่ต้องทำเอง"
