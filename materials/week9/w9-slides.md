## 🧪 ช่วงที่ 1 — ให้ AI ทดสอบระบบแทนเรา · 1 ชม. 20 นาที
> note: เริ่มด้วยคำถามให้ห้องคิด — "หลังแก้โค้ดครั้งล่าสุด ใครไล่กดครบทุกหน้าบ้างครับ" · มักไม่มีใครยกมือ แล้วพูดว่า "นั่นแหละคือปัญหาที่ช่วงนี้แก้"

# ทำไมต้องทดสอบอัตโนมัติ
- ทุกครั้งที่แก้อะไร ควรไล่กดใหม่ทั้งระบบ
- ระบบมีหลายหน้า หลายเส้นทาง — กดเองทุกรอบไม่ไหว
- บั๊กที่หลุดถึงผู้ใช้ แพงกว่าบั๊กที่เจอในเครื่องเรา
- ให้หุ่นยนต์กดแทน แล้วเราไปทำอย่างอื่น
> note: พูดว่า "เราไม่ได้ทดสอบเพราะอยากได้ใบรับรอง เราทดสอบเพราะไม่มีเวลากดเองทุกรอบ" · บอกว่าชุดทดสอบนี้เป็น 1 ใน 5 ของส่งมอบให้ Module 3

# สัปดาห์ที่แล้วเรามี 🔍 Reviewer แล้ว
- สัปดาห์ที่ 8 เราตั้ง **Reviewer** ให้อ่านโค้ดแล้วรายงาน
- Reviewer เห็นโค้ด แต่**ไม่เคยกดปุ่มในเว็บของเราเลย**
- รายงานที่บอกว่าผ่าน **ไม่ใช่ใบรับประกัน**
- สัปดาห์นี้เราเติมอีกตัว — 🧪 **Tester**
> note: ทวน Reviewer สั้น ๆ 1 นาที ห้ามสอนซ้ำ เพราะทำไปแล้วสัปดาห์ที่ 8 · พูดว่า "Reviewer อ่านแบบแปลนบ้าน Tester เดินเข้าไปในบ้านแล้วลองเปิดประตูทุกบาน" · ย้ำว่าสองตัวนี้เจอปัญหาคนละแบบ

# 🔍 อ่านโค้ด ≠ 🧪 ใช้งานจริง
```flow compare
🔍 Reviewer (สัปดาห์ที่ 8) :: อ่านโค้ด | เดาว่าตรงไหนเสี่ยง | ไม่ได้กดจริง
🧪 Tester (สัปดาห์นี้) :: เปิดเบราว์เซอร์ | *กดใช้จริง | บอกว่าพังจริงไหม
```
> note: ชี้แถบบนก่อนแล้วพูดว่า "อันนี้คือของสัปดาห์ที่แล้ว มีประโยชน์ แต่มันเดาจากโค้ด" · เลื่อนลงชี้กล่องเข้มในแถบล่าง พูดช้า ๆ ว่า "กล่องนี้คือของใหม่วันนี้ — มันกดจริง มันจึงตอบได้ว่าพังจริงหรือไม่พัง" · ย้ำว่านี่ไม่ใช่การบอกว่า Reviewer ผิด สองอย่างนี้ใช้คู่กัน

# Sub-Agent แปลว่าอะไร — ทวน 1 นาที
- **Sub-agent = ผู้ช่วย AI อีกตัวที่มีหน้าที่เฉพาะ**
- เราตั้งชื่อ ตั้งหน้าที่ และตั้งขอบเขตให้มัน
- ตั้งค่าด้วย**ไฟล์**ที่วางไว้ในโฟลเดอร์โครงงาน
- **เราไม่พิมพ์ไฟล์นี้เอง — สั่ง Claude สร้างให้**
> note: พูดว่า "ไม่ใช่ AI ตัวใหม่ที่ต้องไปสมัคร มันคือ Claude Code ตัวเดิมที่เราสั่งให้สวมหมวกคนละใบ" · อ้างกลับสัปดาห์ที่ 8 ว่าเราทำแบบนี้มาแล้วครั้งหนึ่งตอนตั้ง Reviewer

# ทำไมการมี context แยกกันถึงได้ผล
- **Context** = "ความจำ" ของ AI ในหนึ่งบทสนทนา
- ตัวที่เขียนโค้ด มีเหตุผลของตัวเองค้างอยู่ในความจำ
- sub-agent เริ่มด้วย**ความจำเปล่า**
- จึงเจอสิ่งที่ตัวเขียนมองข้าม
> note: พูดว่า "นี่คือเหตุผลที่มันได้ผลจริง ไม่ใช่การตั้งชื่อใหม่ให้ดูดี" · เชื่อมกลับสัปดาห์ที่ 6 เรื่อง context บวมและ `/clear`

# MCP คืออะไร
- **MCP = ช่องทางให้ AI ใช้เครื่องมือภายนอกได้**
- ปกติ AI พิมพ์ข้อความและแก้ไฟล์ได้เท่านั้น
- มี MCP แล้ว AI หยิบเครื่องมืออื่นมาใช้ได้
- เปรียบเทียบ: **เหมือนต่อมือให้ AI**
> note: พูดว่า "เหมือนเมื่อก่อน AI พูดได้อย่างเดียว ตอนนี้มันหยิบของได้แล้ว" · ไม่ต้องลงรายละเอียดว่ามันทำงานเบื้องหลังอย่างไร ห้องนี้ไม่ต้องรู้

# Playwright คืออะไร
- **Playwright = หุ่นยนต์ที่กดใช้เว็บแทนคน**
- เปิดเบราว์เซอร์จริง · พิมพ์จริง · กดปุ่มจริง
- แล้วบอกกลับมาว่าเห็นอะไรบนหน้าจอ
- **Playwright MCP** = ต่อหุ่นยนต์ตัวนี้เข้ากับ Claude Code
> note: พูดว่า "เดี๋ยวจะได้เห็นเบราว์เซอร์เปิดขึ้นมาเองแล้วกดปุ่มเองสด ๆ ตรงนี้แหละที่ห้องมักจะฮือฮา" · บอกว่าเราสั่งเป็นภาษาไทย ไม่ต้องเขียนโค้ดเทสต์เอง

> note: อ้างกลับสัปดาห์ที่ 8 — "ตอนนั้นเราตั้งกติกา 3 อย่างของผู้ช่วย AI ไว้ หนึ่งในนั้นคือเรียกไม่สำเร็จแล้วระบบห้ามค้าง วันนี้เราให้เทสต์เป็นคนพิสูจน์ข้อนั้นแทนเรา" · บอกวิธีทำให้เรียกไม่สำเร็จแบบปลอดภัย: ใส่คีย์ผิดชั่วคราวในหน้าเว็บ แล้วค่อยใส่คีย์จริงกลับหลังเทสต์เสร็จ

# 💬 prompt เทสต์ปุ่ม AI
```prompt จังหวะที่ 1 — ขอแผนก่อน
ให้ tester วางแผนเทสต์ว่าถ้าเรียก AI ไม่สำเร็จ ระบบต้องไม่ค้าง
ร่างให้ผมดูก่อน ยังไม่ต้องรัน
```
- ⭐ ตอนแก้แผน ให้เพิ่มว่า **"ต้องเห็นข้อความภาษาไทย และปุ่มอื่นยังกดได้"**
> note: อ่าน prompt ออกเสียง แล้วบอกว่า "เทสต์ตัวนี้กับเทสต์ความปลอดภัยเป็นญาติกัน — ทั้งคู่ทดสอบวันที่แย่ ไม่ใช่วันที่ดี" · ย้ำว่าถ้าระบบของกลุ่มไม่มีปุ่ม AI ให้ข้ามเทสต์ตัวนี้ได้ แต่ต้องมีเทสต์ครบ 5 ตัวจากกลุ่มอื่นแทน

# เทสต์ fail — โค้ดผิด หรือเทสต์เขียนผิด
- เจอ fail แล้ว **อย่าเพิ่งแก้อะไรทั้งนั้น**
- อ่านก่อนว่ามันคาดว่าจะเห็นอะไร และเห็นอะไรจริง
- แล้วจึงตัดสินว่า **โค้ดผิด** หรือ **เทสต์เขียนผิด**
> note: พูดว่า "นาทีนี้คือนาทีที่คนส่วนใหญ่ตัดสินใจผิด — รีบแก้โค้ดให้เทสต์เขียว แล้วระบบพังเงียบ ๆ" · บอกว่าเดี๋ยวจะให้ดูของจริงตอนสาธิต

# เทสต์ fail แล้วทำอย่างไรต่อ
```flow chain
เทสต์ fail | *กดเองแล้วพังไหม | พังจริง = โค้ดผิด | ไม่พัง = เทสต์ผิด
```
> note: ชี้กล่องแรก "ตรงนี้ยังไม่ต้องแก้อะไรทั้งนั้น" · หยุดค้างที่กล่องเข้มกล่องที่สอง พูดว่า "ทุกอย่างขึ้นอยู่กับกล่องนี้ เปิดเว็บกดเองด้วยมือ 30 วินาที" · แล้วชี้สองกล่องขวาทีละกล่อง "พังเหมือนกัน แปลว่าโค้ดผิด ไปแก้โค้ด · กดเองใช้ได้ปกติ แปลว่าเทสต์เขียนผิด ไปแก้เทสต์" · ย้ำว่าห้ามข้ามกล่องที่สองไปเดาเอง

# วิธีแยกสองอย่างนี้ออกจากกัน
| อาการ | มักแปลว่า |
|---|---|
| กดเองแล้วก็พังเหมือนกัน | **โค้ดผิด** — ไปแก้โค้ด |
| กดเองใช้ได้ปกติ | **เทสต์เขียนผิด** — ไปแก้เทสต์ |
> note: พูดว่า "วิธีตัดสินคือเปิดเว็บกดเองด้วยมือ 30 วินาที จบ" · ย้ำว่าอย่าเดา ให้กดจริง · บอกว่าในกลุ่มให้คนที่ไม่ได้พิมพ์เป็นคนกดทดสอบด้วยมือ

!! ห้ามแก้โค้ดเพื่อให้เทสต์ผ่าน

> note: พูดว่า "เทสต์มีไว้จับปัญหา ไม่ได้มีไว้ให้ผ่าน" · เล่าว่าการลบเทสต์ที่ fail ทิ้งคือการปิดตาตัวเอง · บอกว่าถ้าเจอเทสต์ที่ fail แล้วยังแก้ไม่ทัน ให้เขียนลงบันทึกสิ่งที่ยังไม่เสร็จ ไม่ใช่ลบทิ้ง

> note: พูดว่า "ถ้านำเสนอจบแล้วไม่มีใครถามอะไรเลย แปลว่าเรายังไม่ได้อะไรกลับมา" · บอกว่าเราจะบังคับให้ผู้ฟังเขียน feedback ทุกคน

# 👥 ทุกคนในกลุ่มต้องพูด
- แบ่งกันเล่าคนละท่อน ไม่ใช่ตัวแทนพูดคนเดียว
- **ข้อนี้เป็นเกณฑ์ประเมินรายบุคคล**
- คนที่ไม่ได้พูดและตอบคำถามไม่ได้ = ยังไม่ผ่าน
- แม้ระบบของกลุ่มจะทำงานได้ครบก็ตาม
> note: พูดตรง ๆ ว่า "ข้อนี้ผมพูดล่วงหน้าตั้งแต่เช้า เพราะมันแก้ตอนบ่ายไม่ทัน" · บอกให้แบ่งท่อนกันตั้งแต่ตอนพักเที่ยง และให้คนที่พิมพ์น้อยที่สุดในกลุ่มเป็นคนสาธิตสด · เชื่อมกับกติกา commit ในชื่อตัวเอง

# โครงนำเสนอ 5 นาที — 5 ช่อง
- 1️⃣ ปัญหาคืออะไร
- 2️⃣ ผู้ใช้เป็นใคร
- 3️⃣ **สาธิตสดบน URL จริง** ← ใช้เวลามากที่สุด
- 4️⃣ สิ่งที่เรียนรู้ — อะไรพัง แก้อย่างไร
- 5️⃣ จะทำอะไรต่อใน Sprint 2
> note: พูดว่า "ช่องที่ 3 คือหัวใจ อีกสี่ช่องคือกรอบให้ช่องที่ 3 เข้าใจได้" · เตือนว่าห้ามใช้เวลาไปกับสไลด์แนะนำตัวสมาชิก

# 5 นาทีนั้นใช้อย่างไร — และใครพูดช่องไหน
```code
0:00 – 0:45   ปัญหา + ผู้ใช้เป็นใคร        คนที่ 1
0:45 – 3:00   🖥️ สาธิตสดบน URL จริง        คนที่ 2 (คนที่พิมพ์น้อยสุด)
3:00 – 4:00   สิ่งที่เรียนรู้ · อะไรพัง      คนที่ 3
4:00 – 5:00   Backlog Sprint 2             คนที่ 4 หรือวนกลับคนที่ 1
```
> note: พูดว่า "จับเวลาเข้ม มีนาฬิกาขึ้นหน้าจอ หมดเวลาแล้วหยุดจริง" · ชี้บรรทัดที่สองแล้วบอกว่า "คนที่พิมพ์น้อยที่สุดในกลุ่มเป็นคนสาธิต เพราะสาธิตได้แปลว่าเข้าใจจริง" · ให้ซ้อมกับกลุ่มตอนบ่ายอย่างน้อย 1 รอบ

# ถาม-ตอบ 3 นาที — ใครตอบ
- ผู้ฟังถาม **กลุ่ม** ไม่ได้ถามคนใดคนหนึ่ง
- คนที่ทำส่วนนั้นเป็นคนตอบ
- ตอบไม่ได้ ให้พูดว่า *"ยังไม่ทราบ จะไปหาคำตอบมา"*
- แล้ว**จดลง Backlog ทันที** ไม่ต้องเดา
> note: พูดว่า "การตอบว่ายังไม่ทราบแล้วจดไว้ ได้คะแนนมากกว่าการเดา" · บอกว่าผู้สอนและ TA จะเป็นคนถามอย่างน้อยกลุ่มละ 1 คำถาม และจะถามเจาะไปที่คนที่ยังไม่ได้พูด

# 📦 ของส่งมอบ 5 รายการ
- 1️⃣ URL ระบบที่ deploy ออนไลน์ใช้งานได้จริง
- 2️⃣ GitHub repo + CLAUDE.md + **commit ของทุกคน**
- 3️⃣ ชุดทดสอบ Playwright ที่ผ่าน
- 4️⃣ Backlog Sprint 2
- 5️⃣ บันทึกสิ่งที่ยังไม่เสร็จ
> note: อ่านทั้งห้าข้อช้า ๆ แล้วพูดว่า "ห้าข้อนี้คือสิ่งที่ Module 3 จะหยิบไปใช้ต่อวันแรก ขาดข้อไหนคือเริ่มช้าไปหนึ่งสัปดาห์" · บอกว่าเราจะไล่ทีละข้อในสไลด์ถัดไป

# 1️⃣ URL — ต้องเปิดจากเครื่องคนอื่นได้
- เปิดจาก**มือถือที่ไม่ได้ต่อ Wi-Fi เดียวกัน**
- ให้เพื่อนอีกกลุ่มลองเปิด แล้วบอกว่าเห็นอะไร
- ต้องเก็บข้อมูลลง Firestore ได้จริง ไม่ใช่ข้อมูลปลอม
- 🆘 เปิดไม่ได้ → กลับไปที่ขั้นตอน deploy สัปดาห์ที่ 8
> note: พูดว่า "URL ที่เปิดได้เฉพาะบนเครื่องตัวเอง ยังไม่นับว่าออนไลน์" · ให้จับคู่กลุ่มสลับกันเปิด URL ของอีกกลุ่มเดี๋ยวนี้ 1 นาที แล้วรายงานในแชท

# 2️⃣ repo — และ 👤 commit ของทุกคน
- ใน repo ต้องมี **CLAUDE.md** ที่ตรงกับระบบจริง
- **ทุกคนในกลุ่มต้องมี commit ในชื่อตัวเอง**
- คนที่ไม่มี commit เลย ถือว่ายังไม่ผ่าน Module
- ตรวจได้จากหน้าประวัติของ repo บน GitHub
> note: พูดตรง ๆ ว่า "ข้อนี้เป็นเกณฑ์รายบุคคล ไม่ใช่รายกลุ่ม" · ให้ทุกกลุ่มเปิดหน้าประวัติ commit ของ repo ตัวเองเดี๋ยวนี้ แล้วนับว่าเห็นชื่อครบทุกคนไหม · ใครยังไม่มี ให้แก้ตั้งแต่บ่ายนี้ อย่ารอถึงศุกร์

# 👤 ยังมีคนไม่มี commit ทำอย่างไร
- ให้คนนั้นเป็นคนคุมคีย์บอร์ดในช่วงถัดไปทันที
- ทำงานจริง 1 ก้อน แล้ว commit ในชื่อตัวเอง
- ❌ ห้ามให้คนอื่น commit แทนแล้วใส่ชื่อให้
- ปัญหานี้แก้บ่ายนี้ได้ แต่แก้วันศุกร์ไม่ทัน
> note: พูดว่า "ผมรู้ว่าบางกลุ่มมีคนหนึ่งที่พิมพ์เร็วกว่าคนอื่นมาก และมันเลยกลายเป็นแบบนี้ ไม่ใช่ความผิดใคร แต่ต้องแก้วันนี้" · บอกว่า TA จะเดินตรวจหน้าประวัติ commit ของทุกกลุ่มในช่วง 15:35 ตามที่นัดไว้

# 3️⃣ ชุดทดสอบ Playwright ที่ผ่าน
- เทสต์อยู่ใน repo ไม่ใช่อยู่ในหน้าจอที่เพิ่งรันอย่างเดียว
- ต้องรันแล้วผ่าน ณ วันที่ส่ง
- เทสต์ที่ยัง fail → เขียนลงข้อ 5 อย่าลบทิ้ง
- ⚠️ **ห้ามแก้โค้ดระบบเพื่อให้เทสต์ผ่าน**
> note: ย้ำประโยคสุดท้ายเป็นครั้งที่สองของวัน · พูดว่า "เทสต์ที่ fail และเราจดไว้ มีค่ามากกว่าเทสต์ที่เราลบทิ้งเพื่อให้รายงานสวย"

# 4️⃣ Backlog Sprint 2

> note: พูดว่า "ถ้าเขียนว่า *ปรับ UI ให้ดีขึ้น* Module 3 หยิบไปทำต่อไม่ได้ ต้องเขียนว่า *ทำให้ปุ่มบันทึกอยู่ในจอบนมือถือ*" · ให้กลุ่มเขียนอย่างน้อย 5 ข้อ
