## 🚀 ช่วงที่ 1 — สั่งทีเดียวจบจากสเปค · 80 นาที
> note: เปิดช่วงด้วยคำถาม — "สามสัปดาห์ที่ผ่านมาเราสั่ง AI ทีละขั้นมาตลอด ใครเคยคิดบ้างว่าถ้าสั่งทีเดียวจบเลยจะเป็นยังไง" · บอกว่าวันนี้จะได้ลองของจริง และจะได้เห็นทั้งข้อดีและราคาที่ต้องจ่าย

# วันนี้ลองอีกแบบ — สั่งทีเดียวจากสเปค
- ให้ AI อ่าน **สเปค** แล้วสร้างระบบทั้งชุดในรอบเดียว
- เราไม่ได้หายไป — **เราตรวจตอนจบ เทียบกับสเปค**
- ใช้ได้เพราะ **สเปคของเราชัดตั้งแต่ Module 1**
> note: ย้ำว่าสิ่งที่ทำให้วิธีนี้เป็นไปได้คือสเปคที่เขียนไว้แล้ว ไม่ใช่ความเก่งของ AI — "ถ้าสเปคกำกวม สั่งทีเดียวจะได้ของกำกวมกลับมาเร็วขึ้นเท่านั้นเอง" · **แทนสไลด์ที่ตัดออก:** เปิดด้วยการทวน 20 วินาที — 3 สัปดาห์ที่ผ่านมาเราสั่งทีละขั้น ทีละหน้า ทีละปุ่ม ตรวจทุกครั้งก่อนไปต่อ · ข้อดีคือพังตรงไหนรู้ทันที ข้อเสียคือช้าและเราต้องอยู่ทุกขั้น

# 🧾 สเปคคือใบสั่งงาน — ทวน 1 นาที
- หน้าจอกี่หน้า ชื่ออะไร
- โครงสร้างข้อมูล ชื่อโฟลเดอร์ ชื่อช่อง
- บทบาทผู้ใช้ และสิ่งที่แต่ละบทบาททำได้
- **สิ่งที่ห้ามทำ** — สำคัญที่สุดเวลาสั่งทีเดียว
> note: เปิดไฟล์ `fixit-spec.md` ค้างบนจอสัก 15 วินาทีให้เห็นของจริง · ชี้หัวข้อ "สิ่งที่ยังไม่ทำใน Module นี้" แล้วพูดว่า "ข้อนี้แหละที่กัน AI แถมของที่เราไม่ได้ขอ"

# 🤖 Sub-agent คืออะไร
- **ผู้ช่วย AI อีกตัวที่มีหน้าที่เฉพาะ**
- เราตั้งชื่อ ตั้งหน้าที่ ตั้งขอบเขต และ**ตั้งโมเดล**ให้มัน
- ตั้งค่าด้วย**ไฟล์**ที่วางไว้ในโฟลเดอร์โครงงาน
- **เราไม่พิมพ์ไฟล์นี้เอง — สั่ง Claude สร้างให้**
> note: พูดว่า "ไม่ใช่ AI ตัวใหม่ที่ต้องไปสมัคร มันคือ Claude Code ตัวเดิมที่เราสั่งให้สวมหมวกคนละใบ" · ย้ำข้อสุดท้าย เพราะบ่ายนี้ผู้เรียนจะสั่งสร้างเอง · **เสริมเรื่อง context:** ถ้ายัดงานทั้งระบบไว้ที่ผู้ช่วยตัวเดียว ความจำจะบวมแล้วเริ่มลืม — แยกผู้ช่วยแปลว่าแต่ละตัวจำเฉพาะงานของตัวเอง ทำงานขนานกันได้และหลงน้อยลง (ปัญหาเดียวกับ context บวมสัปดาห์ที่ 6 แต่แก้ด้วยการแบ่งงาน ไม่ใช่ล้างความจำ)

# แบ่งงานของสัปดาห์ที่ 6–8 ให้ 3 ผู้ช่วย
```flow chain
builder-ui หน้าจอ | builder-data ข้อมูล+ล็อกอิน | *builder-ai ปุ่มผู้ช่วย
```
> note: ไล่ทีละกล่อง — "กล่องแรกคืองานสัปดาห์ที่ 6 กล่องสองคือสัปดาห์ที่ 7 กล่องสามคือสัปดาห์ที่ 8" · บอกว่านี่คือการเอา 3 สัปดาห์มาอัดในรอบเดียว และนั่นคือเหตุผลที่ต้องแบ่งงาน

# 💰 เลือกโมเดลให้เหมาะกับงาน = ประหยัดโทเคน
| งานของผู้ช่วย | โมเดลที่พอ |
|---|---|
| สร้างหน้าจอตามสเปคที่ชัดแล้ว | `haiku` |
| ต่อฐานข้อมูล · CRUD · ล็อกอิน | `sonnet` |
| ปุ่มผู้ช่วย AI + ตรวจคำตอบ | `sonnet` |
> note: ย้ำประโยคนี้ — "ไม่ใช่ทุกงานต้องใช้โมเดลที่ฉลาดที่สุด งานทำตามแบบใช้ตัวเล็กก็จบ และถูกกว่าหลายเท่า" · บอกว่าเขียนบรรทัด `model:` ไว้ในไฟล์ตั้งค่าของผู้ช่วยแต่ละตัว · เสริมว่านี่คือทักษะที่ใช้ได้กับทุกงาน AI ไม่ใช่แค่หลักสูตรนี้

# 💬 สั่งสร้างผู้ช่วย 3 ตัว — อันนี้ยาวได้
```prompt พิมพ์แบบนี้
อ่าน fixit-spec.md แล้วสร้าง sub-agent ให้ผม 3 ตัว
1 builder-ui สร้างหน้าจอทุกหน้า ใช้โมเดล haiku
2 builder-data ต่อ Firestore ทำ CRUD และล็อกอิน ใช้โมเดล sonnet
3 builder-ai ทำปุ่มผู้ช่วย AI ใช้โมเดล sonnet
ทุกตัวห้ามทำงานนอกสเปค เสร็จแล้วให้ผมอ่านไฟล์ก่อน
```
> note: อธิบายว่าทำไม prompt นี้ยาวได้ — เพราะเป็น**รายการหน้าที่และชื่อโมเดล** ไม่ใช่การสั่งหลายงานพร้อมกัน · ย้ำบรรทัดสุดท้าย "ให้ผมอ่านไฟล์ก่อน" คือจังหวะที่ 3 ของเราที่ห้ามข้าม

# 💬 แล้วค่อยสั่งทีเดียวจบ
```prompt พิมพ์แบบนี้
ให้ผู้ช่วยทั้ง 3 ตัวสร้างระบบตาม fixit-spec.md ให้ครบ
แบ่งงานกันตามหน้าที่ของแต่ละตัว
เสร็จแต่ละส่วนให้รายงานผมทีละตัว
```
> note: ย้ำว่าเราสั่งเป็นภาษาไทยประโยคเดียว แต่สิ่งที่เกิดคือผู้ช่วยสามตัวเดินงานคนละส่วน · บอกให้ห้องสังเกตว่า Claude รายงานกลับมาเป็นช่วง ๆ ไม่ใช่เงียบยาว

# 🎬 ดูของจริง — สั่งทีเดียวจบจากสเปค ⏱ 22 นาที

- สั่งทีเดียว แล้วดูผู้ช่วยเดินงานทีละส่วน
- 👀 จุดที่ต้องดูให้ทัน: ชื่อโมเดลของแต่ละตัว และผลที่ได้กลับมา
> note: 📍 **สคริปต์สาธิต: `w9-demo-fixit.md` → ก้อน A (ขั้นที่ 1–3)** · จบแล้ว**กลับเข้าสไลด์ถัดไป** · ระหว่างรอให้เล่าว่ากำลังเกิดอะไรขึ้น อย่าปล่อยจอเงียบ

# ⭐ จังหวะตรวจ — เทียบผลกับสเปคทีละข้อ
- เปิดสเปคไว้ข้างจอ แล้วไล่ทีละหัวข้อ
- หน้าจอครบไหม · ชื่อช่องตรงไหม · สถานะครบไหม
- ขาดอะไร **สั่งแก้เฉพาะข้อนั้น** ไม่ต้องสั่งใหม่ทั้งชุด
- 🚫 ได้ของแถมที่ไม่ได้ขอ → สั่งเอาออก
> note: นี่คือหัวใจของช่วงนี้ ห้ามข้าม — "สั่งทีเดียวไม่ได้แปลว่าเราหายไป มันแปลว่างานของเราย้ายมาอยู่ตอนจบ" · บอกว่าของแถมที่ AI ใส่มาเองคือสิ่งที่ต้องเอาออก เพราะไม่มีใครดูแลมันต่อ

# ทีละขั้น vs ทีเดียว — ใช้เมื่อไร
```flow compare
🐢 ทีละขั้น :: ของใหม่ที่ยังไม่ชัด | แก้ของที่มีอยู่ | *ตอนกำลังเรียนรู้
🚀 ทีเดียว :: สเปคชัดแล้ว | งานซ้ำแบบเดิม | ทำใหม่จากศูนย์
```
> note: ชี้กล่องเข้มแล้วพูดว่า "ตอนกำลังเรียนรู้ ให้ใช้ทีละขั้นเสมอ เพราะคุณต้องเข้าใจสิ่งที่เกิดขึ้น" · ปิดด้วยคำถามประจำหลักสูตร — "หัวข้อของคุณ สเปคชัดพอจะสั่งทีเดียวหรือยัง" · **เกริ่นก่อนขึ้นรูปนี้ — ราคาที่ต้องจ่าย:** สั่งทีเดียวพังทีเดียวทั้งก้อน หาจุดพังยากกว่า · สเปคไม่ชัดจะได้ของไม่ตรงเร็วขึ้นเท่านั้น · และเปลืองโทเคนกว่าถ้าเลือกโมเดลไม่เป็น

## 🧪 ช่วงที่ 2 — ทดสอบด้วย Playwright · 60 นาที
> note: เริ่มด้วยคำถามให้ห้องคิด — "หลังแก้โค้ดครั้งล่าสุด ใครไล่กดครบทุกหน้าบ้างครับ" · มักไม่มีใครยกมือ แล้วพูดว่า "นั่นแหละคือปัญหาที่ช่วงนี้แก้"

# 👀 อ่านโค้ด ≠ 🧪 ใช้งานจริง
```flow compare
👀 อ่านโค้ดเอง :: เห็นแต่ตัวอักษร | เดาว่าตรงไหนเสี่ยง | ไม่ได้กดจริง
🧪 Tester (สัปดาห์นี้) :: เปิดเบราว์เซอร์ | *กดใช้จริง | บอกว่าพังจริงไหม
```
> note: ชี้แถบบนก่อนแล้วพูดว่า "แบบนี้มีประโยชน์ แต่มันเดาจากโค้ด" · เลื่อนลงชี้กล่องเข้มในแถบล่าง พูดช้า ๆ ว่า "กล่องนี้คือของใหม่วันนี้ — มันกดจริง มันจึงตอบได้ว่าพังจริงหรือไม่พัง" · **เปิดช่วงด้วยคำถาม:** "หลังแก้โค้ดครั้งล่าสุด ใครไล่กดครบทุกหน้าบ้างครับ" มักไม่มีใครยกมือ — นั่นคือเหตุผลของการทดสอบอัตโนมัติ — ไม่ใช่เพราะอยากได้ใบรับรอง แต่เพราะไม่มีเวลากดเองทุกรอบ · เสริมว่าอ่านโค้ดแล้วดูดีไม่ได้แปลว่ากดแล้วไม่พัง

# Playwright คืออะไร
- **Playwright = หุ่นยนต์ที่กดใช้เว็บแทนคน**
- เปิดเบราว์เซอร์จริง · พิมพ์จริง · กดปุ่มจริง
- แล้วบอกกลับมาว่าเห็นอะไรบนหน้าจอ
- **Playwright MCP** = ต่อหุ่นยนต์ตัวนี้เข้ากับ Claude Code

> note: ย้ำว่าตอนแก้แผนให้พิมพ์ว่า "เทสต์นี้ผ่านเมื่อระบบไม่ยอมให้เข้า และมีข้อความบอกผู้ใช้ · ถ้าเปิดดูได้ให้รายงานว่าไม่ผ่านพร้อมบอกว่าเห็นข้อมูลอะไร" · บอกว่ารูปแบบนี้คือรูปแบบเดียวกับที่จะใช้ตอนบ่าย · **เกริ่นก่อน ห้ามข้าม:** สองตัวนี้คือเทสต์ที่ **"เข้าไม่ได้ = ผ่าน"** ต้องเขียนกำกับให้ชัด ไม่งั้นรายงานจะถูกอ่านกลับด้าน · ทวนสองรอบเพราะห้องมักสับสน

# 💬 prompt เทสต์ปุ่ม AI
```prompt จังหวะที่ 1 — ขอแผนก่อน
ให้ tester วางแผนเทสต์ว่าถ้าเรียก AI ไม่สำเร็จ ระบบต้องไม่ค้าง
ร่างให้ผมดูก่อน ยังไม่ต้องรัน
```
- ⭐ ตอนแก้แผน ให้เพิ่มว่า **"ต้องเห็นข้อความภาษาไทย และปุ่มอื่นยังกดได้"**
> note: อ่าน prompt ออกเสียง แล้วบอกว่า "เทสต์ตัวนี้กับเทสต์ความปลอดภัยเป็นญาติกัน — ทั้งคู่ทดสอบวันที่แย่ ไม่ใช่วันที่ดี" · ย้ำว่าถ้าระบบของคุณไม่มีปุ่ม AI ให้ข้ามเทสต์ตัวนี้ได้ แต่ต้องมีเทสต์ครบ 5 ตัวจากเพื่อนแทน · **เกริ่นก่อน:** ตัวนี้พิสูจน์ว่าเรียก AI ไม่สำเร็จแล้วระบบต้องขึ้นข้อความและกดบันทึกต่อได้ ไม่ค้างหมุนตลอด

# วิธีแยกสองอย่างนี้ออกจากกัน
| อาการ | มักแปลว่า |
|---|---|
| กดเองแล้วก็พังเหมือนกัน | **โค้ดผิด** — ไปแก้โค้ด |
| กดเองใช้ได้ปกติ | **เทสต์เขียนผิด** — ไปแก้เทสต์ |
> note: พูดว่า "วิธีตัดสินคือเปิดเว็บกดเองด้วยมือ 30 วินาที จบ" · ย้ำว่าอย่าเดา ให้กดจริง · บอกว่าในห้องย่อยให้คนที่ไม่ได้พิมพ์เป็นคนกดทดสอบด้วยมือ · **เกริ่นก่อน:** เทสต์ fail ไม่ใช่เรื่องน่ากลัว มันคือสิ่งที่เทสต์มีไว้ทำ — คำถามเดียวคือ *โค้ดผิด* หรือ *เทสต์เขียนผิด* · **ถ้าผ่านบ้างไม่ผ่านบ้างแบบสุ่ม** มักเป็นเรื่องจังหวะเวลา สั่งว่า "ให้รอจนหน้าจอโหลดเสร็จก่อนค่อยตรวจ"

!! ห้ามแก้โค้ดเพื่อให้เทสต์ผ่าน

> note: พูดว่า "เทสต์มีไว้จับปัญหา ไม่ได้มีไว้ให้ผ่าน" · เล่าว่าการลบเทสต์ที่ fail ทิ้งคือการปิดตาตัวเอง · บอกว่าถ้าเจอเทสต์ที่ fail แล้วยังแก้ไม่ทัน ให้เขียนลงบันทึกสิ่งที่ยังไม่เสร็จ ไม่ใช่ลบทิ้ง
