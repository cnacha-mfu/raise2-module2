### ขั้นที่ 2 — สั่ง Claude สร้างหน้าล็อกอินและผูก uid ⏱ 8 นาที

**พูดว่า:** "ผมจะใช้วิธีเดิมที่เราใช้มาตั้งแต่สัปดาห์ที่ 6 — สั่งสั้น ขอแผนก่อน อ่านแผนแล้วแก้ แล้วค่อยสั่งลงมือทีละข้อ วันนี้ยิ่งต้องทำ เพราะเรื่องนี้พลาดแล้วข้อมูลรั่วได้"

**ทำ:** เปิด Terminal → รัน `claude` → วาง prompt จังหวะที่ 1 ด้านล่าง

**prompt จังหวะที่ 1 — ขอแผนก่อน:**
> ผมอยากเพิ่มระบบล็อกอินให้ FixIt ด้วย Firebase Authentication
> ช่วยเขียนแผนให้ผมดูก่อน อย่าเพิ่งลงมือ

**ผู้เรียนจะเห็น:** Claude ไม่แตะไฟล์เลย แต่เขียนแผนออกมาเป็นข้อ ๆ ประมาณนี้
1. สร้างหน้าสมัครสมาชิกและหน้าเข้าสู่ระบบ
2. เก็บข้อมูลผู้ใช้ลง Firestore หลังสมัครสำเร็จ
3. กันไม่ให้คนที่ยังไม่ล็อกอินเข้าหน้าอื่น
4. เพิ่มชื่อผู้ใช้และปุ่มออกจากระบบบนแถบบน

**ชี้ให้ดูตรงนี้:** 🔴 **หยุดที่นี่ 30 วินาที** อ่านแผนออกเสียงทีละข้อ แล้วถามห้องว่า "ข้อไหนยังไม่ครบครับ" · รอ 5 วินาที · เฉลยว่าข้อ 2 ยังไม่ได้บอกว่าชื่อไฟล์คืออะไรและข้างในมีอะไร — และนี่คือจังหวะเดียวที่แก้ได้ด้วยการพิมพ์บรรทัดเดียว

**ทำต่อ:** วาง prompt จังหวะที่ 3 เพื่อแก้แผน

**prompt จังหวะที่ 3 — แก้แผน:**
> ข้อ 2 ขอให้ตั้งชื่อไฟล์ใน `users` เป็น uid ของผู้ใช้
> ข้างในไฟล์มี `name`, `email`, `role` โดย `role` เริ่มต้นเป็น `"reporter"`

> ⚠️ **บรรทัดที่สองยาวกว่าปกติเพราะเป็นชื่อ field ที่ห้ามสะกดผิด** — Firestore แยกตัวพิมพ์เล็กใหญ่ สะกดผิดแล้วพังแบบเงียบ ๆ ส่วนคำสั่งอื่นให้กลับไปสั้นเหมือนเดิม

**prompt จังหวะที่ 4 — ลงมือ:**
> แผนโอเคแล้ว ลงมือข้อ 1 กับข้อ 2 ก่อน แล้วหยุดให้ผมทดสอบ

**ผู้เรียนจะเห็น:** Claude สร้างไฟล์หน้าจอใหม่ 2 ไฟล์ และแก้ไฟล์ตั้งค่า Firebase · จบด้วยข้อความสรุปว่าทำอะไรไปบ้าง แล้ว**หยุดรอ** ไม่ทำข้อ 3 ต่อเอง

**ทำต่อ:** กลับไปแท็บ 1 → รีเฟรช → สมัครด้วย `somchai@example.com` → ไปแท็บ 2 (Firestore) → กดโฟลเดอร์ `users`

**ผู้เรียนจะเห็น:** ไฟล์ใหม่ในโฟลเดอร์ `users` ที่ **ชื่อไฟล์เป็นตัวอักษรยาว ๆ** และข้างในมี `name`, `email`, `role: "reporter"`

**ชี้ให้ดูตรงนี้:** 🔴 **หยุดที่นี่ 30 วินาที** ชี้ที่ชื่อไฟล์แล้วพูดว่า "ตัวอักษรยาว ๆ นี้คือ uid — บัตรประจำตัวที่ Firebase ออกให้สมชาย ตั้งแต่นี้ไปเวลาระบบถามว่าใครใช้อยู่ คำตอบคือตัวนี้"

**ทำต่อ:** วาง prompt จังหวะที่ 1 ชุดที่สอง เพื่อผูก uid เข้ากับใบแจ้งซ่อม

**prompt จังหวะที่ 1 — ขอแผนก่อน:**
> ผมอยากให้ใบแจ้งซ่อมรู้ว่าใครเป็นคนแจ้ง
> ช่วยเขียนแผนให้ผมดูก่อน อย่าเพิ่งลงมือ

**prompt จังหวะที่ 3 — แก้แผน:**
> เพิ่ม 2 ช่องในไฟล์ของ `tickets` คือ `reporterId` (uid ของคนที่ล็อกอิน)
> และ `reporterName` (ชื่อจากไฟล์ใน `users`) แล้วเอาช่องพิมพ์ชื่อผู้แจ้งเองออก

**prompt จังหวะที่ 4 — ลงมือ:**
> แผนโอเคแล้ว ลงมือทีละข้อ เสร็จข้อไหนบอกผมก่อน

**ทำต่อ:** แจ้งซ่อมใบใหม่ 1 ใบ (พิมพ์ว่า "หลอดไฟห้องประชุม 3 กะพริบทั้งวัน") → ไปแท็บ 2 → เปิดไฟล์ที่เพิ่งเกิด

**ผู้เรียนจะเห็น:** ไฟล์ใบแจ้งซ่อมใหม่ที่มี `reporterId` เป็นตัวอักษรยาว ๆ ชุดเดียวกับชื่อไฟล์ใน `users`

**ชี้ให้ดูตรงนี้:** วางสองแท็บเทียบกันแล้วชี้ว่า "เลขนี้กับเลขนี้ตัวเดียวกัน — นี่คือกาวที่เชื่อมคนเข้ากับข้อมูล"

**เชื่อมกับ LeaveEasy:** "ของ FixIt คือ `reporterId` ในใบแจ้งซ่อม ตอนบ่ายของคุณคือ `requesterId` ในใบขอลา ชื่อต่างกันแต่เป็นเรื่องเดียวกัน"

![screenshot: สองแท็บเทียบกัน ฝั่งซ้ายไฟล์ใน users ฝั่งขวาไฟล์ ticket ที่มี reporterId ตรงกัน](assets/w8-21-uid-link.png)

### ขั้นที่ 3 — 💥 สาธิตข้อมูลรั่ว (จุดที่ตั้งใจให้พัง จุดที่ 1) ⏱ 6 นาที

> **ทำไมต้องมี:** ถ้าไม่เห็นการรั่วกับตา ผู้เรียนจะมองว่า Rules เป็นงานเอกสารที่น่าเบื่อ พอเห็นข้อมูลทั้งฐานไหลออกมาบนจอ ทุกคนจะตั้งใจฟังท่อนถัดไปทันที

**พูดว่า:** "ก่อนจะปิดประตู ผมอยากให้ทุกคนเห็นก่อนว่าตอนนี้ประตูของเราเปิดกว้างขนาดไหน ผมมีไฟล์ทดสอบเตรียมไว้ไฟล์หนึ่ง"

**ทำให้พังอย่างไร:**
1. เปิดไฟล์ `leak-test.html` ให้ผู้เรียนดู 5 บรรทัดสั้น ๆ — เป็นหน้าเว็บที่ **ไม่มีการล็อกอินเลย** แล้วสั่งอ่านทุกไฟล์ในโฟลเดอร์ `tickets` มาแสดง
2. **เปิดหน้าต่างไม่ระบุตัวตน** → ลากไฟล์นั้นเข้าไป
3. รอ 2 วินาที

**ผู้เรียนจะเห็น:** รายการใบแจ้งซ่อม **ทั้ง 8 ใบ** ไหลออกมาเต็มจอ พร้อมชื่อผู้แจ้งและรายละเอียด **ทั้งที่ไม่มีใครล็อกอินเลย**

**พูดตอนพัง:** "นี่คือระบบที่ผมทำเสร็จเมื่อสัปดาห์ที่แล้วครับ และผมยังไม่ได้ทำอะไรผิดเลย ผมทำตามที่สอนทุกอย่าง — ปัญหาคือเรายังไม่ได้ตั้งยาม"

**ทำต่อ (บีตที่สอง — โฟลเดอร์ย่อย):**
4. แก้ 1 บรรทัดในไฟล์เดิม ให้อ่าน `tickets/t001/comments` แทน → รีเฟรช

**ผู้เรียนจะเห็น:** ความเห็นการอัปเดตงานทั้งหมดของใบนั้นไหลออกมาอีกชุด

**พูดว่า:** "จำภาพนี้ไว้ให้ดี เพราะเดี๋ยวผมจะปิดโฟลเดอร์ `tickets` ให้ดู แล้วเรามาดูกันว่าโฟลเดอร์ `comments` จะปิดตามไหม"

**ชี้ให้ดูตรงนี้:** ชี้แถบที่อยู่ของเบราว์เซอร์ที่ยังเป็นหน้าต่างไม่ระบุตัวตน แล้วย้ำว่า "ไม่ได้ล็อกอิน ไม่ได้ใช้เครื่องมือพิเศษอะไรเลย"

**⚠️ ต้องพูดปิดท้ายทุกครั้ง:** "ไฟล์ทดสอบนี้ผมจะลบทิ้งหลังคาบ และข้อมูลในนี้เป็นชื่อสมมติทั้งหมด ตอนบ่ายห้ามทำแบบนี้กับข้อมูลจริงของใคร"

**พูดว่า:** "ผมไม่ได้จะสอนไวยากรณ์ของไฟล์นี้ ผมจะสั่งให้ Claude เขียนตามเช็กลิสต์ แล้วเราสองฝ่ายมาช่วยกันตรวจว่าครบ 5 ข้อไหม"

**⚠️ ต้องพูดก่อนวาง prompt:** "อันนี้เป็นข้อยกเว้นนะครับ ปกติผมสั่งสองบรรทัดแล้วขอแผนก่อน แต่ตรงนี้เป็นเช็กลิสต์ความปลอดภัย ตกไปข้อเดียวข้อมูลรั่ว ผมจึงวางให้ครบทั้ง 5 ข้อ พองานอื่นเราจะกลับไปสั่งสั้นเหมือนเดิม"

**ทำ:** วาง prompt ด้านล่างใน Claude Code

**prompt ที่ใช้ (กรณียกเว้น — ยาวได้เพราะตกข้อเดียวข้อมูลรั่ว):**
> เขียน Firebase Security Rules ให้โปรเจกต์ FixIt ลงไฟล์ `firestore.rules`
> ต้องผ่านเช็กลิสต์ 5 ข้อนี้ครบทุกข้อ
>
> 1. คนที่ไม่ได้ล็อกอิน อ่านหรือเขียนอะไรไม่ได้เลยทุกโฟลเดอร์
> 2. ผู้ใช้สร้างใบแจ้งซ่อมใหม่ได้เฉพาะที่ `reporterId` ตรงกับ uid ของตัวเองเท่านั้น
> 3. ผู้ใช้อ่านใบแจ้งซ่อมได้เฉพาะใบที่ตัวเองเป็นผู้แจ้ง ยกเว้นผู้ใช้ที่มี `role` เป็น `"admin"` ให้อ่านได้ทุกใบ
> 4. การเปลี่ยน `status` ของใบแจ้งซ่อม ทำได้เฉพาะผู้ใช้ที่มี `role` เป็น `"admin"`
> 5. เขียนกฎให้โฟลเดอร์ย่อย `tickets/{ticketId}/comments` ด้วย ห้ามลืม โดยให้อ่านและเขียนได้เฉพาะคนที่มีสิทธิ์อ่านใบแจ้งซ่อมใบแม่นั้น
>
> โครงสร้างข้อมูล
> ```
> users/{uid}      { name, email, role }   role เป็น "reporter" หรือ "admin"
> categories/{id}  { name }
> tickets/{id}     { title, detail, status, categoryId, reporterId, reporterName, createdAt }
>    comments/{id} { authorId, authorName, message, createdAt }
> ```
>
> เมื่อเขียนเสร็จ ให้อธิบายเป็นภาษาไทยทีละบล็อกว่าบล็อกนั้นตรงกับเช็กลิสต์ข้อไหน

**ผู้เรียนจะเห็น:** ไฟล์ `firestore.rules` ถูกสร้างขึ้น ตามด้วยคำอธิบายภาษาไทยเป็นข้อ ๆ ว่าบล็อกไหนตรงกับข้อไหน

**ชี้ให้ดูตรงนี้:** เลื่อนไปที่บล็อกของ `comments` แล้วพูดว่า "ข้อ 5 อยู่ตรงนี้ ถ้าคุณไม่สั่ง มันจะไม่มีบล็อกนี้ และคุณจะไม่รู้ตัวเลยว่าขาด"

**ทำต่อ — กวาดตาตรวจ 4 คำถามให้ผู้เรียนดู:**
- มีบล็อกครบทุกโฟลเดอร์ไหม (`users` · `categories` · `tickets` · `comments`)
- มีบล็อกของโฟลเดอร์ย่อยไหม
- มีคำว่า `request.auth` อยู่ทุกบล็อกไหม
- มีบล็อกไหนที่อนุญาตทุกคนหลงเหลืออยู่ไหม

**เชื่อมกับ LeaveEasy:** "ของ FixIt คือ `tickets` กับ `comments` ตอนบ่ายของคุณคือ `leaveRequests` กับ `approvals` — prompt ตัวนี้อยู่ในใบงานแล้ว เปลี่ยนชื่อโฟลเดอร์อย่างเดียว"

### ขั้นที่ 5 — deploy Rules แล้วดูของรั่วปิดลงกับตา ⏱ 4 นาที

**พูดว่า:** "เขียนเสร็จยังไม่พอ ต้องส่งขึ้นไปด้วย ตรงนี้คือจุดที่คนติดกันทั้งห้องทุกปี"

**ทำ:** ใน Terminal พิมพ์

```
firebase deploy --only firestore:rules
```

**ผู้เรียนจะเห็น:** ข้อความประมาณ 5–8 บรรทัด และบรรทัดสุดท้ายเขียนว่า **Deploy complete!**

**ทำต่อ:** กลับไปหน้าต่างไม่ระบุตัวตนที่ยังเปิด `leak-test.html` ค้างอยู่ → **กดรีเฟรช**

**ผู้เรียนจะเห็น:** ข้อมูลหายไปทั้งหมด เหลือข้อความ error ที่มีคำว่า **Missing or insufficient permissions**

**ชี้ให้ดูตรงนี้:** 🔴 **หยุดชี้คำว่า permissions** แล้วพูดว่า "คำนี้คือคำที่เราอยากเห็นตอนนี้ ตอนบ่ายถ้าคุณเห็นคำนี้ในหน้าจอของตัวเองแล้วตกใจ ให้กลับมาดูว่าคุณกำลังทดสอบในฐานะใครอยู่"

**ทำต่อ (ปิดวงของบีตที่สอง):** แก้ไฟล์ทดสอบกลับไปอ่าน `comments` → รีเฟรช → **ต้องถูกปฏิเสธเหมือนกัน**

**พูดว่า:** "ปิดตามด้วย เพราะเราสั่งข้อ 5 ไว้ ถ้าไม่สั่ง ตรงนี้จะยังเปิดโล่งอยู่และเราจะไม่มีทางรู้"

### ขั้นที่ 6 — ทดสอบด้วยการสวมรอยเป็นผู้ใช้อีกคน ⏱ 3 นาที

**พูดว่า:** "หน้าจอของผมผ่านเสมอ เพราะผมเป็นเจ้าของข้อมูล การทดสอบที่นับได้มีอย่างเดียวคือสวมรอยเป็นคนอื่น"

**ทำ:**
1. ไปแท็บ 4 → **Firestore → Rules → Playground** (สนามทดสอบกฎ)
2. ตั้งค่า: ประเภทคำขอ **get** · เส้นทาง `tickets/t001` · เปิดสวิตช์ **Authenticated** · ใส่ uid ของ **สมหญิง** (คนที่ไม่ใช่เจ้าของใบนี้)
3. กด **Run**

**ผู้เรียนจะเห็น:** แถบสีแดงขึ้นคำว่า **Denied** พร้อมชี้บรรทัดของกฎที่ปฏิเสธ

**ทำต่อ:** เปลี่ยน uid เป็นของ **สมชาย** (เจ้าของใบ) → กด Run อีกครั้ง → ขึ้น **Allowed** สีเขียว

**ชี้ให้ดูตรงนี้:** "แดงกับเขียวสลับกันตาม uid ที่ใส่ — นี่คือหลักฐานว่ายามทำงานจริง ไม่ใช่เพราะหน้าจอเราดูปกติ"

**เชื่อมกับ LeaveEasy:** "ตอนบ่ายนี่คือ Checkpoint ที่สำคัญที่สุดของสัปดาห์ — ล็อกอินเป็นพนักงาน ก. แล้วเปิดใบลาของพนักงาน ข. ไม่ได้"

![screenshot: Rules Playground ที่แสดงผล Denied เมื่อใส่ uid ของผู้ใช้คนอื่น](assets/w8-24-playground-denied.png)

### ขั้นที่ 9 — ปุ่ม "จัดหมวดหมู่อัตโนมัติ" ⏱ 6 นาที

**พูดว่า:** "ทีนี้เอามาต่อกับข้อมูลจริง สามขั้นเหมือนที่อยู่บนสไลด์ — อ่านจาก Firestore ส่งให้ AI แล้วบันทึกกลับ"

**ทำ:** วาง prompt จังหวะที่ 1 ด้านล่าง

**prompt จังหวะที่ 1 — ขอแผนก่อน:**
> ผมอยากเพิ่มปุ่มให้ AI ช่วยจัดหมวดหมู่ใบแจ้งซ่อม
> ช่วยเขียนแผนให้ผมดูก่อน อย่าเพิ่งลงมือ

**ผู้เรียนจะเห็น:** แผนเป็นข้อ ๆ ประมาณนี้
1. เพิ่มปุ่มในหน้าแจ้งซ่อมใหม่
2. ส่งข้อความของผู้แจ้งไปให้ AI
3. รับคำตอบมาใส่ช่องหมวดหมู่
4. บันทึกลง Firestore

**ชี้ให้ดูตรงนี้:** 🔴 อ่านแผนออกเสียง แล้วถามห้องว่า "แผนนี้ขาดอะไรครับ" · รอ 5 วินาที · เฉลยว่าขาดสองอย่างที่เราคุยกันบนสไลด์ — ไม่ได้ส่งรายชื่อหมวดหมู่ที่มีจริงไปด้วย และไม่มีการตรวจคำตอบก่อนบันทึก · "จังหวะนี้คือจังหวะที่เราทำงาน ไม่ใช่ AI"

**prompt จังหวะที่ 3 — แก้แผน:**
> ข้อ 2 ขอให้ส่งรายชื่อหมวดหมู่จากโฟลเดอร์ `categories` ไปด้วย
> ข้อ 3 ต้องตรวจก่อนว่าคำตอบอยู่ในรายการจริง ไม่อยู่ในรายการห้ามบันทึก
> เพิ่มอีกข้อ — มีป้ายบอกว่าเป็นข้อเสนอจาก AI · มีสถานะกำลังโหลด · รอเกิน 15 วินาทีต้องไม่ค้าง · ผู้ใช้แก้เองได้เสมอ

**prompt จังหวะที่ 4 — ลงมือ:**
> แผนโอเคแล้ว ลงมือทีละข้อ เสร็จข้อไหนบอกผมก่อน

**ทำต่อ:** พอ Claude ถามว่าให้ส่งข้อความแบบไหนไปหา AI ให้วางกล่องด้านล่าง

**⚠️ ต้องพูดก่อนวาง:** "กล่องนี้ยาวกว่าปกติ และมันเป็นข้อยกเว้น เพราะนี่ไม่ใช่คำสั่งที่ผมพิมพ์คุยกับ Claude แต่เป็นข้อความที่ระบบจะส่งให้ AI ทุกครั้งที่ผู้ใช้กดปุ่ม กติกาและตัวอย่างต้องครบ ถ้าตัดออก AI จะตอบผิดรูปแบบทันที"

**ข้อความที่ระบบส่งให้ AI (กรณียกเว้น — ต้องมีกติกาและตัวอย่างครบ):**
> ```
> คุณเป็นผู้ช่วยจัดหมวดหมู่ใบแจ้งซ่อมของอาคารสำนักงาน
> หมวดหมู่ที่มีอยู่ในระบบ: {รายชื่อหมวดหมู่จาก categories}
>
> ข้อความที่ผู้แจ้งพิมพ์มา:
> """{ข้อความจากช่องรายละเอียด}"""
>
> กติกาการตอบ
> - ตอบกลับมาเป็นชื่อหมวดหมู่เดียวจากรายการข้างบนเท่านั้น
> - ห้ามมีคำอธิบาย ห้ามขึ้นบรรทัดใหม่
> - ถ้าไม่แน่ใจ ให้ตอบว่า อื่น ๆ
>
> ตัวอย่าง
> ข้อความ: "หลอดไฟห้องประชุม 3 กะพริบทั้งวัน" → ไฟฟ้า
> ข้อความ: "ก๊อกน้ำห้องน้ำชาย ชั้น 2 ปิดไม่สนิท น้ำไหลตลอด" → ประปา
> ```
>
> ⚠️ ส่งเฉพาะข้อความรายละเอียดอาการเสีย ห้ามส่งชื่อ อีเมล หรือเบอร์โทรของผู้แจ้งไปด้วย

**ทำต่อ:** เปิดหน้าแจ้งซ่อมใหม่ → พิมพ์ `แอร์ห้อง 402 ไม่เย็นตั้งแต่เมื่อวาน มีน้ำหยดลงพื้นด้วย` → กดปุ่ม

**ผู้เรียนจะเห็น:**
1. ปุ่มเปลี่ยนเป็น "กำลังให้ AI ช่วยดู..." และกดไม่ได้
2. ประมาณ 2–5 วินาทีต่อมา ช่องหมวดหมู่เด้งเป็น **แอร์**
3. ใต้ช่องขึ้นป้ายสีอ่อนว่า **ข้อเสนอจาก AI — โปรดตรวจสอบก่อนยืนยัน**

**ชี้ให้ดูตรงนี้:** 🔴 ชี้ป้ายแล้วพูดว่า "ป้ายนี้ไม่ใช่ของประดับ มันคือหน้าที่ตามหลักการที่เราเรียนตั้งแต่เดือนที่ 1 ว่า AI แต่งเรื่องได้อย่างมั่นใจ ผู้ใช้ต้องรู้ว่ากำลังดูอะไรอยู่"

### ขั้นที่ 10 — 💥 จงใจให้ AI ตอบผิดรูปแบบ (จุดที่ตั้งใจให้พัง จุดที่ 2) ⏱ 6 นาที

> **ทำไมต้องมี:** ผู้เรียนส่วนใหญ่เชื่อคำตอบของ AI แล้วบันทึกลงฐานข้อมูลตรง ๆ ต้องให้เห็นด้วยตาว่าเกิดอะไรขึ้นเมื่อคำตอบไม่ตรงรูปแบบ และเห็นว่าการรับมือเป็นงานปกติ ไม่ใช่ความล้มเหลว

**พูดว่า:** "ทีนี้ผมจะทำลาย prompt ของตัวเองให้ดู ผมจะลบกติกาการตอบออก แล้วเราจะได้เห็นว่าระบบเจออะไร"

**ทำให้พังอย่างไร:**
1. เปิดไฟล์ที่มีข้อความส่งให้ AI → **ลบทั้งบล็อก "กติกาการตอบ" และบล็อก "ตัวอย่าง" ออก** เหลือแต่คำถามลอย ๆ
2. เซฟ → รีเฟรชหน้าเว็บ
3. พิมพ์รายละเอียดเดิม แล้วกดปุ่มอีกครั้ง

**ผู้เรียนจะเห็น:** AI ตอบกลับมาเป็นย่อหน้ายาว เช่น *"จากข้อมูลที่ให้มา ปัญหานี้น่าจะเกี่ยวข้องกับระบบปรับอากาศ ซึ่งควรจัดอยู่ในหมวดหมู่แอร์ครับ เนื่องจาก..."* และช่องหมวดหมู่ **ไม่เปลี่ยน** พร้อมข้อความ "AI ยังจัดหมวดหมู่ให้ไม่ได้ กรุณาเลือกเอง"

**พูดตอนพัง:** "เห็นไหมครับ ผมเองก็เจอ — และสังเกตให้ดีว่าระบบไม่ได้พัง มันปฏิเสธคำตอบที่ไม่เข้าพวกแล้วบอกผู้ใช้ นั่นเพราะตอนแก้แผน เราสั่งเพิ่มไว้ว่าต้องตรวจคำตอบก่อนบันทึก"

**พูดต่อ:** "ทีนี้ลองคิดตามว่า ถ้าผมไม่ได้ใส่การตรวจนั้นไว้ จะเกิดอะไรขึ้นกับฐานข้อมูลของผม" — รอคำตอบจากห้อง 10 วินาที

**วิธีกู้ทีละขั้น:**
1. **ชั้นที่ 1 — ใส่กติกากลับเข้าไป** วางบล็อก "กติกาการตอบ" กลับ → รีเฟรช → ทดสอบ → กลับมาถูกต้อง
2. **ชั้นที่ 2 — ใส่ตัวอย่างกลับเข้าไป** วางบล็อก "ตัวอย่าง" กลับ → พูดว่า "เดือนที่ 1 เราเรียกวิธีนี้ว่า Few-shot"
3. **ชั้นที่ 3 — ชี้ให้ดูว่าการตรวจก่อนบันทึกยังอยู่** เปิดโค้ดบรรทัดที่ตรวจว่าคำตอบอยู่ในรายการหรือไม่ แล้วพูดว่า "ชั้นนี้ห้ามเอาออกเด็ดขาด ต่อให้ prompt ดีเยี่ยมแล้วก็ตาม"

**ชี้ให้ดูตรงนี้:** ย้ำว่า "สามชั้นนี้อยู่ในเกณฑ์ตรวจงานสัปดาห์นี้ ใบงานตอนบ่ายข้อ 12 บังคับให้ทำครบ"

**เชื่อมกับ LeaveEasy:** "ตอนบ่ายคุณจะเจออาการเดียวกัน เพราะเหตุผลการลาที่คนเขียนยาวกว่าอาการเสียเยอะ — ในใบงานมีอยู่ในตาราง 🆘 แล้ว"

### ขั้นที่ 12 — เพิ่มค้นหาและกรอง แล้วชนเรื่อง index ⏱ 10 นาที

**พูดว่า:** "ช่วงสุดท้าย ผมจะทำฟีเจอร์ที่ผู้ใช้ขอเป็นอันดับแรกเสมอ และระหว่างทางเราจะเจอ error หนึ่งตัวที่ผมอยากให้ทุกคนเจอตอนที่ผมยังอยู่ด้วย"

**ทำ:** วาง prompt จังหวะที่ 1 ด้านล่าง

**prompt จังหวะที่ 1 — ขอแผนก่อน:**
> ผมอยากให้หน้ารายการใบแจ้งซ่อมค้นหาและกรองได้
> ช่วยเขียนแผนให้ผมดูก่อน อย่าเพิ่งลงมือ

**ชี้ให้ดูตรงนี้:** อ่านแผนที่ได้มาให้ห้องฟัง แล้วถามว่า "ขาดอะไรครับ" · เฉลยว่ามักขาดสามอย่าง — ไม่ได้บอกลำดับการเรียง ไม่ได้จำกัดจำนวน และไม่ได้บอกว่าถ้าไม่เจอให้ขึ้นข้อความอะไร

**prompt จังหวะที่ 3 — แก้แผน:**
> ขอเรียงตามวันที่แจ้งใหม่ไปเก่า ดึงมาไม่เกิน 50 รายการ
> ไม่เจอให้ขึ้นว่า "ไม่พบใบแจ้งซ่อมที่ตรงกับเงื่อนไข" และถ้าต้องสร้าง index ให้บอกผมด้วย

**prompt จังหวะที่ 4 — ลงมือ:**
> แผนโอเคแล้ว ลงมือทีละข้อ เสร็จข้อไหนบอกผมก่อน

**ทำต่อ:** รีเฟรชหน้ารายการ → เลือกตัวกรองสถานะ **กำลังซ่อม** พร้อมกับเรียงตามวันที่

**ผู้เรียนจะเห็น:** รายการว่างเปล่า และในคอนโซลเบราว์เซอร์ (F12) ขึ้นข้อความ **The query requires an index** พร้อม **ลิงก์สีฟ้ายาว ๆ**

**พูดตอนเจอ error:** "อันนี้ไม่ใช่ความผิดพลาดครับ Firestore กำลังบอกว่า 'ฉันต้องมีสารบัญก่อนถึงจะหาให้ได้' และมันเตรียมลิงก์สร้างมาให้เสร็จแล้ว"

**วิธีจัดการทีละขั้น:**
1. คลิกลิงก์ในข้อความ error → เปิด Firebase Console หน้าสร้าง index ที่กรอกข้อมูลไว้ให้แล้ว
2. กดปุ่ม **Create index**
3. **ผู้เรียนจะเห็น:** สถานะ **Building** — บอกห้องว่า "ตรงนี้ต้องรอ ระหว่างรอ error เดิมยังขึ้นอยู่ ซึ่งเป็นเรื่องปกติ"
4. รอจนขึ้น **Enabled** → กลับไปรีเฟรชหน้าเว็บ → รายการที่กรองแล้วแสดงขึ้นมา

**ชี้ให้ดูตรงนี้:** "จำสองอย่างนี้ไว้คู่กัน — 'ในเครื่องได้ ออนไลน์พัง' ของ Firebase มักเป็น Rules ยังไม่ deploy หรือยังไม่ได้สร้าง index"

**เชื่อมกับ LeaveEasy:** "ตอนบ่ายส่วน C ของคุณคือเรื่องเดียวกัน — ค้นหาใบลา กรองตามสถานะ เรียงใหม่ไปเก่า และคุณจะเจอ error ตัวนี้เหมือนกัน ในใบงานเขียนวิธีแก้ไว้แล้ว"

![screenshot: ข้อความ error เรื่อง index ในคอนโซลเบราว์เซอร์ พร้อมลิงก์สร้าง index](assets/w8-27-index-error.png)

### 🔌 แผนสำรองเมื่อ OpenRouter ล่มกลางคาบ

   - **พูดว่า:** "ผมจะสลับไปใช้คำตอบที่เตรียมไว้ล่วงหน้า เพราะสิ่งที่ผมอยากสอนคือการรับคำตอบมาตรวจแล้วบันทึก ซึ่งสอนได้ครบโดยไม่ต้องพึ่งอินเทอร์เน็ต"
   - สาธิตต่อได้ครบ: การตรวจคำตอบก่อนบันทึก · ป้ายบอกผู้ใช้ · การรับมือเมื่อเรียกไม่สำเร็จ · การบันทึกลง Firestore
3. **ยังไม่ได้อีก → เปลี่ยนลำดับคาบ** — ยกก้อน C (ค้นหา/กรอง) ขึ้นมาทำก่อน แล้ววนกลับมาที่ AI ตอนท้าย

## ❓ คำถามที่ผู้เรียนมักถามตรงนี้

| คำถาม | ตอบสั้น ๆ ว่า |
|---|---|
| "ถ้าซ่อนปุ่มไว้แล้ว ยังต้องเขียน Rules อีกไหม" | ต้อง — การซ่อนปุ่มคือการจัดหน้าจอ ไม่ใช่การกันคน ใครเปิดเครื่องมือนักพัฒนาก็สั่งข้ามปุ่มได้ |
| "Firebase config อยู่ในหน้าเว็บ แบบนี้ไม่อันตรายเหรอ" | ไม่ — มันคือที่อยู่ของโครงการ ไม่ใช่กุญแจ สิ่งที่กันข้อมูลคือ Rules |
| "แล้วทำไม API key ของ OpenRouter ถึงอันตราย" | เพราะไม่มีอะไรยืนกันอยู่หลังมัน ใครถือก็ใช้ในนามเราได้ และบิลมาที่เรา |
| "ผมจะรู้ได้อย่างไรว่า Rules ที่ AI เขียนถูก" | ตรวจ 4 ข้อ: ครบทุกโฟลเดอร์ · มีบล็อกโฟลเดอร์ย่อย · มี `request.auth` ทุกบล็อก · ไม่มีบล็อกที่อนุญาตทุกคนหลงเหลือ แล้วทดสอบด้วยการสวมรอย |
| "ทำไมต้องรอสถานะล็อกอินก่อนอ่านข้อมูล" | เพราะช่วงเสี้ยววินาทีแรกระบบยังไม่รู้ว่าเราเป็นใคร ถ้าอ่านตอนนั้นจะโดนปฏิเสธ ทั้งที่กฎถูกแล้ว |
| "AI ตอบผิดหมวด ต้องแก้ prompt ทุกครั้งไหม" | ไม่ต้องไล่แก้ทีละกรณี — ให้ผู้ใช้แก้เองได้เสมอเป็นทางออกหลัก ส่วน prompt แก้เมื่อผิดซ้ำแบบเดิมหลายครั้ง |
| "ใส่คีย์ในเว็บแบบนี้ ผมเอาไปใช้กับงานจริงได้ไหม" | ไม่ได้ — วันนี้ทำได้เพราะมีวงเงินจำกัดที่ผู้สอนตั้งไว้ ของจริงต้องมีตัวกลางเก็บคีย์ |
| "ทำไมข้อมูลผมยังอ่านได้อยู่ทั้งที่ deploy Rules แล้ว" | ส่วนใหญ่คือกำลังทดสอบในฐานะเจ้าของข้อมูลเอง ให้ทดสอบด้วย uid ของคนอื่นใน Playground |
| "ต้องสร้าง index ทุกครั้งที่เพิ่มตัวกรองใหม่ไหม" | บางครั้งเท่านั้น — Firestore จะบอกเองเมื่อจำเป็น ให้กดลิงก์ที่มันให้มา |
