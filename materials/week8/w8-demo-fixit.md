> **ทำไมต้องมี:** ถ้าไม่เห็นการรั่วกับตา ผู้เรียนจะมองว่า Rules เป็นงานเอกสารน่าเบื่อ ฉากนี้คือฉากจำของทั้งวัน — ระบบที่ "มีล็อกอินแล้ว" ยังเปิดให้คนแปลกหน้าทั้งโลก

**พูดว่า:** "นี่คือ FixIt ที่เราจบกันไว้สัปดาห์ที่แล้ว มีล็อกอิน มีกุญแจประตูหน้าบ้าน อยู่บนอินเทอร์เน็ตจริง ทีนี้ผมจะเลิกเป็นเจ้าของระบบสักครู่ ผมจะเป็นคนแปลกหน้าที่เพิ่งเจอลิงก์นี้"

**ทำต่อ (บีตที่สอง — โฟลเดอร์ย่อย):**
4. กดเข้าใบแจ้งซ่อมของสมชาย 1 ใบ → เลื่อนดูความเห็นการอัปเดตงาน (`comments`) ที่อ่านได้ทั้งหมด

### ขั้นที่ 2 — สั่ง Claude เขียนกฎตามเช็กลิสต์ 5 ข้อ แล้วตรวจด้วยตา ⏱ 5 นาที

**พูดว่า:** "ผมจะไม่สอนไวยากรณ์ของไฟล์กฎเลย ผมจะสั่งให้ Claude เขียนตามเช็กลิสต์ 5 ข้อบนสไลด์ แล้วงานของเราคืออ่านว่าครบไหม — ก้อนนี้เป็นข้อยกเว้นที่ prompt ยาวได้ เพราะเป็นเช็กลิสต์ความปลอดภัย ตกไปข้อเดียวข้อมูลรั่ว งานอื่นเรากลับไปสั่งสั้นเหมือนเดิม"

**ทำ:** ไปที่ Terminal ที่รัน `claude` อยู่ → วาง prompt ด้านล่าง

**prompt ที่ใช้ (กรณียกเว้น — ยาวได้เพราะตกข้อเดียวข้อมูลรั่ว):**
> เขียน Firebase Security Rules ให้ FixIt ลงไฟล์ `firestore.rules` ให้ผ่านเช็กลิสต์ 5 ข้อนี้ครบทุกข้อ
>
> 1. คนที่ไม่ได้ล็อกอิน อ่านหรือเขียนอะไรไม่ได้เลยทุกโฟลเดอร์
> 2. สร้างใบแจ้งซ่อมใหม่ได้เฉพาะเมื่อ `reporterId` ตรงกับ uid ของคนที่ล็อกอินอยู่
> 3. อ่านใบแจ้งซ่อมได้เฉพาะใบที่ตัวเองแจ้ง ยกเว้น `role` เป็น `"technician"` หรือ `"admin"` อ่านได้ทุกใบ
> 4. เปลี่ยน `status` ได้เฉพาะ `"technician"` กับ `"admin"` · มอบหมายช่าง (แก้ `assigneeId`) และแก้โฟลเดอร์ `categories` ได้เฉพาะ `"admin"`
> 5. เขียนกฎให้โฟลเดอร์ย่อย `tickets/{ticketId}/comments` ด้วย ห้ามลืม — กฎของแม่ไม่ครอบลูกอัตโนมัติ ให้อ่านเขียนได้เฉพาะคนที่มีสิทธิ์อ่านใบแม่นั้น
>
> โครงสร้างข้อมูล (ชื่อ field ห้ามสะกดผิด)
> ```
> users/{uid}      { name, email, role }   role: "reporter" | "technician" | "admin"
> categories/{id}  { name }
> tickets/{id}     { title, detail, location, status, categoryId, categoryName,
>                    reporterId, reporterName, assigneeId, assigneeName, createdAt }
>    comments/{id} { authorId, authorName, message, createdAt }
> ```
>
> เขียนเสร็จแล้วอธิบายเป็นภาษาไทยทีละบล็อกว่าบล็อกนั้นตรงกับเช็กลิสต์ข้อไหน

**ผู้เรียนจะเห็น:** ไฟล์ `firestore.rules` ถูกสร้าง ตามด้วยคำอธิบายภาษาไทยทีละบล็อกว่าตรงกับข้อไหน

**ทำต่อ — กวาดตาตรวจ 4 คำถามให้ห้องดู (นี่คือทักษะที่ใบงานวัด):**
1. มีบล็อกครบทุกโฟลเดอร์ไหม (`users` · `categories` · `tickets` · `comments`)
2. มีบล็อกของโฟลเดอร์ย่อย `comments` ไหม — เลื่อนไปชี้ให้เห็นบรรทัดจริง
3. มีคำว่า `request.auth` อยู่ทุกบล็อกไหม
4. มีบล็อกไหนอนุญาตทุกคนหลงเหลืออยู่ไหม — กวาดตาถึงบรรทัดสุดท้ายของไฟล์

**ชี้ให้ดูตรงนี้:** หยุดที่บล็อกของ `comments` แล้วพูดว่า "ข้อ 5 อยู่ตรงนี้ ถ้าไม่สั่ง มันอาจไม่มีบล็อกนี้ และไม่มีใครรู้ตัวเลยว่าขาด"

**เชื่อมกับ LeaveEasy:** "ของ FixIt คือ `tickets` กับ `comments` ของ LeaveEasy คือ `leaveRequests` กับ `approvals` — prompt เต็มอยู่ในใบงานแล้ว คุณเปลี่ยนเป็นชื่อโฟลเดอร์ของโครงงานตัวเอง"

### ขั้นที่ 3 — deploy กฎ แล้วดูของรั่วปิดลงกับตา ⏱ 3 นาที

**พูดว่า:** "เขียนเสร็จในเครื่องยังไม่พอ ยามยังไม่ขึ้นเวร ต้องส่งกฎขึ้นไปด้วย — คำสั่งเดียวกับที่ใช้ส่งกุญแจประตูหน้าบ้านเมื่อสัปดาห์ที่แล้ว"

**ทำ:** ใน Terminal พิมพ์

```
firebase deploy --only firestore:rules
```

**ผู้เรียนจะเห็น:** ข้อความประมาณ 5–8 บรรทัด บรรทัดสุดท้ายเขียนว่า **Deploy complete!**

**ทำต่อ:** กลับไปหน้าต่างไม่ระบุตัวตนของ `somsak@example.com` ที่ยังเปิดค้าง → **กดรีเฟรชหน้ารายการ**

**ผู้เรียนจะเห็น:** รายการใบแจ้งซ่อมของคนอื่นหายไปทั้งหมด — คนแปลกหน้าเห็นเฉพาะส่วนของตัวเอง (ซึ่งว่างเปล่า) หรือขึ้นข้อความที่มีคำว่า **Missing or insufficient permissions**

**ชี้ให้ดูตรงนี้:** 🔴 **หยุด 30 วินาที** ชี้จอเดิมที่เมื่อกี้เต็มไปด้วยข้อมูล แล้วพูดว่า "จอเดียวกัน บัญชีเดียวกัน ต่างกันตรงที่ตอนนี้มียามยืนอยู่ — และถ้าตอนบ่ายคุณเห็น permission denied เต็มจอแล้วตกใจ ให้จำภาพนี้ไว้ นั่นคือยามทำงาน ไม่ใช่ระบบพัง"

**เชื่อมกับ LeaveEasy:** "ตอนบ่าย Checkpoint แรกของคุณคือภาพแบบนี้ — เพื่อนเพื่อนเปิด URL ใช้งานได้ แต่เปิดดูข้อมูลของคุณไม่ได้"

📸 **ภาพที่ควรค้างบนจอตอนนี้:** หน้าจอเดิมของคนแปลกหน้าหลัง deploy กฎ — ข้อมูลคนอื่นหายทั้งหมด

### ขั้นที่ 4 — ทดสอบสวมรอยใน Rules Playground รวมโฟลเดอร์ย่อย ⏱ 4 นาที

**⚠️ หลังคาบ:** เพิกถอนคีย์ใบที่ใช้สาธิตทันที แล้วออกใบใหม่สำหรับคาบถัดไป

## ❓ คำถามที่ผู้เรียนมักถามตรงนี้

| คำถาม | ตอบสั้น ๆ ว่า |
|---|---|

| "Firebase config อยู่ในหน้าเว็บ อันตรายไหม" | ไม่ — มันคือที่อยู่ของโครงการ ไม่ใช่กุญแจ สิ่งที่กันข้อมูลคือ Rules |

| "จะรู้ได้อย่างไรว่ากฎที่ AI เขียนถูก" | ตรวจ 4 คำถาม (ครบทุกโฟลเดอร์ · มีโฟลเดอร์ย่อย · มี `request.auth` · ไม่มีบล็อกอนุญาตทุกคน) แล้วทดสอบด้วยการสวมรอย |
| "ทำไมข้อมูลผมยังอ่านได้ ทั้งที่ deploy กฎแล้ว" | ส่วนใหญ่กำลังทดสอบในฐานะเจ้าของข้อมูลเอง — ใช้ uid คนอื่นใน Playground |
| "AI ตอบผิดหมวด ต้องแก้ข้อความส่งทุกครั้งไหม" | ไม่ — ทางออกหลักคือผู้ใช้แก้เองได้เสมอ ข้อความส่งค่อยแก้เมื่อผิดซ้ำแบบเดิมหลายครั้ง |
| "ระดับ 2 ต่างจากระดับ 1 ตรงไหน" | ระดับ 1 ถามหนึ่งได้หนึ่ง · ระดับ 2 อ่านหลายที่ ตัดสินใจ เขียนกลับ และทิ้งบันทึกว่าทำอะไรไป |
| "ให้ AI กดมอบหมาย/อนุมัติเองเลยได้ไหม" | ไม่ได้ในระบบนี้ — AI เสนอ คนที่มีสิทธิ์ตามกฎเป็นคนกดยืนยัน นี่คือจุดที่ Rules กับผู้ช่วย AI มาบรรจบกัน |
| "ใส่คีย์ในเว็บแบบนี้ เอาไปใช้งานจริงได้ไหม" | ไม่ได้ — วันนี้ทำได้เพราะวงเงินจำกัดที่ผู้สอนตั้งไว้ ระบบจริงต้องมีตัวกลางเก็บคีย์ จดไว้ใน Backlog Sprint 2 แล้ว |
