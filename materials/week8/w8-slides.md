## ช่วงที่ 1 — ล็อกอินและสิทธิ์ผู้ใช้ ⏱ 50 นาที

> note: บอกว่า "ช่วงนี้เราทำเรื่องเดียว คือทำให้ระบบรู้ว่าใครเป็นใคร ยังไม่ปิดข้อมูล การปิดอยู่ช่วงถัดไป" · เหตุผลที่ต้องมีช่วงนี้ตามหลักสูตร: PLO 1.1 ระบุว่าระบบต้องมี Auth

# มองล็อกอินเป็นฟีเจอร์ก่อน
- ผู้ใช้เห็นชื่อตัวเองบนหน้าจอ
- ผู้ใช้เห็นเฉพาะงานของตัวเอง
- หัวหน้าเห็นภาพรวมและกดอนุมัติได้
> note: "ใครเห็นอะไรได้บ้าง — นี่คือฟีเจอร์ที่ผู้ใช้สัมผัสได้ ไม่ใช่เรื่องเทคนิคลอย ๆ ถ้ามองเป็นฟีเจอร์ก่อน เดี๋ยวเรื่องความปลอดภัยจะเข้าใจได้เร็วขึ้นมาก"

# Firebase Authentication คืออะไร
- แปลว่า **ระบบสมัครสมาชิกและล็อกอินสำเร็จรูป**
- Firebase ทำหน้าจอ + เก็บรหัสผ่านให้
- เราเปิดใช้ ไม่ต้องเขียนเอง
> note: ใช้คำเทียบทันที — "Authentication อ่านว่า ออ-เธน-ทิ-เค-ชั่น แปลว่าการยืนยันตัวตน ในหลักสูตรนี้เรียกสั้น ๆ ว่า ระบบล็อกอิน"

# ทำไมห้ามเขียนระบบล็อกอินเอง
- รหัสผ่านต้องเก็บแบบที่แม้เราเองก็อ่านไม่ได้
- ต้องมีรีเซ็ตรหัสผ่าน · ยืนยันอีเมล · กันบอทเดารหัส
- 👉 เรื่องนี้ทำผิดแล้วเสียหายหนัก ให้คนที่ทำมาแล้วทำแทน
> note: "ข้อนี้เป็นข้อสอบชีวิตจริง — ระบบที่เป็นข่าวว่ารหัสผ่านหลุด ส่วนใหญ่คือคนเขียนระบบล็อกอินเอง เราไม่แข่งเรื่องนี้"

# สิ่งที่เราได้กลับมาหลังผู้ใช้ล็อกอิน
```code
uid   = "8fK2pQ..."      ← เลขประจำตัวผู้ใช้ ไม่ซ้ำกับใครในโลก
email = "somchai@example.com"
```
> note: "uid คือบัตรประจำตัวที่ Firebase ออกให้ผู้ใช้แต่ละคน ตั้งแต่วินาทีนี้ไป เวลาระบบถามว่าใครกำลังใช้อยู่ คำตอบคือ uid ตัวนี้"

# uid คือกาวที่เชื่อมคนเข้ากับข้อมูล
```code
📁 users/
   📄 8fK2pQ...  { name: "สมชาย", email, role: "reporter" }
                   ↑ ชื่อไฟล์คือ uid
```
> note: ย้ำจุดนี้ให้ช้า — "เราตั้งชื่อไฟล์ในโฟลเดอร์ users ให้เท่ากับ uid เลย เพราะเวลาระบบรู้ว่า uid นี้ล็อกอินอยู่ มันจะเปิดไฟล์ของคนนั้นได้ทันทีโดยไม่ต้องไปไล่หา"

# บทบาทผู้ใช้ (role) ของ FixIt
| role | ภาษาคน | ทำอะไรได้ |
|---|---|---|
| `reporter` | ผู้แจ้ง | แจ้งซ่อม · ดูใบของตัวเอง |
| `admin` | ผู้ดูแล | ดูทุกใบ · เปลี่ยนสถานะ |
> note: "role อ่านว่า โรล แปลว่าบทบาท เราเก็บเป็นข้อมูลหนึ่งช่องในไฟล์ผู้ใช้" · ถามต่อทันที "โครงงานของกลุ่มคุณมีบทบาทกี่แบบ ใครกดอนุมัติได้" · บอกว่าบทบาทนี้มาจาก Persona ที่ทำไว้ตั้งแต่ Module 1 ไม่ต้องคิดใหม่

# ใครเห็นอะไรได้บ้าง
```flow chain
ไม่ล็อกอิน ไม่เห็นอะไร | พนักงาน เห็นของตัวเอง | *หัวหน้า เห็นของทีม
```
> note: ชี้กล่องซ้ายสุดก่อน แล้วพูดว่า "คนที่ยังไม่ล็อกอิน เห็นศูนย์ ไม่ใช่เห็นน้อย" · เลื่อนนิ้วมากล่องกลาง "ล็อกอินแล้วเห็นของตัวเองอย่างเดียว" · จบที่กล่องเข้มขวาสุด "บทบาทหัวหน้าคือบทบาทเดียวที่เห็นของคนอื่นได้" · ปิดด้วยคำถาม "โครงงานของกลุ่มคุณมีกี่ระดับ"

# ผูกผู้ใช้เข้ากับใบแจ้งซ่อม
```code
📁 tickets/
   📄 t001 { title, detail, status,
             reporterId:   "8fK2pQ...",   ← uid ของผู้แจ้ง
             reporterName: "สมชาย" }      ← จดชื่อซ้ำไว้เหมือนเดิม
```
> note: "สัปดาห์ที่แล้วเราให้ผู้ใช้พิมพ์ชื่อตัวเองลงไป วันนี้ระบบเติมให้เอง และเติมจากคนที่ล็อกอินอยู่จริง — พิมพ์ชื่อคนอื่นแทนไม่ได้แล้ว" · ชี้ไปที่ช่อง reporterId บนจอแล้วพูดว่า "ตัวอักษรยาว ๆ นี้คือ uid ของคนที่ล็อกอินตอนกดส่ง ไม่ใช่ชื่อที่พิมพ์เอง"

## ช่วงที่ 2 — ยามเฝ้าประตูข้อมูล ⏱ 45 นาที

> note: เปิดช่วงด้วยประโยคนี้ — "ช่วงที่แล้วเราทำให้ระบบรู้ว่าใครเป็นใคร ช่วงนี้เราจะทำให้มันปฏิเสธคนที่ไม่ควรเข้า" · บอกล่วงหน้าว่าจะมีการสาธิตข้อมูลรั่วสด

# ใน Firebase หน้าเว็บคุยกับฐานข้อมูลตรง ๆ
```code
[หน้าเว็บของผู้ใช้]  ──────────►  [Firestore]
                      ▲
              ไม่มีเซิร์ฟเวอร์ของเรากั้นอยู่ตรงนี้
```
- สิ่งเดียวที่ยืนกั้นคือ **Security Rules**
> note: "สัปดาห์ที่แล้วผมบอกว่าข้อดีของ Firebase คือไม่ต้องเขียนเซิร์ฟเวอร์เอง วันนี้เรามาจ่ายราคาของข้อดีนั้น — เมื่อไม่มีเซิร์ฟเวอร์ของเรา ก็ไม่มีใครตรวจคนเข้าออกให้ นอกจากกฎที่เราเขียน"

# Firebase config ที่อยู่ในหน้าเว็บ ไม่ใช่ความลับ
- ใครเปิดหน้าเว็บก็เห็นได้ — ปกติ
- มันคือ "ที่อยู่ของโครงการ" ไม่ใช่กุญแจ
- 🛡️ **Rules ต่างหากที่ป้องกัน**
> note: ข้อนี้ผู้เรียนตกใจกันทุกปี — พูดว่า "อย่าเสียเวลาไปซ่อน Firebase config มันไม่ใช่ความลับ เอาแรงไปเขียน Rules ให้ครบดีกว่า"

# Security Rules = ยามเฝ้าประตูโฟลเดอร์
- อยู่ที่ฝั่ง Firebase ผู้ใช้แก้ไม่ได้
- ตรวจทุกครั้งที่มีคนขออ่านหรือขอเขียน
- ปฏิเสธไว้ก่อนเป็นค่าเริ่มต้น
> note: "Security Rules อ่านว่า ซี-คิว-ริ-ตี้ รูลส์ แปลว่ากฎความปลอดภัย ในหลักสูตรนี้เราเรียกว่า ยามเฝ้าประตูโฟลเดอร์ — ยามคนนี้ยืนอยู่ฝั่ง Firebase ไม่ได้อยู่ในหน้าเว็บ ผู้ใช้จึงแก้ไม่ได้"

# มียามกับไม่มียาม ต่างกันตรงนี้
```flow compare
❌ ไม่มี Rules :: ใครก็ได้ | เปิดฐานข้อมูล | เห็นข้อมูลทุกคน
✅ มี Rules :: ผู้ใช้ | *ยามตรวจสิทธิ์ | เห็นเฉพาะของตัวเอง
```
> note: ชี้แถบบนก่อนทั้งแถบ แล้วพูดว่า "นี่คือระบบของทุกกลุ่มตอนนี้ — ไม่มีใครยืนกั้นระหว่างผู้ใช้กับฐานข้อมูล" · แล้วเลื่อนลงแถบล่าง หยุดที่กล่องเข้มตรงกลาง "เช้านี้เราเพิ่มกล่องนี้เข้าไปกล่องเดียว แล้วภาพทั้งเส้นเปลี่ยน" · ปิดด้วย "สังเกตว่าปลายทางของสองแถบไม่เหมือนกัน"

# เราจะไม่เรียนไวยากรณ์ของ Rules
- ให้ Claude เขียนกฎให้
- เรามีหน้าที่ **ตรวจว่าครบ 5 ข้อ**
- แล้ว **ทดสอบว่ากันได้จริง**
> note: พูดให้ชัด — "วันนี้คุณไม่ต้องท่องไวยากรณ์ของไฟล์ Rules เลย สิ่งที่ต้องทำเป็นคือ อ่านออกว่ากฎที่ได้มาครอบอะไรบ้าง และทดสอบว่ามันกันได้จริง" · นี่คือหลักการเดียวกับที่ใช้กับ CLAUDE.md เมื่อสัปดาห์ที่แล้ว

# เช็กลิสต์ความปลอดภัยขั้นต่ำ 5 ข้อ
| # | ข้อ |
|:--:|---|
| 1 | คนไม่ล็อกอิน อ่านอะไรไม่ได้เลย |
| 2 | เขียนข้อมูลใหม่ได้เฉพาะในชื่อตัวเอง |
| 3 | อ่านได้เฉพาะข้อมูลของตัวเอง |
> note: อ่านออกเสียงทีละข้อช้า ๆ · บอกว่า "แผ่นนี้ให้ถ่ายรูปเก็บไว้ ตอนบ่ายจะใช้ทั้งใบ และ Module หน้าก็ยังใช้"

# เช็กลิสต์ 5 ข้อ (ต่อ)
| # | ข้อ |
|:--:|---|
| 4 | การกระทำสำคัญ ทำได้เฉพาะบทบาทที่มีสิทธิ์ |
| 5 | ⚠️ **มีกฎครอบโฟลเดอร์ย่อยด้วย** |
> note: หยุดที่ข้อ 5 ให้นานที่สุด — "ข้อนี้คือข้อที่คนลืมมากที่สุดในโลก และเป็นสาเหตุของข่าวข้อมูลรั่วจริง ๆ"

# ข้อ 5 — กฎของแม่ไม่ครอบลูกอัตโนมัติ
```code
📁 tickets/            ← เขียนกฎแล้ว ✅
   📄 t001
      📁 comments/     ← ยังไม่มีกฎ ❌ เปิดโล่ง
```
> note: "หลายคนเขียนกฎให้ tickets เสร็จแล้วสบายใจ แต่โฟลเดอร์ comments ที่ซ้อนอยู่ข้างในยังเปิดอยู่ ระบบดูปกติทุกอย่าง แต่ข้อมูลรั่วเงียบ ๆ — เดี๋ยวผมจะสาธิตให้ดูสด"

# 💬 prompt เขียน Rules — อันนี้ยาวได้
```prompt กรณียกเว้น — เช็กลิสต์ห้ามตกข้อ
เขียน Firebase Security Rules ให้ FixIt
ต้องผ่านเช็กลิสต์ 5 ข้อนี้ครบทุกข้อ
(วางเช็กลิสต์ 5 ข้อ + โครงสร้างโฟลเดอร์)
แล้วบอกทีละบล็อกว่าตรงกับข้อไหน
```
- ⚠️ ยาวได้เพราะตกไปข้อเดียว = ข้อมูลรั่ว
> note: บอกตรง ๆ ว่า "ปกติเราสั่งสั้นแล้วขอแผนก่อน แต่ตรงนี้เป็นเช็กลิสต์ความปลอดภัย ตกข้อเดียวข้อมูลรั่ว จึงต้องวางให้ครบทั้ง 5 ข้อ งานอื่นให้กลับไปใช้แบบสั้นเหมือนเดิม" · prompt เต็มอยู่ในใบงานตอนบ่าย คัดลอกไปใช้ได้เลย · เน้นบรรทัดสุดท้าย — "การบังคับให้ AI บอกว่าบล็อกไหนตรงข้อไหน คือวิธีตรวจที่เร็วที่สุดสำหรับคนที่อ่านไวยากรณ์ไม่ออก"

# ตรวจกฎที่ได้มาด้วย 4 คำถามนี้
- มีบรรทัดที่พูดถึงโฟลเดอร์ครบทุกโฟลเดอร์ไหม
- มีบล็อกของโฟลเดอร์ย่อยไหม
- มีคำว่า `request.auth` อยู่ทุกบล็อกไหม
- มีบล็อกไหนที่อนุญาตทุกคนหลงเหลืออยู่ไหม
> note: "ข้อสุดท้ายสำคัญ — บางครั้ง AI ทิ้งบล็อกทดสอบที่อนุญาตทุกคนไว้ท้ายไฟล์ กฎท้ายไฟล์ก็ทำงานเหมือนกัน ต้องกวาดตาให้ครบทั้งไฟล์" · ย้ำว่านี่คือการตรวจไฟล์ที่ AI ร่างให้ ซึ่งเป็นทักษะหลักของหลักสูตรนี้

!! ห้ามทดสอบด้วยการดูหน้าจอตัวเอง

> note: ประโยคที่ต้องพูด — "หน้าจอของคุณผ่านเสมอ เพราะคุณคือเจ้าของข้อมูล การทดสอบที่นับได้มีอย่างเดียวคือสวมรอยเป็นคนอื่นแล้วลองเข้า"

# ทดสอบว่ากันได้จริง — 3 วิธี
- 🕵️ เปิดหน้าต่างไม่ระบุตัวตน แล้วเข้าโดยไม่ล็อกอิน
- 👥 สมัครบัญชีที่สอง แล้วลองเปิดใบของบัญชีแรก
- 🧪 ใช้ Rules Playground ใน Firebase Console
> note: "ทั้งสามวิธีใช้เวลารวมกันไม่ถึง 5 นาที และเป็น 5 นาทีที่คุ้มที่สุดของสัปดาห์นี้" · ตอนบ่ายใบงานบังคับทั้งสามวิธี · ชี้คำว่า Denied ในการสาธิตแล้วพูดว่า "คำนี้คือคำที่เราอยากเห็น — แปลว่ายามทำงาน"

# หลังเขียน Rules แล้วต้องส่งกฎขึ้นไปด้วย
```code
firebase deploy --only firestore:rules
```
- เขียนกฎในเครื่อง ≠ กฎขึ้นไปทำงานจริง
> note: "จุดนี้คนติดกันทั้งห้องทุกปี — แก้ Rules ในเครื่องแล้วไม่ส่งขึ้นไป ของจริงบนอินเทอร์เน็ตยังใช้กฎเก่าอยู่" · บอกว่าเดี๋ยวช่วงที่ 3 จะเจอคำสั่งนี้อีกครั้งในบริบทของการ deploy ทั้งเว็บ

## ช่วงที่ 3 — Deploy ขึ้นใช้งานจริง ⏱ 25 นาที

> note: เปิดช่วงด้วยคำถาม — "ตอนนี้ถ้าผมอยากให้แม่ผมลองใช้ระบบนี้ ผมต้องทำยังไงครับ" · รอคำตอบ แล้วบอกว่า "เอาโน้ตบุ๊กไปให้ท่านไม่ใช่คำตอบ ช่วงนี้คือคำตอบ"

# รันในเครื่อง กับ ขึ้นออนไลน์ ต่างกันตรงไหน
| | รันในเครื่อง | ขึ้นออนไลน์ |
|---|---|---|
| ใครเปิดได้ | เราคนเดียว | ใครก็ได้ที่มีลิงก์ |
| ที่อยู่ | `localhost` | URL จริง |
| ปิดเครื่องแล้ว | ดับ | ยังอยู่ |
> note: "สามบรรทัดนี้คือเหตุผลทั้งหมดว่าทำไมต้อง deploy" · ชี้บรรทัดสุดท้ายแล้วพูดว่า "ข้อนี้สำคัญตอนนำเสนอ — ปิดโน้ตบุ๊กแล้วกรรมการยังเปิดดูได้"

# Firebase Hosting คืออะไร
- แปลว่า **ที่ฝากหน้าเว็บให้คนทั้งโลกเปิดได้**
- Firebase ให้ URL มาให้ฟรี 1 อัน
- อยู่ใน Firebase project เดิม ไม่ต้องสมัครใหม่
> note: "Hosting อ่านว่า โฮส-ติ้ง แปลว่าการรับฝากเว็บ คิดเป็นภาพว่าเราเอาไฟล์ไปฝากไว้บนเครื่องของ Google แล้วเขาแจกลิงก์ให้" · ย้ำว่าอยู่ใน project เดิมที่ตั้งไว้ตั้งแต่ Module 1 ไม่ต้องสมัครอะไรใหม่

# เส้นทางของการนำขึ้นออนไลน์
```flow chain
โค้ดในเครื่อง | สั่ง deploy | *Firebase Hosting | URL ที่คนอื่นเปิดได้
```
> note: ไล่นิ้วจากซ้ายไปขวาทีละกล่องขณะพูด "โค้ด · สั่ง · ฝาก · ลิงก์" · หยุดค้างที่กล่องเข้ม แล้วพูดว่า "กล่องนี้คือของ Google ไม่ใช่เครื่องเรา ดังนั้นปิดโน้ตบุ๊กแล้วเว็บยังอยู่" · ปิดด้วย "กล่องขวาสุดคือของส่งมอบของสัปดาห์นี้ครับ"

# 💬 สั่งเตรียม deploy — จังหวะที่ 1
```prompt จังหวะที่ 1 — ขอแผนก่อน
ผมอยากนำโปรเจกต์นี้ขึ้น Firebase Hosting
ช่วยเขียนแผนให้ผมดูก่อน อย่าเพิ่งลงมือ
```
> note: "สองบรรทัดเหมือนเดิมครับ ไม่มีอะไรพิเศษ" · บอกว่าแผนที่ได้กลับมามักมี 3 ข้อ — ตั้งค่าโครงการ · เลือกโฟลเดอร์ที่จะส่งขึ้น · สั่ง deploy · ให้ห้องดูว่าข้อที่สองคือข้อที่คนตอบผิดบ่อยที่สุด

# คำสั่งที่จะได้ใช้จริง
```code
firebase login                    ← ครั้งแรกครั้งเดียว
firebase init hosting             ← ตอบคำถามไม่กี่ข้อ
firebase deploy                   ← ส่งขึ้นจริง
```
- จบแล้วจะเห็นบรรทัด **Hosting URL:** พร้อมลิงก์
> note: อ่านทีละบรรทัดแล้วบอกว่า "สองบรรทัดแรกทำครั้งเดียวตลอดโครงงาน บรรทัดที่สามทำทุกครั้งที่อยากอัปเดตเว็บ" · ⚠️ เตือนตอน init hosting ว่าถ้าถามว่าให้เขียนทับ index.html ไหม **ต้องตอบว่าไม่** ไม่งั้นหน้าแรกที่ทำมาจะหายไป

# deploy เว็บ กับ deploy กฎ เป็นคนละคำสั่ง

```flow compare
🛡️ ส่งกฎขึ้นไป :: *deploy --only firestore:rules | ยามเริ่มทำงาน
```

> note: บอกก่อนว่า "แถบบนกับแถบล่างไม่ได้แปลว่าถูกหรือผิด มันคืองานคนละงานที่ต้องทำทั้งคู่" · ชี้แถบบน "อันนี้ส่งหน้าเว็บ" · หยุดค้างที่กล่องเข้มแถบล่าง "อันนี้ส่งกฎ ถ้าทำแค่แถบบน เว็บใหม่จะไปเจอกฎเก่า" · ปิดด้วย "จำไว้ว่าสองคำสั่งนี้ไม่แทนกัน"

## ช่วงที่ 4 — Sub-Agent: ให้ AI อีกตัวมาตรวจงาน ⏱ 30 นาที

> note: เริ่มด้วยคำถามให้ห้องคิด — "สามสัปดาห์ที่ผ่านมา ใครเป็นคนตรวจงานที่ AI เขียนให้เราครับ" · รอคำตอบ แล้วสรุปว่า "เราเองครับ และเราตรวจได้เท่าที่เรารู้ ช่วงนี้เราจะให้ AI อีกตัวมาช่วยตรวจ ตัวที่ไม่ได้เป็นคนเขียนโค้ดนั้น"

# ปัญหาที่พาเรามาถึงตรงนี้
- AI ตัวที่เขียนโค้ด มองไม่เห็นข้อผิดพลาดของตัวเอง
- เหมือนคนตรวจงานเขียนที่ตัวเองเพิ่งเขียนเสร็จ
- ตาเราไปอ่านสิ่งที่**ตั้งใจจะเขียน** ไม่ใช่สิ่งที่เขียนจริง
> note: ถามห้องว่า "ใครเคยอ่านงานตัวเองสามรอบแล้วยังมีคนอื่นเจอคำผิด" · รอให้คนพิมพ์ในแชท แล้วพูดว่า "AI เป็นแบบเดียวกันเป๊ะ"

# ทำไมคนเขียนตรวจงานตัวเองไม่ออก
```flow compare
❌ คนเดียวเขียนแล้วตรวจเอง :: Claude เขียนโค้ด | *Claude ตรวจเอง | มองข้ามที่ผิด
✅ คนละตัว ความจำแยกกัน :: Claude เขียนโค้ด | Reviewer ความจำเปล่า | เจอที่ผิด
```
> note: ชี้กล่องเข้มในแถบ ❌ ก่อน แล้วพูดว่า "ตัวเดียวกันนี้ยังจำได้ว่าตั้งใจจะเขียนอะไร มันจึงอ่านเจอสิ่งที่ตั้งใจ ไม่ใช่สิ่งที่เขียนลงไปจริง" · แล้วเลื่อนลงชี้กล่องกลางของแถบ ✅ "ตัวนี้ไม่เคยเห็นบทสนทนาเมื่อกี้เลย มันเห็นแต่โค้ดที่มีอยู่จริง" · ปิดด้วย "ความต่างอยู่ที่ความจำ ไม่ได้อยู่ที่ความเก่ง"

!! คนเขียน กับ คนตรวจ ควรเป็นคนละคน

> note: หยุด 2 วินาทีแล้วพูดว่า "นี่คือทั้งหมดของช่วงนี้ ที่เหลือคือวิธีทำให้มันเกิดขึ้นจริง" · โยงกลับสไลด์แกนของวันตอนต้นคาบ — "จำได้ไหมครับที่ผมบอกตอนเก้าโมงว่าเช้านี้มีสองประโยค นี่คือประโยคที่สอง"

# Sub-Agent แปลว่าอะไร
- แปลว่า **ผู้ช่วย AI อีกตัวที่มีหน้าที่เฉพาะ**
- เราตั้งชื่อ ตั้งหน้าที่ และตั้งขอบเขตให้มัน
- มันทำงานของมัน แล้วส่งผลกลับมาให้เรา
- วันนี้เราตั้ง 1 ตัว: 🔍 คนตรวจ (Reviewer)
> note: พูดว่า "ไม่ใช่ AI ตัวใหม่ที่ต้องไปสมัคร มันคือ Claude Code ตัวเดิม ที่เราสั่งให้สวมหมวกคนละใบ" · บอกล่วงหน้าว่าสัปดาห์หน้าจะมีตัวที่สอง คือคนทดสอบ

# ทำไมความจำแยกกันถึงได้ผล
- **Context** = ความจำของ AI ในหนึ่งบทสนทนา *(เรียนไว้สัปดาห์ที่ 6)*
- ตัวที่เขียนโค้ด มีเหตุผลของตัวเองค้างอยู่ในความจำ
- sub-agent เริ่มด้วย**ความจำเปล่า** เห็นแต่โค้ดที่มีจริง
- จึงเจอสิ่งที่ตัวเขียนมองข้าม
> note: พูดว่า "นี่คือเหตุผลที่มันได้ผลจริง ไม่ใช่การตั้งชื่อใหม่ให้ดูดี" · เชื่อมกลับสัปดาห์ที่ 6 เรื่อง context บวมและคำสั่ง `/clear`

# 🔍 Reviewer เจออะไรได้บ้าง
- กฎเฝ้าข้อมูลที่หลวมเกินไป *(เรื่องของเช้านี้)*
- จุดที่รับข้อมูลจากผู้ใช้โดยไม่ตรวจก่อน
- จุดที่ไม่ได้จัดการกรณี "หาข้อมูลไม่เจอ"
- ค่าที่ไม่ควรอยู่ในโค้ด เช่น รหัสผ่าน
> note: อ่านทีละข้อ แล้วชี้ข้อแรกพูดว่า "ข้อนี้คือจุดที่สองเรื่องของเช้านี้มาบรรจบกัน — เราจะให้ Reviewer ตรวจไฟล์ Rules ที่เราเพิ่งเขียนกันไปด้วย" · ไม่ต้องอธิบายลึก เดี๋ยวเห็นของจริงตอนสาธิต

# 🔍 Reviewer มีข้อจำกัดอะไร
- **ตรวจแล้วไม่ได้แปลว่าไม่มีบั๊ก**
- Reviewer เดาผิดได้เหมือน AI ตัวอื่น
- มันเห็นโค้ด แต่ไม่เห็นว่าผู้ใช้จริงกดอะไร
- 👉 จึงยังต้องทดสอบด้วยมือเหมือนเดิม
> note: พูดว่า "รายงานที่บอกว่าผ่านหมด ไม่ใช่ใบรับประกัน" · อ้างกลับ Module 1 เรื่องข้อจำกัดของ AI · บอกว่าสัปดาห์หน้าจะมีคนทดสอบมาเสริมอีกชั้น

# ตั้งค่า Reviewer อย่างไร
- ตั้งค่าด้วย**ไฟล์**ที่วางไว้ในโฟลเดอร์โครงงาน
- ในไฟล์เขียน 3 อย่าง: **ชื่อ · หน้าที่ · ขอบเขต**
- ขอบเขตต้องแคบและชัด ไม่ใช่ "ตรวจให้หมด"
- **เราไม่พิมพ์ไฟล์นี้เอง — สั่ง Claude สร้างให้**
> note: พูดว่า "ขอบเขตกว้างเกินไป จะได้รายงานยาวเป็นร้อยข้อจนเราท้อ แล้วสุดท้ายไม่ได้แก้อะไรเลย" · ย้ำข้อสุดท้ายให้ชัด — "เราไม่ต้องไปหาเมนูหรือหน้าจอตั้งค่าที่ไหนเลยครับ เราพิมพ์สั่งเป็นภาษาไทยให้ Claude สร้างไฟล์นี้ให้ วิธีนี้ได้ผลเหมือนกันทุกเวอร์ชันของ Claude Code" · ไฟล์นี้อยู่ใน repo จึงติดไปกับโครงงานตลอด

# ตั้ง sub-agent — 3 จังหวะ

# 💬 prompt ตั้งค่า Reviewer — อันนี้ยาวได้

# ⭐ จังหวะที่ 2 — เปิดไฟล์ที่ Claude สร้างมาอ่าน
- Claude สร้างไฟล์ตั้งค่าแล้ววางไว้ในโฟลเดอร์โครงงาน
- **เปิดไฟล์นั้นอ่านก่อน** อย่าเพิ่งสั่งให้เริ่มตรวจ
- ดูว่ามีบรรทัด **"ห้ามแก้ไขโค้ดเอง"** ไหม
- ดูว่ารายการที่ให้ตรวจอยู่ครบ **5 ข้อ** ไหม
- ขาดข้อไหน พิมพ์บอกให้เพิ่มเข้าไป
> note: พูดว่า "ขั้นนี้ห้ามข้ามครับ — ถ้าเราไม่เปิดอ่าน เราจะไม่รู้เลยว่า Reviewer ของเราตรวจอะไรอยู่ และตอบไม่ได้ตอนนำเสนอว่าใครเป็นคนตรวจงานเรา" · เปิดไฟล์ให้ห้องดูจริงบนจอ แล้วชี้ทีละบรรทัดว่าตรงไหนคือชื่อ ตรงไหนคือหน้าที่ ตรงไหนคือขอบเขต · บอกว่าถ้าขาดข้อไหน ให้พิมพ์กลับไปว่า "ในไฟล์ตั้งค่ายังไม่มี … ช่วยเพิ่มให้ด้วย"

# อ่านผล review โดยไม่ตื่นตระหนก — จัด 3 กอง

# แก้กองแดงอย่างไรให้ไม่พัง
- แก้**ทีละข้อ** ห้ามสั่งรวดเดียว
- แก้เสร็จ 1 ข้อ → **เปิดเว็บกดใช้จริง** → commit
- ข้อไหนอ่านแล้วไม่เข้าใจ ให้**ถามก่อนแก้**
> note: พูดว่า "แก้ทีละข้อแล้ว commit ทีละข้อ พอพังเราจะรู้ทันทีว่าพังเพราะข้อไหน" · นี่คือวินัยเดียวกับสัปดาห์ที่ 6 · เพิ่มกติกากลุ่ม — "ให้คนละคนรับกองแดงคนละข้อ แล้ว commit ในชื่อตัวเอง"

# 💬 prompt แก้กองแดงทีละข้อ
```prompt จังหวะที่ 1 — ขอแผนก่อน
เอาข้อที่ 1 ในไฟล์ review-notes.md ข้อเดียว
บอกผมก่อนว่าจะแก้ไฟล์ไหน เพราะอะไร อย่าเพิ่งแก้
```
```prompt จังหวะที่ 4 — ลงมือ
เข้าใจแล้ว แก้ได้เลย แก้เฉพาะข้อนี้ ห้ามแตะข้ออื่น
```
> note: ชี้กล่องบนบรรทัดท้ายแล้วพูดว่า "คำว่า อย่าเพิ่งแก้ ทำให้เราได้อ่านก่อนที่โค้ดจะเปลี่ยน — เราคือคนตัดสินใจ ไม่ใช่ AI" · ชี้กล่องล่าง "ห้ามแตะข้ออื่น คือสิ่งที่กันไม่ให้รายงานสามสิบข้อกลายเป็นการรื้อทั้งระบบ"
