# ปัญหาของ prototype ที่คุณถืออยู่

- 🖼️ **prototype** (หน้าเว็บตัวอย่างที่กดดูได้) จาก Module 1 เป็น *ภาพนิ่ง*
- กรอกอะไรลงไป รีเฟรชแล้วหายหมด
- เพราะยังไม่มี **ฐานข้อมูล** (คลังเก็บข้อมูลที่อยู่ต่อแม้ปิดเบราว์เซอร์)
- 🎯 วันนี้เราต่อคลังเก็บข้อมูลให้ระบบของคุณ

> note: ถามห้องก่อนว่า "ใครเคยกรอกฟอร์มใน prototype ของตัวเองแล้วรีเฟรช ข้อมูลหายไหมครับ" รอคำตอบในแชท แล้วพูดว่า "หายทุกคนครับ เพราะมันยังไม่มีที่เก็บ วันนี้เราจะแก้เรื่องนี้"

!! ระบบเริ่มมีความจำ

> note: หยุด 3 วินาทีให้อ่าน แล้วพูดว่า "ประโยคนี้คือความคิดเดียวของวันนี้ครับ เย็นนี้ระบบของคุณจะจำข้อมูลได้ ปิดเบราว์เซอร์แล้วเปิดใหม่ ข้อมูลยังอยู่"

# วันนี้คุณจะได้ 4 อย่างกลับไป

- 📁 **Repo** (โฟลเดอร์โครงงานที่มีปุ่มเซฟย้อนได้) ที่รันเว็บของคุณได้
- 📝 แบบโครงสร้างข้อมูลบนกระดาษ 1 แผ่น
- 🗄️ **Firestore** (คลังเก็บข้อมูลบนคลาวด์) ที่มีข้อมูลจริงอยู่ข้างใน
- 🖥️ หน้ารายการที่อ่านข้อมูลจากคลังจริง ไม่ใช่ของปลอมในโค้ด

> note: พูดว่า "สี่ข้อนี้คือของจับต้องได้ ไม่ใช่ความรู้สึกว่าเข้าใจ ตอนบ่ายคุณจะทำครบทั้งสี่ข้อกับ LeaveEasy แล้วการบ้านทำซ้ำกับหัวข้อของตัวเอง" ย้ำว่าข้อสุดท้ายคือครั้งแรกที่หน้าจอกับฐานข้อมูลได้เจอกัน

!! สิ่งที่คุณไม่ต้องรู้

> note: หยุด 2 วินาทีก่อนพูด แล้วพูดว่า "ก่อนเริ่ม ผมอยากเคลียร์เรื่องนี้ก่อน เพราะความกลัวว่าต้องรู้ทุกอย่างทำให้คนหยุดตัวเองก่อนได้เริ่ม" ค้างสไลด์ 5 วินาทีให้อ่านทัน

# 5 อย่างที่คุณไม่ต้องรู้ใน Module นี้

- ❌ ไม่ต้องเขียนโค้ดเองจากศูนย์
- ❌ ไม่ต้องท่องคำสั่ง เปิดใบงานดูได้ตลอด · ลืมเมื่อไรพิมพ์ `/help`
- ❌ ไม่ต้องรู้ว่าทุกไฟล์ทำอะไร
- ❌ ไม่ต้องเข้าใจเบื้องหลังของ Firebase
- ❌ ไม่ต้องจำศัพท์อังกฤษ มีแผ่นคำแปลให้

> note: พูดทีละข้อ ช้า ๆ แล้วปิดท้ายว่า "สิ่งที่คุณต้องทำได้มีอย่างเดียว คืออ่านสิ่งที่ AI เขียนมาแล้วบอกได้ว่าใช่หรือไม่ใช่ นั่นคือทักษะของ Module นี้" · เตือนว่า "คำสั่งของ Claude Code เปลี่ยนได้ตามเวอร์ชัน ถ้าพิมพ์แล้วไม่ได้ผล พิมพ์ /help ดูรายการที่ใช้ได้จริงในเครื่องคุณ"

# LLM สร้างมาอย่างไร แล้วเราใช้ตอนไหน

```flow compare
🏭 ตอนสร้าง · ทำครั้งเดียว :: อ่านข้อความมหาศาล | จำรูปแบบที่เจอบ่อย | *ได้โมเดล 1 ก้อน
💬 ตอนใช้ · ทุกครั้งที่พิมพ์ :: ส่งข้อความไปให้ | โมเดลเดาคำตอบ | ส่งกลับมาหาเรา
```

> note: **สไลด์ภาพรวมก่อนลงรายละเอียด ใช้ 2 นาทีพอ** · ชี้แถบบนจากซ้ายไปขวา "บริษัทที่สร้าง AI เอาข้อความจากทั้งอินเทอร์เน็ตมาให้มันอ่าน แล้วให้มันจำว่าคำไหนมักตามหลังคำไหน · ใช้เวลาเป็นเดือนและใช้เงินมหาศาล แต่**ทำครั้งเดียวจบ**" · หยุดที่กล่องเข้ม "ผลลัพธ์คือไฟล์ก้อนหนึ่งที่เรียกว่าโมเดล — LLM ย่อมาจาก Large Language Model แปลตรงตัวว่าโมเดลภาษาขนาดใหญ่" · ชี้แถบล่าง "ส่วนตอนที่พวกคุณใช้ คือส่งข้อความไปให้ก้อนนั้น มันเดาคำตอบ แล้วส่งกลับมา จบในไม่กี่วินาที" · **ประโยคที่สำคัญที่สุดของสไลด์นี้** "สังเกตนะครับว่าตอนคุยกับเรา มันไม่ได้เรียนรู้อะไรเพิ่มเลย — ก้อนเดิมทั้งวัน · เพราะฉะนั้นสิ่งที่คุณสอนมันวันนี้ พรุ่งนี้มันจำไม่ได้ · เดี๋ยวสัปดาห์ที่ 7 เราจะแก้ข้อนี้ด้วยไฟล์ CLAUDE.md"

!! 🙋 "วันนี้อากาศ ______" · คำถัดไปคืออะไร

> note: **จังหวะแรกที่ให้ห้องลงมือ ห้ามข้าม** · อ่านออกเสียงแล้วพูดว่า "พิมพ์คำเดียวในแชทเลยครับ ไม่ต้องคิดนาน" · **รอจนมีคำตอบอย่างน้อย 10 คน** แล้วอ่านออกเสียง 4–5 อัน · เกือบทั้งห้องจะตอบว่า "ดี" · พูดว่า "เห็นไหมครับ พวกคุณเพิ่งทำสิ่งเดียวกับที่ AI ทำ" แล้วค่อยกดสไลด์ถัดไป

# AI ไม่ได้ "รู้" — มันเดาคำถัดไป

- พิมพ์ว่า "วันนี้อากาศ" → AI เดาว่าคำถัดไปคือ "ดี"
- มันไม่ได้เข้าใจอากาศ — มันเคยอ่านประโยคแบบนี้มาเป็นล้านครั้ง
- เดาทีละคำต่อกันไปเรื่อย ๆ จนได้คำตอบทั้งย่อหน้า
- 📌 **โค้ดก็คือข้อความแบบหนึ่ง** — มันจึงเขียนโค้ดด้วยวิธีเดียวกันนี้

> note: เฉลยต่อจากที่ห้องเพิ่งตอบ — "ที่พวกคุณตอบว่าดีกันเกือบหมด ไม่ใช่เพราะรู้จักอากาศวันนี้นะครับ แต่เพราะเคยได้ยินประโยคแบบนี้มาเยอะ · AI ทำแบบเดียวกันเป๊ะ" · ชี้บรรทัดสุดท้าย "และโค้ดก็คือข้อความแบบหนึ่ง มันจึงเขียนโค้ดด้วยวิธีเดียวกันนี้" · ปิดด้วย "ส่วนคณิตศาสตร์ข้างในโมเดล ไม่ต้องรู้เลยครับ ไม่มีผลกับงานของคุณ"

# เดาเก่ง ไม่เท่ากับ รู้จริง

- 🙋 **ใครเคยเจอ AI ตอบมั่วแบบมั่นใจบ้าง — พิมพ์ ✋ ในแชท**

# โทเคน — AI หั่นข้อความเป็นชิ้นก่อนอ่าน

- AI ไม่ได้อ่านเป็นคำแบบเรา — หั่นเป็นชิ้นเล็ก ๆ เรียกว่า **โทเคน (token)**
- นับเป็นโทเคนหมด: ที่คุณพิมพ์ · ไฟล์ที่มันเปิด · คำตอบที่มันเขียน
- ภาษาไทยถูกหั่นละเอียดกว่าอังกฤษ ประโยคเท่ากันเรากินโทเคนมากกว่า
- 💰 **โทเคนคือหน่วยคิดเงิน** เหมือนค่าน้ำค่าไฟ ใช้เท่าไรจ่ายเท่านั้น
- 🙋 **ทายก่อน: ประโยคยาวเท่ากัน ไทยหรืออังกฤษกินโทเคนมากกว่า**

> note: **ถามบรรทัด 🙋 ก่อนเฉลยบรรทัดสาม** ให้พิมพ์ ไทย หรือ อังกฤษ ในแชท · ส่วนใหญ่จะตอบผิดว่าอังกฤษ · เฉลยว่า "ภาษาไทยครับ ถูกหั่นละเอียดกว่า ประโยคเท่ากันเรากินโทเคนมากกว่า" แล้วรีบบอกว่า "ข้อนี้ไม่ต้องทำอะไรนะครับ ขอให้รู้ไว้เฉย ๆ" · พูดว่า "ทีนี้มาดูว่ามันอ่านข้อความของเรายังไง" · ชี้บรรทัดสาม "ข้อนี้ไม่ต้องทำอะไรนะครับ ขอให้รู้ไว้เฉย ๆ" · ปิดด้วย "การพิมพ์สั้นแต่ชัด จึงไม่ได้ประหยัดเวลาอย่างเดียว ประหยัดเงินด้วย"

# จากแชทตอบคำถาม สู่ **coding agent**

```flow compare
💬 แชทธรรมดา :: เราถาม | มันตอบเป็นข้อความ | *เราคัดลอกไปวางเอง
🤖 coding agent :: เราบอกเป้าหมาย | *มันลงมือในเครื่องเรา | เราตรวจ
```

> note: **สไลด์ที่อธิบายว่าทำไมคอร์สนี้ไม่ใช้หน้าเว็บแชท** · ชี้แถบบนทีละกล่อง "แบบที่ทุกคนคุ้น คือเราถาม มันตอบเป็นข้อความ แล้วเราต้องคัดลอกไปวางเองทีละไฟล์ ผิดไฟล์เมื่อไรก็พัง" · ชี้แถบล่าง "ส่วน coding agent เราบอกแค่เป้าหมาย มันเปิดไฟล์ในเครื่องเราเอง แก้เอง รันเอง อ่าน error เอง แล้วแก้ต่อ" · ย้ำกล่องเข้มขวาสุดของแถบล่าง "หน้าที่ที่เหลือของเราคือตรวจ ซึ่งเป็นงานที่คุณทำได้แม้ไม่เคยเขียนโปรแกรม"

# coding agent ทำอะไรได้บ้าง

- 📂 **เปิดอ่านไฟล์ในโปรเจกต์เราเองทั้งโฟลเดอร์** ไม่ต้องคัดลอกไปวาง

- ▶️ **รันคำสั่งแล้วอ่านผลเอง** — เจอ error ก็แก้ต่อโดยไม่ต้องถามเรา
- 🌐 **ทำงานกับบริการภายนอกได้** เช่น สร้างฐานข้อมูล นำเว็บขึ้นออนไลน์
- 🔍 **สั่งให้ตรวจงานตัวเองได้** — สัปดาห์ที่ 8 กับ 9 เราจะใช้ข้อนี้
- 🙋 **ข้อไหนที่หน้าเว็บแชทธรรมดาทำไม่ได้เลย — พิมพ์เลขข้อในแชท**

> note: **ถามบรรทัด 🙋 ก่อนอธิบาย** · คำตอบคือ **ทำไม่ได้เลยทั้ง 5 ข้อ** ถ้าไม่ให้มันเข้าถึงเครื่องเรา — เฉลยแล้วห้องจะเข้าใจทันทีว่าทำไมคอร์สนี้ไม่ใช้หน้าเว็บแชท · จากนั้นอ่านไล่ทีละข้อ แล้วผูกกับสิ่งที่ผู้เรียนจะเห็นวันนี้ — "ข้อหนึ่งกับข้อสองคุณจะเห็นตอนสาธิตอีกสิบนาที ข้อสามคือตอนที่เดโมพังแล้วผมไม่ต้องแก้เอง ข้อสี่คือตอนสร้าง Firestore ช่วงเกือบเที่ยง ส่วนข้อห้าเก็บไว้สัปดาห์ที่ 8" · **ย้ำข้อสำคัญ** "มันทำได้เยอะแบบนี้ แปลว่าเวลามันทำผิด มันก็ผิดได้เยอะเหมือนกัน — นี่คือเหตุผลที่เราจะไม่ปล่อยให้มันลงมือก่อนเราตรวจแผน"

# commit — ปุ่มเซฟที่ย้อนกลับได้

- **commit** = กดเซฟหนึ่งครั้ง พร้อมเขียนกำกับว่าทำอะไรไป
- ทุก commit คือหมุดที่ย้อนกลับมายืนได้
- AI แก้เร็วและบางครั้งแก้พัง — มีหมุดจึงกล้าปล่อยให้แก้
- 🎯 กติกาทั้งเดือน: ทำอะไรสำเร็จ → commit ทันที

> note: พูดว่า "commit คือเหตุผลที่เรากล้าให้ AI แตะโปรเจกต์จริง พังเมื่อไรย้อนกลับได้ใน 5 วินาที" · เตือนว่าข้อความ commit ต้องอ่านรู้เรื่อง เช่น "เพิ่มหน้ารายการใบแจ้งซ่อม" ไม่ใช่ "update" เพราะตอนต้องย้อน คุณต้องหาหมุดเจอ · บ่ายนี้ Checkpoint 3 ตรวจข้อนี้

# แบบ Firestore — ของเดียวกัน คนละคำเรียก

```flow chain
โฟลเดอร์ | ไฟล์ | *ข้อมูลในไฟล์
```

> note: ชี้กล่องซ้ายสุด "โฟลเดอร์คือของที่สไลด์ที่แล้วเรียกว่าตาราง" · ไล่เทียบเป็นคู่ "แถวคือไฟล์ คอลัมน์คือข้อมูลในไฟล์" · จบที่กล่องเข้ม "ไม่มีของใหม่ที่ต้องเรียนเลยครับ มีแต่ชื่อเรียกใหม่"

# แปลศัพท์ชุดที่ 1

| สิ่งที่คุณคุ้นอยู่แล้ว | เรียกว่า | ตัวอย่างใน FixIt |
|---|---|---|
| 📁 โฟลเดอร์ | Collection | `tickets` |
| 📄 ไฟล์ในโฟลเดอร์ | Document | ใบแจ้งซ่อม 1 ใบ |
| ✏️ ข้อมูลข้างในไฟล์ | Field | หัวข้อ สถานะ วันที่ |

> note: อ่านออกเสียงทีละแถวจากซ้ายไปขวา "โฟลเดอร์ เรียกว่า collection ตัวอย่างคือโฟลเดอร์ tickets" · ย้ำว่าจำสามคำนี้ได้ ที่เหลือของวันนี้จะตามได้ลื่น

# แปลศัพท์ชุดที่ 2

| สิ่งที่คุณคุ้นอยู่แล้ว | เรียกว่า | ตัวอย่างใน FixIt |
|---|---|---|
| 🏷️ ชื่อไฟล์ | Document ID | `t001` |
| 📁 โฟลเดอร์ย่อยข้างใน | Subcollection | `comments` |
| 🗺️ ที่อยู่เต็มของไฟล์ | Document Path | `tickets/t001/comments/c001` |

> note: ชี้ path เต็มแล้วพูดว่า "อ่านจากซ้ายไปขวาเหมือนที่อยู่บ้าน โฟลเดอร์ tickets ไฟล์ t001 ข้างในมีโฟลเดอร์ comments ไฟล์ c001" · ให้ห้องอ่านตามพร้อมกัน 1 รอบ

# หน้าตาจริงของ FixIt บน Firestore

```code
📁 users/       📄 u001 { name: "สมชาย", role: "employee" }
📁 categories/  📄 c001 { name: "ไฟฟ้า" }
📁 tickets/
   📄 t001 { title, status: "แจ้งใหม่",
             reporterId: "u001",  reporterName: "สมชาย",
             categoryId: "c001",  categoryName: "ไฟฟ้า" }
      📁 comments/
         📄 cm001 { authorName, message }
```

> note: พูดว่า "ค่อย ๆ กวาดตาดูนะครับ นี่คือทั้งฐานข้อมูลของ FixIt อยู่ในภาพเดียว" หยุด 10 วินาที · อย่าเพิ่งอธิบายบรรทัดที่จดชื่อซ้ำ ปล่อยค้างไว้ก่อน เดี๋ยวกลับมาที่มัน · ถามห้อง "โฟลเดอร์ใหญ่มีกี่โฟลเดอร์ · โฟลเดอร์ย่อยซ้อนอยู่ตรงไหน" ให้ตอบในแชท คำตอบคือ 3 กับ ซ้อนในไฟล์ t001

!! `status` กับ `Status` ไม่ใช่ตัวเดียวกัน

> note: พูดว่า "ถ้าไฟล์หนึ่งสะกดตัวเล็ก อีกไฟล์สะกดตัวใหญ่ ระบบจะพังแบบเงียบ ๆ ไม่มี error ให้เห็น หน้าจอจะว่างเฉย ๆ" · บอกว่า "นี่คือเหตุผลที่ตอนบ่ายคุณต้องเขียนชื่อช่องข้อมูลทุกตัวลงกระดาษก่อน แล้วใช้ชุดเดียวกันทั้งระบบ และเป็นเหตุผลเดียวที่วันนี้จะมี prompt ยาวอยู่หนึ่งอัน"

# ข้อที่ต่างจากตารางมากที่สุด — ไม่มี JOIN

- ในไฟล์ใบแจ้งซ่อม เก็บไว้เท่านี้ `reporterId: "u001"`
- อยากรู้ชื่อผู้แจ้ง ต้องเปิดโฟลเดอร์ `users` หาไฟล์ `u001` อีกที
- ทำทุกครั้งที่แสดงรายการ = ช้าและยุ่ง
- 20 ใบแจ้งซ่อม = เปิดหาอีก 20 รอบ

> note: **สไลด์ที่ห้ามรีบที่สุดของช่วงนี้** · เล่าเป็นภาพ "เหมือนเปิดใบเสร็จแล้วเห็นแต่รหัสลูกค้า ต้องวิ่งไปเปิดแฟ้มทะเบียนลูกค้าอีกตู้ทุกครั้งที่อยากรู้ว่าใคร" · แปลศัพท์ JOIN = การเชื่อมสองตารางเข้าหากันในฐานข้อมูลแบบเดิม ซึ่ง Firestore ไม่มี

# ไม่มี JOIN จึงต้องจดชื่อซ้ำ

```flow compare
❌ เก็บไว้เฉพาะรหัส :: เปิดใบแจ้งซ่อม | *เห็นรหัส u001 | วิ่งไปเปิด users
✅ จดชื่อซ้ำไว้ในไฟล์ :: เปิดใบแจ้งซ่อม | เห็นชื่อสมชาย | จบในไฟล์เดียว
```

> note: ชี้แถบบนไล่จากซ้าย หยุดที่กล่องเข้ม "ถึงตรงนี้หน้าจอขึ้นแต่ u001 อ่านแล้วไม่รู้ว่าใคร" · กล่องขวาสุดแถบบน "ใบแจ้งซ่อม 20 ใบ ก็วิ่ง 20 รอบ" · ไล่แถบล่างทีละกล่อง ปิดที่ "จบในไฟล์เดียว" · **แล้วให้ศัพท์ตรงนี้** "วิธีนี้มีชื่อทางการว่า Denormalize แปลว่าจดข้อมูลที่ใช้บ่อยซ้ำไว้ในไฟล์เลย จะได้ไม่ต้องไปเปิดหาที่อื่น เก็บทั้ง reporterId และ reporterName คู่กันไว้" · เตือนล่วงหน้า "ถ้าตอนบ่ายหน้าจอขึ้นแต่รหัสประหลาด ไม่ขึ้นชื่อคน เก้าในสิบคือเก็บแต่ ID ไว้ ให้กลับมาที่สไลด์นี้"

# ราคาของการจดชื่อซ้ำ — ต้องรู้ก่อนเลือก

- สมชายเปลี่ยนชื่อเป็น "สมชาย ใจดี"
- ไฟล์ใน `users` แก้จุดเดียวจบ
- แต่ใบแจ้งซ่อม 20 ใบยังขึ้นชื่อเก่า
- **ต้องไล่แก้ทุกใบที่จดชื่อเขาไว้**

> note: พูดว่า "นี่คือการแลกที่ NoSQL บังคับให้เลือก ไม่มีทางเลือกที่ได้ทุกอย่าง" · เกณฑ์ตัดสิน: จดซ้ำสิ่งที่ต้องโชว์บนหน้ารายการและเปลี่ยนไม่บ่อย เช่นชื่อคน ชื่อประเภท · ตอบไม่ได้ว่าเปลี่ยนบ่อยไหม ให้จดซ้ำไว้ก่อน

# แปลง DB Schema เป็นโฟลเดอร์ — กติกา 4 ข้อ

- ตาราง → 📁 โฟลเดอร์
- แถว → 📄 ไฟล์ · คอลัมน์ → ✏️ ข้อมูลในไฟล์
- ช่องที่ชี้ไปตารางอื่น → เก็บ ID **+ จดชื่อซ้ำ**
- ตารางลูกที่ห้อยกับแม่ → 📁 โฟลเดอร์ย่อย

> note: บอกว่า "สี่บรรทัดนี้คือทั้งหมดของการแปลง ถ่ายรูปสไลด์นี้เก็บไว้ ตอนบ่ายคุณใช้มันวาดแบบของโครงงานตัวเองบนกระดาษ" · อธิบายข้อสาม "ช่องที่ชี้ไปตารางอื่น ศัพท์ทางการคือ Foreign Key เช่นช่องผู้แจ้งที่ชี้ไปตาราง users"

# Firestore — คลังเก็บข้อมูลบนคลาวด์

- เก็บเป็น 📁 โฟลเดอร์ 📄 ไฟล์ แบบที่เพิ่งเรียนเป๊ะ ๆ
- อยู่บนคลาวด์ — ปิดเบราว์เซอร์ ข้อมูลไม่หาย
- หน้าเว็บคุยกับมันตรง ๆ เราไม่ต้องเขียนเซิร์ฟเวอร์เอง
- ใช้ **Firebase project** ที่สมัครไว้แล้วจาก Module 1

> note: พูดว่า "ข้อสามคือของขวัญของ Firebase ครับ หลักสูตรทั่วไปต้องเขียนตัวกลางเองอีกชั้น เราข้ามไปได้ทั้งชั้น" · ถามว่า "ใครเข้า Firebase console ไม่ได้ หรือลืมรหัส พิมพ์ 1 ในแชท" ให้ TA ตามช่วยก่อนบ่าย

# เส้นทางข้อมูลของวันนี้ — อ่านอย่างเดียว

```flow chain
เปิดหน้ารายการ | หน้าเว็บถามคลัง | *Firestore ตอบกลับ | แสดงบนจอ
```

| ตัว | แปลว่า | ทำเมื่อไร |
