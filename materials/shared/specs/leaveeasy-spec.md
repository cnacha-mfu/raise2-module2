# ข้อกำหนดระบบ (Spec) — 🔧 LeaveEasy ระบบขอลาออนไลน์

> **เอกสารนี้คือใบสั่งงานของระบบ LeaveEasy** — บอกว่าระบบต้องทำอะไรได้บ้าง หน้าตาเป็นอย่างไร และเก็บข้อมูลไว้ที่ไหน
> ใช้ในคาบ Lab ของ ADT-RAISE Batch 2 · Module 2 (สัปดาห์ที่ 6–9) โดย **คุณเป็นคนลงมือทำเองตามใบงาน**
> เอกสารคู่ขนานของเอกสารนี้คือ `fixit-spec.md` (ระบบแจ้งซ่อมออนไลน์) ที่ผู้สอนใช้สาธิตในคาบบรรยาย — โครงสร้างเทียบกันได้ทุกข้อ แต่ไม่ได้เหมือนกันทุกอย่าง (ดูตารางเทียบในหัวข้อ 10)

## 0. วิธีใช้เอกสารนี้ และข้อกำหนดทางเทคนิค

### 0.1 เอกสารนี้ใช้อย่างไร

1. วางไฟล์ `leaveeasy-spec.md` ไว้ใน **โฟลเดอร์โปรเจกต์** (โฟลเดอร์เดียวกับที่จะสร้างระบบ)
2. เปิด **Claude Code** (โปรแกรมผู้ช่วย AI ที่อ่านและแก้ไฟล์จริงในเครื่องเรา) ในโฟลเดอร์นั้น
3. สั่งให้อ่านไฟล์นี้ก่อนลงมือทำอะไร เช่น

   > อ่านไฟล์ leaveeasy-spec.md ในโฟลเดอร์นี้ แล้วสรุปกลับมาเป็นข้อ ๆ ว่า
   > 1. ระบบนี้ใช้ทำอะไร 2. มีหน้าจอกี่หน้า อะไรบ้าง 3. ผู้ใช้มีกี่บทบาท
   > ยังไม่ต้องเขียนโค้ด

4. **ถ้าสรุปกลับมาไม่ตรงกับเอกสารนี้ ให้แก้เอกสารก่อน อย่าเพิ่งสร้างหน้าจอ**

> ⚠️ **กติกาสำคัญสำหรับ AI ที่อ่านเอกสารนี้:** ทำเฉพาะสิ่งที่เขียนไว้ในเอกสารนี้ **ห้ามเพิ่มฟีเจอร์ที่ไม่ได้ระบุ** และ **ห้ามทำงานของสัปดาห์ถัดไปล่วงหน้า** (ดูหัวข้อ 8 และ 9)

## 1. ระบบนี้แก้ปัญหาอะไร ให้ใคร

LeaveEasy คือ **ระบบขอลาออนไลน์ของที่ทำงาน**

- ทุกวันนี้พนักงานขอลาด้วยการเขียนใบกระดาษ ส่งแชท หรือบอกปากเปล่า ทำให้ใบลาหายและไม่มีใครยืนยันได้ว่าอนุมัติแล้วหรือยัง
- หัวหน้าไม่มีที่รวมใบลาไว้ที่เดียว จึงตอบไม่ได้ว่าสัปดาห์หน้าใครลาบ้าง และมีใบไหนรออนุมัติค้างอยู่
- ฝ่ายบุคคลต้องตามเก็บใบลาจากหลายทางเมื่อถึงเวลาสรุปวันลาประจำเดือน
- **LeaveEasy รวมทุกใบลาไว้ที่เดียว** — พนักงานยื่นใบลาผ่านหน้าเว็บ หัวหน้าพิจารณา อนุมัติหรือไม่อนุมัติ แล้วผลถูกบันทึกไว้ให้ทุกฝ่ายเปิดดูย้อนหลังได้
- ผู้ใช้กลุ่มเป้าหมายคือ **ที่ทำงานขนาด 20–100 คน** ที่มีหัวหน้าผู้อนุมัติ 1–3 คน

**เส้นทางหลักของระบบ:** พนักงานยื่นใบลา → หัวหน้าพิจารณา → อนุมัติหรือไม่อนุมัติ → บันทึกผล

## 2. ผู้ใช้ 3 บทบาท

| บทบาท | ค่าที่เก็บในช่อง `role` | ทำอะไรได้ | ทำอะไรไม่ได้ |
|---|---|---|---|
| 🙋 **ผู้ขอลา** | `employee` | ยื่นใบขอลาใหม่ · ดูใบลาของตัวเอง · เขียนความเห็นเพิ่มในใบของตัวเอง · ลบใบของตัวเองที่สถานะยังเป็น `รอพิจารณา` | เปลี่ยนสถานะใบลา · ดูใบลาของคนอื่น · แก้ประเภทการลา |
| ✅ **ผู้อนุมัติ** | `manager` | ดูใบลาทุกใบ · **เปลี่ยนสถานะใบลา (อนุมัติ / ไม่อนุมัติ)** · เขียนความเห็นในทุกใบ | ลบใบลาของคนอื่น · แก้ประเภทการลา |
| 🧾 **ฝ่ายบุคคล** | `hr` | ทำได้ทุกอย่างที่ผู้อนุมัติทำได้ · **กำหนดผู้อนุมัติให้แต่ละใบ** · **เพิ่ม แก้ ลบ ประเภทการลา** · เห็นแดชบอร์ดสรุปทั้งระบบ *(หน้าโครงจาก prototype · ต่อข้อมูลจริงใน Module 3)* | — |

> 📌 **ค่าที่เก็บในช่อง `role` ให้ใช้รหัสภาษาอังกฤษตามตารางนี้เสมอ** (`employee` / `manager` / `hr`) เพราะสัปดาห์ที่ 8 จะเอาไปใช้เขียนกฎเฝ้าข้อมูล ส่วนคำไทยใช้แสดงบนหน้าจอ

> 🔓 **สัปดาห์ที่ 6 ยังไม่มีล็อกอิน** — ทุกหน้าจอเปิดใช้ได้หมด · **สัปดาห์ที่ 7 มีล็อกอิน + กฎขั้นต่ำ "ต้องล็อกอินก่อน"** แต่ยังไม่แยกสิทธิ์ตามคน · ข้อจำกัดรายบทบาทในตารางนี้เริ่มมีผลจริงในสัปดาห์ที่ 8

## 3. User Story และเกณฑ์การยอมรับ

> 📖 **User Story** = ประโยคที่บอกว่า *ใคร* อยากทำ *อะไร* เพื่อ *อะไร*
> 📖 **เกณฑ์การยอมรับ (Acceptance Criteria)** = รายการที่ต้องเห็นบนหน้าจอจริง ถึงจะนับว่าฟีเจอร์นั้นเสร็จ

### US-01 — ดูรายการใบลาทั้งหมด · สัปดาห์ที่ 6 (หน้าจอ + อ่านข้อมูลจริงจาก Firestore)
**ในฐานะ** ผู้ขอลา **ฉันต้องการ** เห็นรายการใบลาเป็นตาราง **เพื่อ** รู้ว่าใบที่ยื่นไปถึงขั้นไหนแล้ว

- [ ] หน้ารายการแสดงตารางที่มีคอลัมน์: หัวข้อ · ประเภทการลา · สถานะ · ผู้ขอลา · วันที่ลา
- [ ] แสดง **ชื่อคนเป็นภาษาไทย** ไม่ใช่รหัสอย่าง `u001`
- [ ] สถานะแสดงเป็นป้ายสี (รอพิจารณา = เหลือง · อนุมัติ = เขียว · ไม่อนุมัติ = แดง)
- [ ] กดที่แถวใดแถวหนึ่ง แล้วไปหน้ารายละเอียดของใบนั้น
- [ ] ถ้ายังไม่มีใบลาเลย ให้ขึ้นข้อความว่า "ยังไม่มีใบขอลาในระบบ" ไม่ใช่ตารางว่างเปล่า

### US-02 — ยื่นใบขอลาใหม่ · สัปดาห์ที่ 6 (ฟอร์ม) → 7 (บันทึกจริง)
**ในฐานะ** ผู้ขอลา **ฉันต้องการ** กรอกฟอร์มขอลา **เพื่อ** ให้ใบลาเข้าระบบโดยไม่ต้องเดินไปยื่นกระดาษ

- [ ] ฟอร์มมีช่อง: หัวข้อ · เหตุผลการลา (กล่องหลายบรรทัด) · ประเภทการลา (รายการเลื่อนลง) · วันที่เริ่มลา · วันที่สิ้นสุด
- [ ] ประเภทการลาในรายการเลื่อนลงอ่านมาจากโฟลเดอร์ `leaveTypes` (สัปดาห์ที่ 7 เป็นต้นไป)
- [ ] กดปุ่ม **บันทึก** แล้วมีใบลาใหม่เกิดขึ้นจริง และหน้าจอพากลับไปหน้ารายการ
- [ ] ใบที่เกิดใหม่มีสถานะเริ่มต้นเป็น `รอพิจารณา` และมีวันเวลาที่ยื่นติดมาด้วยอัตโนมัติ
- [ ] มีปุ่ม **ยกเลิก** ที่พากลับหน้ารายการโดยไม่บันทึก

### US-03 — เปิดดูรายละเอียดใบลา · สัปดาห์ที่ 6 → 7
**ในฐานะ** ผู้ขอลา **ฉันต้องการ** เปิดดูใบลาหนึ่งใบแบบเต็ม **เพื่อ** ดูว่าใครเป็นผู้พิจารณาและผลเป็นอย่างไร

- [ ] แสดงครบทุกช่อง: หัวข้อ · เหตุผล · ประเภทการลา · วันที่เริ่มลาและวันที่สิ้นสุด · ผู้ขอลา · ผู้อนุมัติ · สถานะ · วันที่ยื่น
- [ ] ด้านล่างแสดง **รายการความเห็นการอนุมัติ** เรียงตามเวลาจากเก่าไปใหม่
- [ ] ถ้ายังไม่มีผู้อนุมัติ ให้ขึ้นว่า "ยังไม่ได้กำหนดผู้อนุมัติ"
- [ ] มีปุ่มกลับไปหน้ารายการ

### US-04 — เปลี่ยนสถานะใบลา · สัปดาห์ที่ 7
**ในฐานะ** ผู้อนุมัติ **ฉันต้องการ** กดอนุมัติหรือไม่อนุมัติใบลา **เพื่อ** ให้พนักงานรู้ผลโดยไม่ต้องเดินมาถาม

- [ ] ในหน้ารายละเอียดมีปุ่ม **อนุมัติ** และปุ่ม **ไม่อนุมัติ** สำหรับใบที่สถานะเป็น `รอพิจารณา` ตามหัวข้อ 6
- [ ] กดแล้วสถานะบนหน้าจอเปลี่ยนทันที และค่าในฐานข้อมูลเปลี่ยนตาม
- [ ] **แก้เฉพาะช่อง `status` เท่านั้น ห้ามเขียนทับช่องอื่นในไฟล์เดิม**
- [ ] ใบที่สถานะเป็น `อนุมัติ` หรือ `ไม่อนุมัติ` แล้ว จะเปลี่ยนสถานะต่อไม่ได้

### US-05 — เขียนความเห็นการอนุมัติ · สัปดาห์ที่ 7
**ในฐานะ** ผู้อนุมัติ **ฉันต้องการ** เขียนความเห็นไว้ในใบลา **เพื่อ** ให้ทุกคนที่เกี่ยวข้องเห็นเหตุผลเดียวกัน

- [ ] ในหน้ารายละเอียดมีกล่องพิมพ์ข้อความและปุ่มส่ง
- [ ] ความเห็นที่ส่งแล้วเก็บอยู่ใน **โฟลเดอร์ย่อย `approvals` ของใบนั้น** ไม่ใช่โฟลเดอร์กลาง
- [ ] แต่ละรายการแสดง ชื่อผู้เขียน · ข้อความ · วันเวลา
- [ ] ส่งข้อความว่างเปล่าไม่ได้ ต้องขึ้นข้อความเตือน

### US-06 — จัดการประเภทการลา · สัปดาห์ที่ 7
**ในฐานะ** ฝ่ายบุคคล **ฉันต้องการ** เพิ่ม แก้ และลบประเภทการลา **เพื่อ** ให้รายการตรงกับระเบียบการลาที่บริษัทใช้จริง

- [ ] หน้าจัดการประเภทการลาแสดงรายการประเภททั้งหมดเป็นตาราง
- [ ] มีช่องกรอกชื่อประเภทใหม่และปุ่มเพิ่ม
- [ ] แต่ละแถวมีปุ่มแก้ไขและปุ่มลบ
- [ ] ประเภทที่เพิ่มใหม่ไปโผล่ในรายการเลื่อนลงของหน้ายื่นใบลาใหม่ทันที

### US-07 — ลบใบลาของตัวเอง · สัปดาห์ที่ 7
**ในฐานะ** ผู้ขอลา **ฉันต้องการ** ลบใบที่ยื่นผิด **เพื่อ** ไม่ให้หัวหน้าเสียเวลาพิจารณาใบที่ไม่ต้องการแล้ว

- [ ] ในหน้ารายละเอียดมีปุ่มลบ
- [ ] กดลบแล้วต้องมีหน้าต่างถามยืนยันก่อนเสมอ
- [ ] ยืนยันแล้วไฟล์ในฐานข้อมูลหายไปจริง และหน้าจอพากลับไปหน้ารายการ
- [ ] ใบที่มีสถานะอื่นนอกจาก `รอพิจารณา` ปุ่มลบต้องกดไม่ได้

### US-08 — ล็อกอินและเห็นเฉพาะใบลาของตัวเอง · สัปดาห์ที่ 7 (ล็อกอิน + กฎขั้นต่ำ) → 8 (เห็นเฉพาะของตัวเอง)
**ในฐานะ** ผู้ใช้ทุกคน **ฉันต้องการ** ล็อกอินก่อนใช้ระบบ **เพื่อ** ให้เหตุผลการลาของฉันไม่ถูกเพื่อนร่วมงานเปิดอ่าน

- [ ] มีหน้าสมัครสมาชิกและหน้าล็อกอิน
- [ ] สมัครสำเร็จแล้วมีไฟล์ใหม่ในโฟลเดอร์ `users` พร้อมช่อง `role` ค่าเริ่มต้นเป็น `employee`
- [ ] ใบลาที่สร้างใหม่บันทึก `requesterId` เป็นรหัสของคนที่ล็อกอินอยู่จริง
- [ ] **คนที่ไม่ได้ล็อกอิน อ่านข้อมูลไม่ได้เลย**
- [ ] **ผู้ขอลาคนหนึ่ง เปิดใบลาของผู้ขอลาอีกคนไม่ได้** ส่วนผู้อนุมัติและฝ่ายบุคคลเปิดได้ทุกใบ
- [ ] มีกฎเฝ้าข้อมูลครอบ **โฟลเดอร์ย่อย `approvals`** ด้วย

## 5. โครงสร้างข้อมูล — เขียนไว้ 2 แบบคู่กัน

> 🗂️ **ทำไมต้องมี 2 แบบ:** แบบแรกคือสิ่งที่ออกแบบไว้ตั้งแต่ Module 1 ในรูปตาราง · แบบที่สองคือหน้าตาจริงบน Firestore ที่ใช้ตั้งแต่สัปดาห์ที่ 6
> **เนื้อหาเป็นเรื่องเดียวกัน เปลี่ยนวิธีจัดวางเท่านั้น** — วางคู่กันไว้เพื่อให้เห็นว่าอันไหนกลายเป็นอันไหน

### 5.1 แบบตาราง (ERD ที่ออกแบบไว้ Module 1)

```
users (ผู้ใช้)         ── 1:N ──►  leave_requests (ใบขอลา)  ◄── N:1 ──  leave_types (ประเภทการลา)
  id, ชื่อ, อีเมล,                   id, หัวข้อ, เหตุผล,                    id, ชื่อประเภท
  บทบาท                             วันที่เริ่มลา, วันที่สิ้นสุด,
                                    สถานะ, ผู้ขอลา(FK),
                                    ผู้อนุมัติ(FK),
                                    ประเภท(FK), วันที่ยื่น
                                          │
                                        1:N
                                          ▼
                                  approvals (ความเห็นการอนุมัติ)
                                    id, ใบลา(FK), ผู้เขียน(FK), ข้อความ, วันที่
```

> 📖 **FK (Foreign Key)** = ช่องที่เก็บรหัสของแถวในตารางอื่น เอาไว้ชี้ว่า "แถวนี้เกี่ยวกับแถวไหนของอีกตาราง"
> 📖 **1:N** = หนึ่งแถวของตารางซ้าย ผูกกับหลายแถวของตารางขวา

| ตาราง | คอลัมน์ |
|---|---|
| `users` | `id` · `name` · `email` · `role` |
| `leave_types` | `id` · `name` |
| `leave_requests` | `id` · `title` · `reason` · `startDate` · `endDate` · `status` · `requesterId`(FK) · `approverId`(FK) · `leaveTypeId`(FK) · `createdAt` |
| `approvals` | `id` · `leaveRequestId`(FK) · `authorId`(FK) · `message` · `createdAt` |

### 5.2 แบบโฟลเดอร์/ไฟล์บน Firestore (ใช้จริงตั้งแต่สัปดาห์ที่ 6)

> 📖 **คำเทียบภาษาคน:** 📁 **Collection** = โฟลเดอร์ · 📄 **Document** = ไฟล์หนึ่งไฟล์ · ✏️ **Field** = หัวข้อข้อมูลข้างในไฟล์ · 📁 **Subcollection** = โฟลเดอร์ย่อยที่ซ้อนอยู่ในไฟล์

```
📁 users/
   📄 u001  { name, email, role }

📁 leaveTypes/
   📄 lt001 { name }

📁 leaveRequests/
   📄 lr001 { title, reason, status,
              requesterId,  requesterName,   ← จดชื่อซ้ำไว้เลย
              approverId,   approverName,    ← จดชื่อซ้ำไว้เลย
              leaveTypeId,  leaveTypeName,   ← จดชื่อซ้ำไว้เลย
              startDate, endDate, createdAt }
      📁 approvals/                          ← โฟลเดอร์ย่อยที่ซ้อนอยู่ในไฟล์ lr001
         📄 ap001 { authorId, authorName, message, createdAt }
```

> ⚠️ **ชื่อโฟลเดอร์บน Firestore เขียนติดกันแบบไม่มีขีดล่าง** — ตาราง `leave_requests` กลายเป็นโฟลเดอร์ `leaveRequests` และ `leave_types` กลายเป็น `leaveTypes`

**ตารางกลายเป็นโฟลเดอร์อย่างไร**

| แบบตาราง | แบบ Firestore |
|---|---|
| ตาราง `leave_requests` | 📁 โฟลเดอร์ `leaveRequests` |
| แถวหนึ่งแถว | 📄 ไฟล์หนึ่งไฟล์ เช่น `lr001` |
| คอลัมน์ | ✏️ หัวข้อข้อมูลในไฟล์ |

| FK ชี้ไปตารางอื่น | เก็บรหัสของไฟล์ปลายทาง **และจดชื่อซ้ำไว้ด้วย** |
| ตารางลูก `approvals` (1:N) | 📁 โฟลเดอร์ย่อย `approvals` ที่ซ้อนอยู่ในไฟล์ใบลานั้น |

### 5.3 ข้อมูลที่จดซ้ำไว้ (denormalize) และเหตุผล

> 📖 **Denormalize (จดซ้ำ)** = จดข้อมูลที่ต้องใช้บ่อยซ้ำไว้ในไฟล์เลย จะได้ไม่ต้องไปเปิดหาที่อื่น

**เหตุผลรวม:** Firestore **ไม่มี JOIN** (คำสั่งดึงข้อมูลจากหลายตารางมาต่อกันในครั้งเดียวแบบฐานข้อมูลตาราง) ถ้าเก็บแต่รหัส หน้าจอจะขึ้นว่า `u001` แทนชื่อคน และต้องไปเปิดโฟลเดอร์ `users` เพิ่มอีกครั้งต่อหนึ่งแถว ซึ่งช้าและเปลืองการเรียกข้อมูล

| ช่องที่จดซ้ำ | จดซ้ำมาจาก | ทำไมต้องจดซ้ำ |
|---|---|---|
| `leaveRequests.requesterName` | `users.name` | หน้ารายการต้องแสดงชื่อผู้ขอลาทุกแถว |
| `leaveRequests.approverName` | `users.name` | หน้ารายการและหน้ารายละเอียดต้องแสดงชื่อผู้อนุมัติโดยไม่เปิดโฟลเดอร์ `users` |
| `leaveRequests.leaveTypeName` | `leaveTypes.name` | ใช้แสดงและใช้กรองในหน้ารายการ |
| `approvals.authorName` | `users.name` | รายการความเห็นต้องขึ้นชื่อคนเขียนทุกบรรทัด |

**ราคาที่ต้องจ่าย ต้องรู้ไว้:** ถ้ามีคนเปลี่ยนชื่อในโฟลเดอร์ `users` ใบลาเก่าจะยังขึ้นชื่อเดิม เพราะชื่อถูกจดไว้ในไฟล์ใบลาแล้ว การแก้ต้องไล่อัปเดตทุกใบที่จดชื่อคนนั้นไว้ — **เดือนนี้ยอมรับข้อจำกัดนี้ ไม่ต้องเขียนระบบไล่อัปเดต**

> ⚠️ **ตัวพิมพ์เล็ก-ใหญ่ของชื่อช่องข้อมูลต้องตรงกันทั้งระบบ** — `status` กับ `Status` ถือเป็นคนละช่องใน Firestore และจะทำให้ระบบพังแบบเงียบ ๆ

## 6. สถานะและการเปลี่ยนสถานะ

**ช่อง `status` ของใบลา ใช้ได้ 3 ค่านี้เท่านั้น**

```
รอพิจารณา  →  อนุมัติ
           └→  ไม่อนุมัติ
```

| สถานะ | หมายความว่า | ใครเปลี่ยนเป็นค่านี้ได้ | เปลี่ยนต่อไปเป็นอะไรได้ |
|---|---|---|---|
| `รอพิจารณา` | ยื่นเข้าระบบแล้ว รอผู้อนุมัติพิจารณา | ระบบตั้งให้อัตโนมัติตอนสร้างใบใหม่ | `อนุมัติ` หรือ `ไม่อนุมัติ` |
| `อนุมัติ` | อนุมัติให้ลาได้ | ผู้อนุมัติ · ฝ่ายบุคคล | **เปลี่ยนต่อไม่ได้ (ปลายทาง)** |
| `ไม่อนุมัติ` | ไม่อนุมัติให้ลา | ผู้อนุมัติ · ฝ่ายบุคคล | **เปลี่ยนต่อไม่ได้ (ปลายทาง)** |

**กฎการเปลี่ยนสถานะ**

- ใบลาที่สร้างใหม่ทุกใบเริ่มต้นที่ `รอพิจารณา` เสมอ ตั้งค่าให้อัตโนมัติ ไม่ให้ผู้ใช้เลือกเอง
- เปลี่ยนได้ตามลูกศรเท่านั้น จาก `รอพิจารณา` ไปเป็น `อนุมัติ` หรือ `ไม่อนุมัติ` · ห้ามย้อนกลับ
- **ผู้ขอลาเปลี่ยนสถานะไม่ได้** เปลี่ยนได้เฉพาะผู้อนุมัติและฝ่ายบุคคล (บังคับจริงในสัปดาห์ที่ 8)
- ทุกครั้งที่เปลี่ยนสถานะ ให้แก้เฉพาะช่อง `status` ห้ามเขียนทับช่องอื่นในไฟล์เดิม
- การเปลี่ยนเป็น `ไม่อนุมัติ` ต้องเขียนความเห็นในโฟลเดอร์ย่อย `approvals` อย่างน้อย 1 รายการก่อน
- ลบใบลาได้เฉพาะใบที่สถานะยังเป็น `รอพิจารณา`

## 7. ข้อมูลตัวอย่าง (seed)

> 📖 **Seed (ข้อมูลตัวอย่าง)** = ข้อมูลชุดเริ่มต้นที่ใส่ไว้ก่อน เพื่อให้แยกออกว่า "อ่านข้อมูลไม่ได้" หรือ "ไม่มีข้อมูลให้อ่าน"

## 9. สิ่งที่ยังไม่ทำใน Module นี้

> 🛑 **ข้อความนี้เขียนไว้สำหรับ AI โดยเฉพาะ:** ทุกข้อด้านล่างอยู่นอกขอบเขต **ห้ามสร้างขึ้นมาเอง แม้จะเห็นว่าระบบควรมี** ถ้าคิดว่าจำเป็น ให้เขียนบอกไว้เป็นรายการข้อเสนอ แล้วรอคำสั่งก่อน

**เรื่องเทคนิค**
- ❌ ไม่ใช้ framework ใด ๆ (React · Vue · Angular · Next.js · Tailwind หรืออื่น ๆ)
- ❌ ไม่เขียนเซิร์ฟเวอร์ของตัวเอง (Express · Node server · Cloud Functions)
- ❌ ไม่ใช้ฐานข้อมูลแบบตาราง (SQL · PostgreSQL · MySQL) และไม่มีการย้ายโครงสร้างข้อมูล (migration)
- ❌ ไม่มีการทดสอบอัตโนมัติจนกว่าจะถึงสัปดาห์ที่ 9
- ❌ ไม่แบ่งหน้ารายการ (pagination) — ให้จำกัดจำนวนที่ดึงมาแสดงแทน เก็บเรื่องนี้ไว้ Module 3

**เรื่องฟีเจอร์**
- ❌ ไม่มีการแจ้งเตือนทางอีเมล LINE หรือ SMS
- ❌ ไม่มีการส่งออกรายงานเป็น Excel หรือ PDF
- ❌ ไม่มีการอนุมัติหลายขั้นหรือสายบังคับบัญชาหลายชั้น
- ❌ **ไม่มีการคำนวณวันลาคงเหลือหรือโควตาวันลาประจำปี** — เดือนนี้บันทึกใบลาอย่างเดียว
- ❌ ไม่มีปฏิทินการลาของทีมหรือการตรวจวันลาชนกัน
- ❌ ไม่มีการเก็บประวัติการแก้ไข (ใครแก้อะไรเมื่อไร)
- ❌ ไม่มีบทบาทที่ 4 ขึ้นไป — มี 3 บทบาทตามหัวข้อ 2 เท่านั้น
- ❌ ไม่มีระบบหลายภาษา ไม่มีโหมดกลางคืน ไม่มีการชำระเงิน
- ❌ ไม่มีแอปบนมือถือ — ทำเป็นหน้าเว็บที่เปิดบนมือถือได้ก็พอ

**เรื่องข้อมูล**
- ❌ **ห้ามใส่ข้อมูลจริงของบุคคลใด ๆ** ใช้ชื่อสมมติและอีเมลตัวอย่างตามหัวข้อ 7 เท่านั้น
- ❌ ไม่เก็บเบอร์โทร เลขบัตรประชาชน หรือข้อมูลอ่อนไหวอื่น
- ❌ **ห้ามส่งเหตุผลการลาที่มีข้อมูลส่วนบุคคลจริงไปให้ AI ภายนอก** (สัปดาห์ที่ 8)

## 10. ตารางเทียบกับ FixIt

> 🔗 ระบบคู่ขนานของ LeaveEasy คือ **FixIt — ระบบแจ้งซ่อมออนไลน์** ที่ผู้สอนสาธิตในคาบบรรยาย · ทั้งสองมีโครงสร้างตรงกันช่องต่อช่อง แต่ **ไม่ได้เหมือนกันทุกอย่าง** ดูหมายเหตุใต้ตาราง

| | 🎬 **FixIt** (บรรยาย) | 🔧 **LeaveEasy** (Lab) |
|---|---|---|
| 📁 โฟลเดอร์หลัก | `tickets` ใบแจ้งซ่อม | `leaveRequests` ใบขอลา |
| ผู้เริ่มเรื่อง | `reporterId` / `reporterName` (ผู้แจ้ง) | `requesterId` / `requesterName` (ผู้ขอลา) |
| ผู้รับผิดชอบ | `assigneeId` / `assigneeName` (ช่างซ่อม) | `approverId` / `approverName` (ผู้อนุมัติ) |
| 📁 โฟลเดอร์ประเภท | `categories` หมวดหมู่ปัญหา | `leaveTypes` ประเภทการลา |
| ช่องประเภทในไฟล์หลัก | `categoryId` / `categoryName` | `leaveTypeId` / `leaveTypeName` |
| 📁 โฟลเดอร์ย่อย | `comments` ความคืบหน้างาน | `approvals` ความเห็นการอนุมัติ |
| ช่องในโฟลเดอร์ย่อย | `authorId` / `authorName` / `message` / `createdAt` | `authorId` / `authorName` / `message` / `createdAt` |
| ช่องเนื้อหาหลัก | `title` / `detail` | `title` / `reason` |
| ช่องเฉพาะของระบบ | `location` สถานที่ | `startDate` / `endDate` วันที่ลา |
| สถานะ | **4 ค่า** — แจ้งใหม่ → รับเรื่องแล้ว → กำลังซ่อม → เสร็จสิ้น | **3 ค่า** — รอพิจารณา → อนุมัติ / ไม่อนุมัติ |
| บทบาท 3 แบบ | `reporter` · `technician` · `admin` | `employee` · `manager` · `hr` |
| ฟีเจอร์ AI (สัปดาห์ที่ 8) | จัดหมวดหมู่ใบแจ้งซ่อมอัตโนมัติ | จัดประเภทการลาอัตโนมัติ |
| ไฟล์แนบ (สัปดาห์ที่ 9) | `attachmentUrl` รูปของที่เสีย | `attachmentUrl` เอกสารประกอบ |

> 📝 **หมายเหตุเรื่องจำนวนสถานะ:** *จำนวนสถานะไม่เท่ากันโดยตั้งใจ — สองระบบเทียบกันได้ในเชิงโครงสร้าง ไม่ใช่เหมือนกันทุกอย่าง ผู้เรียนจึงต้องแปล ไม่ใช่ลอก ซึ่งเป็นทักษะเดียวกับที่ต้องใช้ตอนทำโครงงานตัวเอง*

> 📌 **คำถามที่ต้องถามตัวเองทุกครั้ง:** "ตอนเช้าผู้สอนทำ `tickets` ของ FixIt — ตอนนี้คุณทำ `leaveRequests` ของ LeaveEasy — **แล้วโครงงานของคุณ โฟลเดอร์หลักคือโฟลเดอร์ไหน?**"
